Tooling for treating an API description as a published artifact rather than a file someone copies around.

[cols="1,3", options="header"]
|===
|Component |What it is

|link:api-only-publisher/README.adoc[API-Only Publisher →]
|A Node.js command-line tool.
Builds one self-contained, linted document per contract from a library of reusable fragments, stamps it with that contract's own version, and publishes it: to a directory, a Maven repository, npm, or a GitHub release.
Published as https://www.npmjs.com/package/@arc-e-tect/api-only-publisher[`@arc-e-tect/api-only-publisher` ↗].

|link:api-only-subscriber/README.adoc[API-Only Subscriber →]
|A Gradle plugin.
Fetches a published contract into a build at the version the build declares, verifies it against a committed lockfile, and fails when the contract has drifted.
Published to the https://plugins.gradle.org/plugin/com.arc-e-tect.api-only-subscriber[Gradle Plugin Portal ↗].

|link:api-only-transcriberj/README.adoc[API-Only TranscriberJ →]
|A Gradle plugin, building on the Subscriber.
Generates a Java class tree from a subscribed contract: bodies, field descriptions and constants for contract tests and stubs, with room for dialects as separate emitter libraries: Spring REST Docs descriptors, and Microcks conformance tests for a contract's events.
Published to the https://plugins.gradle.org/plugin/com.arc-e-tect.api-only-transcriberj[Gradle Plugin Portal ↗].
|===

[#why-one-repository]
== Why they share a repository

They are one design with two halves, and the seam between them is a single artifact: an archive containing the built documents and a `manifest.json` describing them.
Neither knows anything else about the other.

That seam is the whole point, and it is also exactly the kind of thing that rots when its two sides live apart.
A field added to the manifest by a producer that no consumer reads, or a consumer that starts requiring a field no producer writes, is a bug that only exists _between_ two repositories and gets noticed by neither.
Keeping them together means the contract between them is changed in one commit, reviewed as one change, and cannot drift silently.

They are nevertheless **versioned independently**.
A Gradle consumer and an npm consumer are different people with different upgrade cadences, and a change to one half is no reason to make the other half's users take a new version.
The manifest carries a `schemaVersion` so that a producer and a consumer of different vintages can still tell whether they understand each other.

[#development]
== Development

[source,console]
----
# Install the repository's Git hooks first: they check for committed secrets and
# require actionlint when a workflow changes.
./scripts/setup-hooks.sh

# Publisher
npm ci  --prefix api-only-publisher
npm test --prefix api-only-publisher

# Subscriber
cd api-only-subscriber && ./gradlew build

# TranscriberJ
cd api-only-transcriberj && ./gradlew check

# The reference API every tool is tested against: rebuild it after changing a fragment
cd reference-api && npm run apionly -- build
----

link:reference-api/README.adoc[`reference-api/` →] is the specification library the tools are tested against: two services, `system-admin` and `user-account`, built with the Publisher in this repository.
It is not released; its built contracts are committed, and its CI fails when they are not what the fragments build.

To change either tool, read link:docs/reference/how-publisher-and-subscriber-work-together.adoc#extending[Where a change belongs →] first.

[#quality-gates]
== Quality gates

Every component gates its own build on coverage, and every gate was checked by making it fail before trusting it to pass.

[cols="1,2,2,2", options="header"]
|===
| |Publisher |Subscriber |TranscriberJ

|Coverage
|`npm test` enforces 90% of lines and functions, 80% of branches
|JaCoCo, 0.9 minimum, wired into `check`
|JaCoCo, 0.9 minimum, wired into `check`

|Measured
|94.8% lines, 95.8% functions, 88.9% branches
|97.1% instructions, 90.8% branches
|97.2% instructions, 89.9% branches

|Exclusions
|none
|none
|none

|Dependencies
|`npm audit`, failing at moderate and above
|OWASP dependency-check, as the Gradle plugins run it
|OWASP dependency-check, as the Gradle plugins run it
|===

Coverage gates a release; dependency scanning does not.
A vulnerability is discovered by someone else, at a time unrelated to anything this repository does, so gating a release on it means an upstream CVE blocks an unrelated release while a quiet week leaves a known problem unreported.
Both scans run weekly instead, in `nvd-cache-refresh.yml`, which first refreshes the shared NVD database that dependency-check needs and that would otherwise be downloaded per release.

Neither coverage rule excludes anything.
The usual reason to exclude a plugin, its extension and its tasks is that TestKit runs them in another process where the coverage agent cannot see them, so they report zero however well they are tested, and the rule is made to look away from precisely the code worth measuring.
The answer taken here is to test those classes in-process as well, so the number means what it says.

[#releasing]
== Releasing

Every component releases through `semantic-release`, driven by Conventional Commits, each with its own tag namespace (`api-only-publisher-v*`, `api-only-subscriber-v*`, `api-only-transcriberj-v*`) so their version histories are genuinely independent.

The TranscriberJ's emitter interface is part of the plugin, so one release publishes both.

Each is seeded with a `-v0.0.0` tag, and `release/first-release-patch-analyzer.js` forces the first real release to be a patch, so a new component starts at `0.0.1` rather than semantic-release's default `1.0.0`.

A commit that changes only a component's `README.adoc` releases nothing: it documents the component without changing what is published, and the next release carries it.
Run that component's release workflow manually when a README has to reach the registry sooner.

Required repository secrets:

[cols="1,3", options="header"]
|===
|Secret |Used for

|`SEMANTIC_RELEASE_TOKEN`
|Tagging, the release commit, and GitHub releases.
Needs a role that can bypass the `commit-push-main` ruleset, since a release pushes to a protected branch.

|`GRADLE_PUBLISH_KEY` / `GRADLE_PUBLISH_SECRET`
|Publishing the Subscriber and the TranscriberJ to the Gradle Plugin Portal.
|===

The Publisher needs no npm credential: it publishes through npm https://docs.npmjs.com/trusted-publishers[trusted publishing ↗], exchanging a short-lived OIDC token for publish rights, and attaches a provenance attestation tying each tarball to the commit and workflow run that produced it.
Nothing long-lived is stored.
