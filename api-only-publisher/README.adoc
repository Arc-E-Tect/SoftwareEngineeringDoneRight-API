[#what-it-is]
== What it is

`api-only-publisher` turns a library of small, reusable API description fragments into one complete, self-contained document per target, and distributes each to whoever needs it.

It is the producer half of a pair.
The consumer half, the link:../api-only-subscriber/README.adoc[API-Only Subscriber →], fetches a published document into an implementation project and verifies that it has not drifted.
The two are coupled only by the published artifact and its manifest; neither knows anything else about the other.

The link:../api-only-transcriberj/README.adoc[API-Only TranscriberJ →] builds on what the Subscriber fetched: it generates Java classes for contract tests from the published document, named after the fragments the Publisher stamps into it with `x-fragment-path`.

A *target* is whatever gets its own contract document: a microservice, a modular monolith, a backend-for-frontend, or a documentation aggregate spanning all of them.
It need not be a deployable, which is why this is not called `services`.

This document is the reference for the Publisher alone.
To set it up for your situation, start at link:../docs/README.adoc[the documentation →].

[#installation]
== Installation

The Publisher behaves the same however it is started.
What differs is where its version is pinned, and what checks that pin.

[#as-a-development-dependency]
=== As a development dependency

The fit for a specification library, and for any build that runs the Publisher more than once.

[source,console]
----
npm install --save-dev --save-exact @arc-e-tect/api-only-publisher
----

.package.json
[source,json,subs="attributes+"]
----
{
  "private": true,
  "scripts": {
    "apionly": "api-only-publisher"
  },
  "devDependencies": {
    "@arc-e-tect/api-only-publisher": "{api-only-publisher-version}"
  }
}
----

[source,console]
----
npm ci
npm run apionly -- build
npm run apionly -- publish --target orders
----

* The version is pinned in one place, `package.json`, and every command and every CI job runs that one.
* `package-lock.json` records the integrity hash of what was installed, so `npm ci` installs exactly those bytes or fails.
* A CI job can cache the installation, keyed on `package-lock.json`, instead of resolving the tool on every run.
* Renovate and Dependabot see the dependency, so an upgrade arrives as a pull request that moves the pin.
* The cost is a `package.json` and a `package-lock.json` in the library, and an `npm ci` before the first command.

Run it through the script, as `npm run apionly -- <command>`.
`npx api-only-publisher`, without the scope, is not this package: npx would look that name up on the public registry.

[#with-npx]
=== With `npx`, installing nothing

The fit for trying the tool, for scaffolding a library with `init`, and for a one-off command.

[source,console,subs="attributes+"]
----
npx @arc-e-tect/api-only-publisher@{api-only-publisher-version} init my-api-library
npx @arc-e-tect/api-only-publisher@{api-only-publisher-version} build -C my-api-library
----

* Nothing is added to the repository.
* The version is pinned in every command instead, so each script and CI job that runs the Publisher has to name the same version, and nothing checks that they do.
* Without a version, `npx` runs whatever it resolves at that moment, which is not reproducible.
* Nothing records an integrity hash, and nothing notices when a newer version is released.

Either way, pin an exact version rather than a range.
A published contract should change only when its fragments or its version change, and a floating tool version lets it change without either.

The bundlers are a separate matter.
However the Publisher itself is started, it fetches them with `npx`, at the versions `toolchain` in `apionly.yaml` pins.

[#commands]
== Commands

[cols="1,3", options="header"]
|===
|Command |Purpose

|`init [dir] [--yes] [--force] [value flags]`
|Scaffold `apionly.yaml` and a reference directory layout that builds as it stands: OpenAPI, AsyncAPI or both.
At a terminal it asks for each value first, as <<init,Scaffolding a library §>> describes.

|`config [section] [--yes] [value flags]`
|Reconfigure a section of `apionly.yaml` that already exists -- `portfolio`, today.
At a terminal it asks the same shape of question `init` would, offering what is already configured as each default, as <<init-additive,Adding a kind to an existing library §>> and <<aggregates,Aggregates §>> describe.

|`build [--target <t>]... [--pre-release <ids>] [--openapi\|--asyncapi]`
|Stage, substitute placeholders, bundle, stamp each published target's version, and lint.

|`lint [--target <t>]...`
|Lint what is already built, without rebuilding, and write a report per document.
Without `--target`, it also fails on a fragment no target reaches, as <<unreferenced,A fragment no target reaches fails the lint §>> describes.

|`targets`
|List the declared targets, what each one builds, and whether it is published.

|`closure [--target <t>]...`
|Show each target's dependency closure: how many files it reaches, and the hash of their content.

|`changed --since <ref>`
|Report which targets' closures changed between a git ref and the working tree.
A target whose closure is untouched needs no new version, however much else in the repository moved.

|`pack [--pre-release <ids>] [--target <t>]... [--out <dir>]`
|Archive each built, published target with a `manifest.json`, at the version its version file declares.

|`publish [--pre-release <ids>] [--target <t>]... [--channel <c>]... [--out <dir>]`
|Pack once, then ship those same bytes to every configured channel, or to each `--channel`.

|`split --out <dir> [--by kind\|target]`
|Make the library safe to break into separate repositories.
|===

`--target` and `--channel` may be repeated.
`-C <dir>` runs as if started in `<dir>`; without it the configuration is found by walking up from the current directory.
`-q` or `--quiet` reports only errors, which is what a script that reads the output wants.
`--pre-release <ids>` appends pre-release identifiers to each target's version, as <<versions,Versions §>> describes.

[source,console]
----
npm run apionly -- build --target orders --openapi
npm run apionly -- publish --target orders --pre-release rc.1
npm run apionly -- changed --since origin/main --quiet
----

[#init]
== Scaffolding a library

`init` writes a library that builds, lints and publishes as it stands, from a handful of values: which kinds of document it holds, its target's name, the API's title and so on.

[source,console,subs="attributes+"]
----
npx @arc-e-tect/api-only-publisher@{api-only-publisher-version} init my-api-library
----

At a terminal it asks for each value, showing the default in brackets; Enter takes it.
An answer that would break the build later is refused, and the question asked again.

[source,text]
----
Kinds of document: openapi, asyncapi or both [openapi]: both
Target name [example-service]: Customer_Orders
'Customer_Orders' is not a target name: use lowercase letters and digits, in words joined by single hyphens, starting with a letter, such as customer-orders
Target name [example-service]: customer-orders
API title [Example API]: Customer Orders API
Initial contract version [0.1.0]:
...
----

Where nobody is watching -- no terminal, as in CI, a script or an AI assistant -- it asks nothing and takes the defaults, as it always has.
`--yes` (or `-y`) does the same at a terminal.

[cols="2,2,3", options="header"]
|===
|Question |Flag |Default, and what is accepted

|Kinds of document
|`--openapi`, `--asyncapi`; both flags for both
|`openapi`. The library's trees and targets follow from it.

|Target name
|`--target <name>`
|`example-service`. Lowercase kebab-case: a lowercase letter first, then lowercase letters and digits, in words joined by single hyphens -- `orders`, `customer-orders`, `orders-v2`.
The name becomes file names, a properties key, a Maven artifactId, a git tag and, through the Subscriber, a Gradle task name, which treats `-`, `_` and `.` alike; one separator keeps two targets from claiming one task.

|API title
|`--title <text>`
|`Example API`. Any text.

|Initial contract version
|`--contract-version <version>`
|`0.1.0`. A semantic release version, not a pre-release: it goes in the target's version file.

|Contact name
|`--contact-name <text>`
|`Example Team`.

|Contact URL
|`--contact-url <url>`
|`https://example.invalid`. An http or https URL.

|Licence
|`--license <spdx-id>`
|`Apache-2.0`. An SPDX identifier; the URL of a well-known licence follows from it.

|Licence URL
|`--license-url <url>`
|Asked only for a licence whose URL the tool does not know, and then required.

|Production server URL
|`--server-url <url>`
|`https://api.example.invalid`. Asked only for a library with OpenAPI.

|Broker host
|`--broker-host <host[:port]>`
|`kafka:9092`. Asked only for a library with AsyncAPI.
|===

A flag always wins: its question is not asked, and an invalid value, or a flag for a kind the library does not hold, stops `init` before it writes anything.

What each kind of library gets::
* *OpenAPI*: the OpenAPI tree under `specs/openapi/`, its target, and `.redocly.yaml`, the lint rules Redocly applies.
`apionly.yaml` holds no `asyncapi` keys.
* *AsyncAPI*: the AsyncAPI tree under `specs/asyncapi/` -- a channel, a message and its payload -- and its target.
`apionly.yaml` holds no `openapi` keys, and there is no `.redocly.yaml` or Redocly pin: an AsyncAPI document is bundled and validated with the AsyncAPI CLI alone.
* *Both*: both trees, one target building both documents, and one schema they share: `specs/openapi/components/common/schemas/ExampleIdV1.yaml`, which the HTTP response and the event payload both refer to.
That is the library's convention in miniature -- a definition used by both protocols is one fragment -- and why the whole source root is staged together (<<what-build-does,What `build` does §>>).

What it reports::
`init` never overwrites what is there unless told to, and says for every file what it did:
+
[horizontal]
`created`:: The file was not there, and is now.
`identical`:: The file was there, and matches what `init` would write, ignoring line endings and final newlines.
`updated`:: `apionly.yaml` was there, and lacked a kind's configuration; it does now.
The message names every slot added -- see <<init-additive,Adding a kind to an existing library §>>.
`differs`:: The file was there, and does not match: where the library has diverged from the scaffold, usually on purpose.
It is left alone.
`overwrote`:: The file differed, and `--force` replaced it.
+
At a terminal, `--force` first lists the files that still differ -- after any additive update apionly.yaml already got -- and asks once whether to overwrite them; without a terminal, or with `--yes`, it overwrites them without asking.

[#init-additive]
=== Adding a kind to an existing library

Running `init` again, with a kind the library did not have, is how a library grows: the fragments the new kind needs, and the configuration that makes the build see them.

*Files* stay create-only, as everywhere else in `init`: a fragment not written before is written now; one already there, however it now reads, is left alone -- even where the new kind changes what the scaffold would write for it, such as `specs/openapi/paths/example/ExamplesV1.yaml` once an AsyncAPI event comes to share its schema.

*Configuration* is additive: whichever of `sources.<kind>`, `defaults.<kind>`, the kind's pin in `toolchain`, and `targets.<target>.<kind>` `apionly.yaml` lacks is added to it, in the position a library scaffolded with both kinds from the start would have it in.
Every value, key and comment already in the file survives untouched, and a slot that is already there, however it reads, is never touched either -- not even to add something missing from *inside* it: a `defaults.openapi` with no `lint` is a choice, and `init` leaves it that way.

[source,console]
----
$ api-only-publisher init . --yes --openapi --target orders
  created    apionly.yaml
  created    specs/openapi/...

$ api-only-publisher init . --yes --openapi --asyncapi --target orders
  created    specs/asyncapi/...
  updated    apionly.yaml (added sources.asyncapi, defaults.asyncapi, toolchain.asyncapi, targets.orders.asyncapi)
  differs    specs/openapi/paths/example/ExamplesV1.yaml (left alone; --force overwrites)
----

Nothing is asked before completing `apionly.yaml`: unlike `--force`, an additive update never discards anything, so there is nothing to confirm.
Run `init` again with the same kinds, and it reports nothing left to add.

The one slot that is asked about, when it applies, is `portfolio` -- see <<aggregates,Aggregates §>> for what it configures, and why growing past one target is what makes it apply.

[source,console]
----
$ api-only-publisher init . --yes --openapi --target payments
Path prefix strategy for a portfolio: target-prefix or none [target-prefix]:
Where a portfolio's generated bundle root lands, as a directory beside bundles/ [portfolios]:
  created    specs/openapi/...
  updated    apionly.yaml (added targets.payments.openapi, portfolio)
----

`--force` is the other tool for an apionly.yaml that differs, and it does the opposite of the additive update: it reinitialises the file wholesale, exactly as a first run with these values would write it -- any target or key it holds that these values would not produce is gone, additive or not.
Use it to discard a customisation on purpose; use a plain `init` to add a kind without touching anything else.

[#what-build-does]
== What `build` does

. **Stage.** The whole source root is copied to `<build.staging>/<kind>/`.
Nothing after this point touches the hand-authored tree.
+
The *whole* root, not just one specification kind's subtree, because the trees `$ref` each other: an event schema can reuse an OpenAPI component schema, so a field means the same thing in an event as in an HTTP response.
A partial copy breaks those references.
Each kind gets *its own* staging root, so building one never invalidates the other's staged tree.

. **Substitute placeholders**, in place, across the staged copy.
A `{{token}}` is replaced with the contents of `<token>.md`, found by searching the staged source root.
Indentation is preserved, so multi-line Markdown stays valid inside an indented YAML scalar.

. **Bundle.** `@redocly/cli bundle` or `@asyncapi/cli bundle` resolves every `$ref` into one flat, self-contained document under `<build.dist>/<target>/`.
An OpenAPI document's components each carry the path of the fragment they came from, as <<fragment-paths,`x-fragment-path` §>> describes.

. **Stamp the version** of each published target on its *finished* document: the version its version file declares, with any `--pre-release` identifiers appended.
A `publish: false` target keeps the version its source declares.

. **Lint** the finished document, so a broken fragment surfaces against the target it actually affects.
`build` prints the linter's output only when the lint fails, and writes no report; to see warnings, and to write each document's report under `reports.lint`, run `lint`.

[#versions]
== Versions

Every published target has a version of its own, and it is kept in the library, beside the fragments it describes.

.specs/openapi/bundles/orders.bundle.properties
[source,properties]
----
# The version of the orders contract, for every document it builds.
# Semantic: major for a breaking change, minor for an additive one, patch for
# anything else. Change it in the same commit as the fragments it describes.
version=2.1.0
----

By convention the file is `<target>.bundle.properties`, beside the target's first bundle root: its OpenAPI one, or its AsyncAPI one when it has no OpenAPI document.
A target that keeps its version elsewhere names the file with `versionFile`, relative to `apionly.yaml`.
The syntax is that of a Java properties file, so a JVM build can read the same file.

`build`, `pack` and `publish` read the version of every target they act on before they act on any of them.
A missing file, a file without a `version`, or a version that is not semantic stops the command before anything has been built or shipped.
A `publish: false` target is never shipped, so it needs no version file.

The version is not a command-line argument, and that is deliberate.
A version on the command line lets two builds of the same commit publish different versions, and lets through a version nobody reviewed.
A version in the library changes in the same commit as the fragments it describes, is reviewed with them, and is the same whoever builds that commit.

The file holds a release version.
A pre-release is that version with identifiers appended when it is built: `publish --pre-release rc.1` publishes `2.1.0-rc.1`.
Cutting one never means editing the file, and then remembering to edit it back, which is why a version file that declares a pre-release is refused.

A version names one set of documents.
Publishing different documents under a version that was published before, after editing a fragment without changing the version file, is refused by the API-Only Subscriber in every project that locked the earlier ones.
Change the version in the same commit as the fragments instead.

[#closure]
== Independent versioning, and the dependency closure

Giving each target its own version has one non-obvious consequence, and the `closure` and `changed` commands are what pay for it.

A change under `components/common/` affects every target that reaches it.
A change under one target's own fragments affects only that one.
Under repository-wide versioning the distinction is invisible, because everything bumps together; under per-target versioning a release has to know the difference, or one target's edit releases every other target and the version numbers stop meaning anything.

A target's *closure* is every file reachable from its bundle root by following `$ref`s transitively.
`changed --since <ref>` resolves each closure and reports which targets a change actually touched:

[source,console]
----
npm run apionly -- changed --since origin/main
----

Two things make this correct rather than approximate.
The closure is computed over the *staged, substituted* tree, so a change to a Markdown snippet, which genuinely changes the published document, counts.
And a change to the *shape* of a closure always means editing a file already inside it, so a bundle gaining or losing a `$ref` is caught without diffing membership separately.

The closure hash is recorded in each release's manifest as `closureSha256`, which is what lets a later commit compare against what was actually published.

[#splitting]
== Splitting the library

A fragment library is one `$ref` graph, and that graph does not respect the directory boundaries a repository split would follow.
When the AsyncAPI documents reuse `openapi/components/common/schemas/`, moving the two trees into separate repositories as they stand leaves every one of those references dangling.

[source,console]
----
npm run apionly -- split --out build/split --by kind
----

Each part is written with its own subtree *plus* a copy of every foreign file it reaches, so that afterwards each side is self-contained and builds on its own.
The copies keep their original path relative to the shared source root, which is what makes this safe: every relative `$ref` keeps resolving exactly as it did, so nothing is rewritten and no reference can break because a rewrite got the depth wrong.

`--by kind` splits along the specification kinds.
`--by target` gives every target its own self-contained tree, which is what you want before splitting into per-target repositories.

Any part that received copies gets an `IMPORTED.adoc` listing them and saying plainly what it costs: those copies can now drift, and nothing will notice.
A shared schema that two repositories both define is two schemas that happen to agree today.
Where that matters, promote the fragment to a contract of its own, published and consumed like any other, rather than copied.

[#aggregates]
== Aggregates

A whole-landscape view -- a portfolio -- used to be maintained by hand for OpenAPI: every path body already lives in a `$ref`'d fragment, so it can be one table of contents that duplicates no contract text.
It can be written that way, but it does not follow that it should be: nothing stops it silently falling behind the members it lists, the moment a service grows an endpoint and nobody remembers the table of contents is a second place to add it.

AsyncAPI never had the choice.
Its operations use document-root pointers (`channel: {$ref: '#/channels/orderPlacedV1'}`), and `#` resolves against whichever file contains it, so moving an operation into a fragment breaks it.
A hand-written async portfolio would have to copy every operation verbatim, and that copy would start rotting the moment a member changed.

So both are generated.
Declare the members on the target that is the aggregate; nothing here says where its generated root lands, because that is the tool's decision, not the author's -- see <<portfolio-location,Where a generated portfolio lands §>>:

[source,yaml]
----
targets:
  orders:
    openapi:
      bundle: bundles/orders_openapi_structure.yaml
  payments:
    openapi:
      bundle: bundles/payments_openapi_structure.yaml
  portfolio:
    openapi:
      aggregate:
        - orders
        - payments
      info:
        title: Everything, together
        version: 0.0.0
----

The bundle root is synthesised into the staging tree immediately before bundling, so nothing is duplicated in the source and the view cannot fall behind its members.
`info` is the aggregate's own identity; omit it and a generated one names the members instead.
Where every member agrees, an AsyncAPI aggregate looks the same, with `asyncapi.aggregate` in place of `openapi.aggregate`.

[#aggregates-merge]
=== How members merge

A repeated key across members is not always the same kind of event, so there are three modes:

[cols="1,2,2", options="header"]
|===
|Mode |A repeat with an identical value |A repeat that differs

|`unique` (the default)
|Error.
Ownership would be ambiguous even when both members agree, because one of the two would silently not appear in the aggregate.
|Error.

|`agree`
|Merges silently.
Several services publishing to one broker, or defining the same shared security scheme, is the ordinary case, not a conflict.
|Error, naming both members.
Members may share a definition; they may not define it differently.

|`reconcile`
|Merges silently.
|Merges too: reported, and the first contributing member's value wins, deterministically -- an inconsistency to notice and fix, not a defect that fails the build.
|===

What each section of an OpenAPI aggregate uses:

[cols="1,2", options="header"]
|===
|Section |Mode

|`paths`
|Prefixed with the member's target, so a repeat is unreachable in practice; `unique` regardless, so a member listed twice is still caught by name.

|`tags`
|`reconcile`, keyed by the tag's `name`.
Two members `$ref`ing the same shared tag fragment -- the ordinary case -- are one tag in the portfolio; two members describing a tag of the same name differently are reconciled, reported, and the first wins.

|`servers`
|`agree`, the same as an AsyncAPI aggregate already used.

|`security`
|Not merged at all -- pushed down. See <<aggregates-security,Security §>>.

|`components.securitySchemes`
|`agree`. A pushed-down operation's `security` names a scheme, so the name has to mean one thing; rename one of them if two members disagree.

|`components.*` (every other sub-map)
|`agree`, per sub-map.
|===

Every operation id is prefixed with its path's member too, in PascalCase: `orders` contributes `OrdersGetOrder`, `payments` contributes `PaymentsGetOrder`, however each member itself spelled its own id.
Two members sharing an operation id is coincidence rather than intent -- an operation id identifies an operation within its own document -- so this is not configurable.

Paths and operation ids are pass-2 work: the merge above happens on what a member's bundle root shows unresolved, before the aggregate's own output is bundled, because that is the only point at which it is still known which member a path came from.
Prefixing paths and pushing security down happen afterwards, on the aggregate's own bundled document, once every `$ref` -- the members' and its own -- has resolved into something with a name to prefix, reconcile or push onto.
Neither pass changes a fragment: this only ever merges documents.

Prefixing paths assumes path-based routing -- a gateway mapping `/orders/**` to that service.
Where routing is by host instead, and a prefixed path would exist nowhere, `portfolio.openapi.paths: none` leaves every path exactly as its member wrote it; a repeated path is then a genuine, reachable conflict, refused by name.

[#aggregates-security]
=== Security

Root-level `security` is an array of Security Requirement Objects -- an OR, where any one entry satisfies the requirement, and AND within one entry, across several schemes.
`security: []` means explicitly nothing required.
Operation-level `security` *replaces* the root's value; it does not merge with it.

Members legitimately differ: one service requires a bearer token, another's login endpoint cannot.
Three ways to merge that were rejected, and the one that is used:

* *Union the arrays.* Looks natural, and is dangerous: because the array is OR, unioning `[{bearerAuth: []}]` with `[]` says every operation may be called with a bearer token *or with nothing*, weakening every member to its least-authenticated one.
* *Intersect the arrays.* Wrong for the same family of reasons: it silently strips a requirement a member actually has.
* *Require every member to agree* (`agree` mode, as `servers` uses). Safe, but different services legitimately having different authentication is normal, not a mistake, so this would make an ordinary landscape unbuildable.
* *Push each member's root security down onto the operations it contributes* (used). Meaning is preserved exactly, per operation: the portfolio keeps no root `security`, and every operation carries its own -- its member's root, unless the operation already declared one of its own, in which case that one is left alone, since it already replaces the root.
A member whose root is explicitly `security: []` has `[]` pushed down explicitly too, rather than left absent: absent means "inherit", and inheriting from an absent root only *coincidentally* means the same thing.

The portfolio is more verbose than its members for this, which is the fair price of being accurate about each one.
Because a YAML comment does not survive bundling -- it parses and re-serialises -- the portfolio says so twice: `info.description` gains a line, for a reader, and `x-security-note` carries the same text machine-readably.

[#aggregates-never-published]
=== An aggregate is never published

A portfolio is a catalogue.
You do not ship a catalogue; you ship the things in it, each on its own, with its own version and its own owner.

* Declaring `aggregate` for a kind means the target is never published for that kind, whatever `publish` says; writing `publish: false` beside it is accepted but no longer necessary.
* `publish: true` alongside an aggregate is refused, naming why: prefixed operation ids match no member's, so a subscriber locking one builds against a name nothing uses; the TranscriberJ names a class after `operationId`, so transcribing a portfolio makes `OrdersGetOrderOperation` where the member makes `GetOrderOperation`; and a portfolio's version answers no useful question, since it moves whenever anything anywhere moves.
A combined surface that genuinely needs publishing is a bundle somebody authors deliberately, with its own owner and version, not a by-product of aggregation.
* A target may not declare both `aggregate` and `bundle` for the same kind: an aggregate is generated whole, so there is no hand-written base to merge into.
* A target aggregating one kind must aggregate every kind it declares; mixing an aggregate for one kind with a hand-written bundle for another is refused.
Somebody who wants a hand-written AsyncAPI portfolio writes an ordinary bundle that happens to look like one, in the bundles location, as an ordinary published target -- which is then a bundle, not a portfolio, the honest description of what they made.
* An aggregate cannot list itself, directly or through another aggregate: nesting is not supported, so listing one aggregate as another's member is refused by name.

[#portfolio-location]
=== Where a generated portfolio lands

Outside the bundles directory, at the same depth: `specs/openapi/portfolios/` beside `specs/openapi/bundles/`, `specs/asyncapi/portfolios/` beside `specs/asyncapi/bundles/`.

That depth matters more than it looks.
The merged document carries each member's `$ref` strings over verbatim -- `../paths/common/RootV1.yaml` -- and those resolve correctly only from the same directory depth the member's own bundle root sat at.
Putting the generated root anywhere else would mean rewriting every such reference, which is work with a subtle failure mode and no benefit, so the directory is fixed at that depth instead.

Keeping generated portfolios out of `bundles/` also makes them visibly separate from what is hand-authored -- nothing hand-written should ever `$ref` into a portfolio, since it is regenerated, and can change shape, on every build.

[#portfolio-config]
=== Configuring a portfolio

Every strategy above has a documented default and a name in `apionly.yaml`'s `portfolio` section, which is absent by default -- an aggregate with no section builds on the defaults, and needs none added to work:

[source,yaml]
----
portfolio:
  openapi:
    paths: target-prefix       # target-prefix (default) | none
    operationIds: target-prefix  # the only value today; named for room to grow
    tags: reconcile               # the only value today
  security: push-down             # the only value today
  location: portfolios            # the directory name, beside bundles/, under each kind
----

Because a portfolio is regenerated on every build, changing a setting here needs no migration: the next build simply produces a different portfolio.

`init` writes this section -- asking, at a terminal, about `paths` and `location` -- once a library is about to have more than one target and does not have the section yet, the same way it writes a kind's own configuration; see <<init-additive,Adding a kind to an existing library §>>.
It never changes a section that already exists, and says so rather than passing over it in silence: `  present    portfolio (already configured; init never changes it)`.

`config portfolio` is the other side of that: it always asks, offering what is already configured as each default, and always rewrites the keys it asked about, whatever else the section or the file holds:

[source,console]
----
$ api-only-publisher config portfolio
Path prefix strategy for a portfolio: target-prefix or none [target-prefix]: none
Where a portfolio's generated bundle root lands, as a directory beside bundles/ [portfolios]:
Configured portfolio: paths=none, location=portfolios
----

`--portfolio-paths` and `--portfolio-location` answer those questions from the command line, for both `init` and `config`, the same way `init`'s other value flags do.

[#channels]
== Channels

[cols="1,3", options="header"]
|===
|Channel |What it is for

|`file`
|A local directory, laid out as `<directory>/<target>/<version>/`.
Not a distribution mechanism between repositories: it makes the pipeline testable end to end with no infrastructure, lets a library share one build with the projects that implement it, and is a local-iteration escape hatch.
Publishing a version again replaces that version and keeps the others; with `clean: true` only the version being published is kept, for a directory that is a build output rather than a record of releases.

|`maven`
|A path publishes into a repository layout on disk; an `http(s)` URL deploys to a remote repository with an HTTP `PUT` per file and a bearer token.
Native for Gradle consumers: version resolution, caching and conflict handling come free, which is what lets the Subscriber carry no HTTP client of its own.

|`npm`
|Real semver, integrity hashes, private scopes, and a toolchain that is already Node.js.

|`github-release`
|The language-neutral floor: immutable per tag, works for private repositories with a token, readable by a consumer with no JVM and no Node.js.
No dependency-resolution semantics and no update notification, which is why it is the fallback rather than the default.
|===

Credentials are read from the environment, never from configuration.
`channels.maven.tokenEnv` names the variable, `MAVEN_TOKEN` by default; a configuration file gets committed, and a credential in a committed file is a credential that has leaked.

link:../docs/reference/how-publisher-and-subscriber-work-together.adoc#channels[How the Publisher and the Subscriber work together →] lists each channel's layout and options.

[#why-registries]
=== Why npm and Maven rather than release assets alone

Publishing is passive.
The producer releases `2.1.0` and nothing happens in an implementation repository until somebody looks.

Renovate and Dependabot understand npm and Maven natively, so a contract bump arrives downstream as a pull request without any bespoke machinery.
That is the practical argument for preferring them, and the reason to design the coordinates so that standard update bots can read them.

[#pre-releases]
== Pre-releases

API-first design means implementation starts against a contract that is not finished.
If the only way to obtain a bundle were a final release, teams would work around the tool by cloning the specification repository, which is exactly the broad read access that publishing artifacts exists to avoid, with none of the guarantees.

So a pre-release version is first-class: `2.1.0-rc.1`, or Maven's `-SNAPSHOT` spelling, which is not semver-legal but is what Maven consumers expect.
It is cut from the version in the target's version file: `publish --pre-release rc.1` publishes `2.1.0-rc.1` when the file declares `2.1.0`.

The hard rule is the other half of it.
A pre-release must never quietly satisfy a production build:

* npm publishes it under the `next` dist-tag, never `latest`, so `npm install` cannot pick one up by accident.
* A GitHub release is marked as a pre-release, so "latest release" never resolves to an unfinished contract.
* The API-Only Subscriber refuses a pre-release version outright unless the subscription sets `allowPrerelease = true`: a visible, reviewable line in a build file rather than a default.

[#configuration]
== Configuration

Everything project-specific lives in `apionly.yaml`, not in the code.
Adapting the tool to another project means editing configuration.

[source,yaml]
----
# The version of this file's own format -- which keys apionly.yaml has and what
# they mean -- not of any API. This Publisher understands 1, and refuses others.
schemaVersion: 1

sources:
  root: specs          # staged wholesale; the kinds share fragments
  openapi: openapi     # each kind's directory under root; bundle paths start here
  asyncapi: asyncapi

defaults:
  openapi:
    lint: .redocly.yaml
    # The file name of every built OpenAPI document: build/dist/<target>/openapi.yaml.
    # The Subscriber looks for exactly this name.
    outputName: openapi.yaml
    fragmentPaths: true  # x-fragment-path on every component; the default
  asyncapi:
    outputName: asyncapi.yaml  # as for OpenAPI: build/dist/<target>/asyncapi.yaml
    fragmentPaths: true  # x-fragment-path on every fragment; the default
  placeholders:
    strict: true       # an unresolved {{token}} fails the build

build:
  staging: build/staging
  dist: build/dist
reports:
  lint: build/reports/lint
lint:
  unreferenced: error  # a fragment no target reaches: error, warn or off
  examples:
    asyncapi: warn      # a message with no example: error, warn (the default) or off
    openapi: warn       # a request body or response with no example: error, warn (the default) or off

toolchain:
  redocly: "@redocly/cli@2.52.0"
  asyncapi: "@asyncapi/cli@6.0.2"

channels:
  file:
    directory: build/publish
    clean: true        # keep only the version being published

targets:
  orders:
    # versionFile: versions/orders.properties
    #              default: orders.bundle.properties beside the first bundle root
    openapi:
      # The bundle root the document is built from, relative to specs/openapi/.
      # It is built into build/dist/orders/openapi.yaml, named by outputName.
      bundle: bundles/orders_openapi_structure.yaml
    asyncapi:
      # Relative to specs/asyncapi/; built into build/dist/orders/asyncapi.yaml.
      bundle: bundles/orders_asyncapi_structure.yaml
  portfolio:
    openapi:
      # Generated, not hand-written: never a bundle, never published -- see
      # Aggregates §, below.
      aggregate:
        - orders

portfolio:                # absent is fine; an aggregate builds on documented defaults
  location: portfolios    # see Aggregates §
----

`targets` is the single source of truth for what gets built.

Every key here is checked against what that level of `apionly.yaml` allows -- a `portfolio:` block that lands under `build:` by a bad indent is `unknown key 'portfolio' in build`, not a silently ignored typo.
`channels` and `toolchain` are the two exceptions: a channel's settings depend on its type and a tool's name is whatever the author calls it, so neither has a closed vocabulary to check against.

A target's `bundle` and a kind's `outputName` are the two ends of one build: the bundle root is what a document is built *from*, in the library, and `outputName` is what it is built *to*, in `<build.dist>/<target>/`.
Every target's document of one kind has the same `outputName`; keep the defaults, `openapi.yaml` and `asyncapi.yaml`, because the Subscriber looks for exactly those names.

[#bundle-roots]
=== Where bundle roots go

Put every bundle root in a `bundles/` directory of its kind's source directory, named `<target>_<kind>_structure.yaml`: `specs/openapi/bundles/orders_openapi_structure.yaml` and `specs/asyncapi/bundles/orders_asyncapi_structure.yaml`.
The `init` scaffold lays out its bundle roots this way, for each kind it writes.

* A bundle root is a table of contents rather than a fragment, and a `bundles/` directory keeps the two apart.
* The name says which target and which kind, so the two roots of one target are never confused, in the tree or in a review.
* The version file's default place is beside the target's first bundle root (<<versions,Versions §>>), so it lands in `bundles/` too.

The Publisher does not require it: a bundle path is any path relative to the kind's source directory.
A bundle root moved into or out of `bundles/` needs its relative `$ref`s adjusted by one `../`, since they resolve against the file's own directory; the built document is otherwise the same.

[#pinning-the-bundlers]
=== Pinning the bundlers

`toolchain` pins the bundler versions.
Unpinned, the documents this tool produces could change because an upstream release happened, with nothing in the library having changed.
An upgrade should be a deliberate commit that moves the pin, reviewed with whatever it changes in the published documents.

[#behaviour]
== Behaviour worth knowing about

[#unresolved-placeholders]
=== Unresolved placeholders fail the build

An unresolved `{{token}}` is an error, so a broken contract cannot ship from a green build.
Set `defaults.placeholders.strict: false` to leave the token visible in the document instead.

[#placeholder-search]
=== Placeholder snippets are found from the source root

`<token>.md` is searched for from the staged source root downwards, so a snippet can live anywhere under it.

[#unreferenced]
=== A fragment no target reaches fails the lint

A linter checks documents, and a fragment reaches a document only through a `$ref`.
A fragment that no target references is therefore never linted, however wrong it is, until the day a target starts to use it.

So `lint`, run without `--target`, also lists every YAML file under the source root that no target's closure reaches, in `<reports.lint>/unreferenced.txt`, and fails when there is one.
Every target counts, `publish: false` ones included, because they are linted too.
That reports a fragment that does not comply before anything uses it, and finds a definition left behind by a change that stopped using it.

Configuration is not a fragment, so it may sit anywhere, `sources.root` included.
The check skips the well-known configuration files of lint tools, wherever they are: `redocly.yaml`, `.redocly.yaml`, `.redocly.lint-ignore.yaml`, `.spectral.yaml`, `.spectral.yml`, and `apionly.yaml`.
It also skips the lint configurations `defaults.<kind>.lint` names, whatever they are called.
Any other YAML file under the source root counts.

`lint.unreferenced` in `apionly.yaml` sets what happens: `error` by default, `warn` to report without failing, or `off` not to look.
`lint --target` does not look, because an unreferenced fragment belongs to no target.

`lint` lints every document even when one of them fails, and names every failure at the end, so a single run reports all of them.

[#examples-check]
=== An operation with no example is reported apart from lint

`build` also checks, after linting, whether each operation's example is one the rest of the API-Only toolchain could use -- and reports that separately from lint's own findings, since "your contract is wrong" and "your contract limits what you can do with it downstream" are different claims.
Neither specification requires an example, and this is not a specification-validity rule: it is never run as a Redocly plugin or a Spectral ruleset.

For AsyncAPI, it is whether a message's own `examples` array is non-empty -- what Microcks reads to build its async mocks and its conformance tests:

[source,text]
----
AsyncAPI operation '<operationId>': message '<messageKey>' (<fragment, or where in the bundle>) carries no example, so this bundle cannot be used for Microcks-based conformance testing.
----

For OpenAPI, it is whether a request body's or response's media type declares `example`/`examples`, or the schema it references carries its own top-level `examples`.
Nothing downstream currently reads an OpenAPI example, so the message never claims the bundle cannot be used -- only that the generated documentation is weaker without one:

[source,text]
----
OpenAPI operation '<operationId>': <request body, or response <status>> (<fragment, or where in the bundle>) carries no example, which makes the generated documentation harder to read.
----

A body or response with no `content` at all, such as a `204`, has nothing to exemplify and is never reported.

`lint.examples.asyncapi` and `lint.examples.openapi` each default to `warn`; `error` fails the build, `off` does not look.
A library that has adopted the Microcks-based conformance emitter will usually want `lint.examples.asyncapi: error`: publishing a bundle its own toolchain cannot use is a real defect there, not merely a gap (link:../docs/reference/authoring-a-specification-library.adoc#give-every-operation-an-example[Give every operation an example →]).

[#version-stamping]
=== Version stamping edits one scalar

Stamping sets `info.version` in the *built* document, `<build.dist>/<target>/<outputName>`, after bundling.
The value it replaces comes from the bundle root's `info` block, written in the bundle root or `$ref`'d from a fragment, which the bundler puts into the document: every bundle root therefore needs an `info` block with a `version`, conventionally `0.0.0`.
The `init` scaffold's bundle root refers to `specs/openapi/shared/info.yaml`, which declares `version: 0.0.0`.
The version that replaces it is the target's version file's (<<versions,Versions §>>).

`info.version` is located structurally and that one scalar is spliced.
It is deliberately not a re-serialisation: re-emitting a document reformats everything around the edit, because the AsyncAPI CLI wraps long descriptions at a width no YAML emitter reproduces.
Splicing keeps every other byte exactly as the bundler wrote it.
A document with no `info` block, or no version inside it, is an error.

[#fragment-paths]
=== Every component says which fragment it came from

Bundling flattens the library's directories into one `components` namespace, and the bundler names each component after its file.
Two fragments with the same file name in different directories become `UserV1` and `UserV1-2`, and nothing in the document says which is which.

So every component the bundler builds from a fragment carries that fragment's path, relative to `sources.root`, as its first key:

[source,yaml]
----
components:
  schemas:
    UsernameV1:
      x-fragment-path: openapi/components/common/schemas/UsernameV1.yaml
      type: string
----

The path always uses forward slashes, and it names a file in the library.
Other OpenAPI tooling ignores the key, as it ignores any `x-` extension.
It is how the API-Only TranscriberJ ties generated code to the fragment it came from, instead of to a component name the bundler picked.

It is on by default, for both specification kinds.
`defaults.openapi.fragmentPaths: false` and `defaults.asyncapi.fragmentPaths: false` turn it off, each for its own kind.

How it is done, for OpenAPI::
The bundler is not told anything; it is shown stamped fragments, in copies of the staged tree under `<build.staging>/fragment-paths/<target>/`.
The first bundle is built with every fragment stamped, to learn which fragments become components.
The second, the one that is published, is built with only those stamped.
So a document differs from one built with `fragmentPaths: false` by exactly one line per component, and in no other byte.
The cost is a second bundler run per OpenAPI target.
+
An AsyncAPI target is stamped differently, in one run and with every fragment stamped, because its bundler inlines rather than hoists: <<fragment-paths-asyncapi,AsyncAPI, where the bundler inlines rather than hoists §>> describes it.

What stops the build::
A fragment that writes `x-fragment-path` itself: the Publisher sets that key and nothing else may.
A component's fragment that is also inlined somewhere else in the same document, since the inlined copy would carry the key as well; the error names where.

A component written directly in a bundle root, rather than `$ref`'d from a fragment, has no fragment and carries no path.

[#fragment-paths-asyncapi]
==== AsyncAPI, where the bundler inlines rather than hoists

An AsyncAPI bundle has no `components` section at all.
The bundler inlines a message into its channel, the message's payload into the message, and any schema that payload references into the payload.
So there is nothing to hoist and nothing to select: every fragment is stamped, and the stamp arrives wherever the bundler put that fragment.

[source,yaml]
----
channels:
  auditV1:
    x-fragment-path: asyncapi/channels/iff/useraccount/AuditV1.yaml
    address: iff.useraccount.audit.v1
    messages:
      registrationInitiatedMessage:
        x-fragment-path: asyncapi/messages/iff/useraccount/RegistrationInitiatedMessageV1.yaml
        payload:
          x-fragment-path: asyncapi/components/iff/useraccount/schemas/RegistrationInitiatedEventV1.yaml
          properties:
            username:
              x-fragment-path: openapi/components/common/schemas/UsernameV1.yaml
----

The last of those is the point of a shared library: a schema the OpenAPI tree owns keeps its own path when an event payload references it, so a consumer can tell that the `username` in an event and the `username` in a response are one fragment, and generate one class for both.

The bundle root is the document rather than a fragment of one, so it is never stamped.
One bundler run is enough, because nothing has to be discovered first.

What stops the build::
A fragment that writes `x-fragment-path` itself, as on the OpenAPI side.
A stamp in the built document that names no file in the library, which would mean the bundler moved a stamp away from what explains it.

[#fragment-path-versions]
==== What a change to `x-fragment-path` means for a contract's version

Semantic versioning describes the contract, so the version follows from what a change does to the contract's promises.
The Publisher does not decide it: it stamps whatever the target's version file declares.
Choosing the next version is the API designer's responsibility, and this table is their guideline:

[cols="2,1,3", options="header"]
|===
|Change |Version |Why

|The key appears for the first time
|MINOR
|A new feature of the published document.

|A fragment moves to another directory, changing the value
|PATCH
|The contract promises the same; only its provenance metadata differs.

|The key is removed, by `fragmentPaths: false` after it was published
|MAJOR
|Consumers relying on it lose provenance and collision disambiguation, and may stop generating code at all.
|===

The policy is the same for both kinds: an AsyncAPI document gains the key exactly as an OpenAPI one does, and the version follows the table above.

Upgrading to a Publisher that stamps the key changes every OpenAPI document that has components built from fragments, and every AsyncAPI document that has fragments at all.
`changed` does not see that, because a target's closure hash covers the fragments, not the Publisher.
Bump each such target's MINOR version in the upgrade's commit, or set `fragmentPaths: false` for the kind until you do: publishing a changed document under a version already published is refused by every Subscriber that locked it (see <<versions,Versions §>>).

[#distribution]
=== `distribution` is transitional

A producer has no business knowing the directory layout of the projects that consume it.
The `distribution` block copies built documents into such a layout, so that a library can adopt this tool before its consumers adopt the API-Only Subscriber.
Once they subscribe, each consuming project declares where its own copy lands, and the block goes away.

[#adapting]
== Adapting it to another project

The tool has no dependency on any particular product, framework or directory layout.
In order of what usually needs changing:

[cols="2,3", options="header"]
|===
|What |Where

|Which documents get built
|`targets`

|Where the fragments live
|`sources`

|What each document is called
|`defaults.<kind>.outputName`

|The lint rules
|`defaults.openapi.lint`

|Whether built documents carry `x-fragment-path`
|`defaults.openapi.fragmentPaths` and `defaults.asyncapi.fragmentPaths`, each defaulting to `true`

|Where lint reports go
|`reports.lint`, a directory, defaulting to `build/reports/lint`: each document's report is `<target>/<kind>.txt` in it, beside `unreferenced.txt`

|Where built documents go
|`build.dist`

|Where artifacts are published
|`channels`

|Where a target's version is kept
|Its version file, or `targets.<target>.versionFile`
|===

Beyond that, a `components/common/` directory beside per-target directories is one convention for organising a multi-target fragment library, not a requirement.
A single-target project can keep every fragment in one flat directory, or skip fragments entirely and hand-author one complete document.
The tool only needs one bundle root file per target; what that file `$ref`s, or whether it `$ref`s anything at all, is up to the library.

Placeholders are optional too.
A library with no `{{token}}` anywhere simply has nothing substituted.

[#breaking-changes]
== Breaking changes

The tool does not police them.
`changed` tells a release which targets a commit altered, and every manifest records the closure hash of what was published, so the hooks a diff gate would need already exist, but the gate itself is deliberately not built.

[IMPORTANT]
.The API designer defines the contract's version, not the Publisher
====
The Publisher reads a target's version from its version file and stamps it; it refuses a version that is not a semantic release version, and nothing else.
It never works out a version from what changed, and never checks that a version matches the change.
Whether a change is major, minor or patch is the API designer's decision, and so is its consequence: raising the version in the target's version file.
====

A breaking change is declared where it is made: the major version in the target's version file changes in the same commit as the fragments it breaks.
A specification library should write down its own policy for what counts as breaking.

[#as-a-library]
== Using it as a library

Everything the CLI does is available programmatically, so a release job that wants to decide something for itself does not have to parse console output:

[source,javascript]
----
const { loadFrom, prepare, changedSince } =
    require('@arc-e-tect/api-only-publisher');

const config = loadFrom('.');
prepare(config);

for (const result of changedSince(config, 'origin/main')) {
    if (result.changed) {
        console.log(`${result.target} changed: ${result.files.join(', ')}`);
    }
}
----
