[#in-short]
== In short

Your project implements an API whose contract another team or another company designs and publishes: an architecture team's contract, a partner's specification, an industry standard.
You did not write the contract, you cannot change it, and it reaches you as an artifact in a Maven repository.

The API-Only Subscriber fetches the contract at the version your project implements, checks every document against the archive's own manifest, records the version and the hashes in a committed lockfile, and puts the documents at the root of the classpath.
Every `./gradlew check` verifies that what your build implements is still what you locked.

Nothing in this use case runs the API-Only Publisher: the other side runs it.

[#fits]
== When this fits

* Someone else owns the contract, and publishes it as an archive built by the API-Only Publisher to a Maven repository your build can read.
* Your project implements that contract, and no other.
* Your project builds with Gradle.
* You want your build to state exactly which version of that contract it implements, and to fail rather than drift when that contract changes.

[#does-not-fit]
== When it does not

* **Your project calls the API rather than implementing it.**
That is a client use case: link:../../client/4-calling-a-published-api/overview.adoc[client use case 4 →] is this situation from the calling side.
* **You own the contract too.**
If it lives in the project that implements it, that is provider use case 1; if it is a library shared by projects in one repository, provider use case 2; if it is in its own repository, provider use case 3.
* **The contract is published only as a plain `openapi.yaml`**, without the Publisher's archive and manifest.
The Subscriber needs the manifest to verify the documents; an ordinary Gradle dependency is then the honest alternative.
* **Your project does not build with Gradle.**
The Subscriber is a Gradle plugin; a producer can also publish to npm or as a GitHub release, which other ecosystems can read.

link:../../../README.adoc[The documentation's entry point →] compares every use case.

[#what-you-get]
== What you get

* A build that cannot silently start implementing a different contract.
* A committed `apionly.lock` that answers "which version of their contract do we implement?" by reading your own repository.
* A test that proves the contract reaches your code.
* A build failure, not a production surprise, when a fetched document is edited or a released version is republished with different bytes.
* A visible, reviewable line whenever the project works against an unfinished contract.

[#what-you-do-not-need]
== What you do not need

Node.js, the Publisher, or access to the fragments the contract is built from.
The archive is everything your build needs, and the manifest inside it is what makes the archive verify itself.

[#adoption]
== Adoption in broad strokes

. **Get the coordinates from the producer**, in one conversation: the Maven repository's URL, the group id, the contract's target name, and the versions available.
. **Declare the version your project implements** as `apiContractVersion` in `gradle.properties`.
. **Write the contract test first**: a test that fails until the contract, at that version, is on the classpath.
. **Apply the Subscriber**: the Maven repository, with its credentials read from outside the build file, the `maven` channel with the producer's group id, and a `subscribe` to the contract.
. **Run `./gradlew check`**, and commit `apionly.lock`.
. **Run the same `./gradlew check` in CI**, with the repository credentials in the environment, and fail the build when the lockfile changed.

[#day-to-day]
== Day to day

* **Taking a new version**: change `apiContractVersion`, run `./gradlew check`, and commit the updated `apionly.lock` with the change.
* **Working against an unfinished contract**: subscribe to the pre-release and set `allowPrerelease = true`, visibly and temporarily.
* **Noticing new releases**: publishing is passive, so nothing tells you a new version exists.
Watch the producer's releases, or configure an update bot to read `apiContractVersion`.
* **Calling other APIs as well**: see link:../../both/implementing-and-calling/overview.adoc[the use case for a project that implements one contract and calls others →].
