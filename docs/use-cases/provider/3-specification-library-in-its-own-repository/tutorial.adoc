Every link ends with a marker saying where it leads, so you can tell before you follow it:

====

This tutorial builds provider use case 3 from nothing, on both sides.
First a `contracts` repository that releases two contracts, `orders` and `payments`, to a Maven repository; then an implementing project in another repository that builds against one of them.
Every file, command and script below was run exactly as shown, with API-Only Publisher {api-only-publisher-version} and API-Only Subscriber {api-only-subscriber-version}, against a Maven repository on disk.
Those are the versions it was verified with; a newer release works the same unless its changelog says otherwise, and the README of link:../../../../api-only-publisher/README.adoc[the Publisher →] and link:../../../../api-only-subscriber/README.adoc[the Subscriber →] says which release is the latest.
What was not run is the part a remote Maven repository adds: the upload with a token in step 8, and resolving with credentials in step 12.
Step 8 says what to check there.
<<gitlab,On GitLab §>> does the same with GitLab's package registry instead; it was not run as part of this tutorial either.

It assumes you know how to design an API in OpenAPI, how a bundler such as https://redocly.com/docs/cli/[Redocly CLI ↗] resolves `$ref`s into one document, and how a Gradle project resolves dependencies.

== The contracts repository

[#step-1]
=== Step 1: Pin the Publisher

.package.json
[source,json]
----
{
  "name": "contracts",
  "private": true,
  "scripts": {
    "apionly": "api-only-publisher"
  }
}
----

[source,console,subs="attributes+"]
----
npm install --save-dev --save-exact @arc-e-tect/api-only-publisher@{api-only-publisher-version}
----

Add `node_modules/` and `build/` to `.gitignore`, and commit `package.json` and `package-lock.json`.

.Considerations
* **Run the Publisher only through the script**: `npm run apionly -- <command>`.
It runs the version `package-lock.json` pins, and nothing else.
`npx api-only-publisher` is not this package; npx would look that unscoped name up on the public registry.

get:

  summary: List the orders.
  responses:

      content:
        application/json:

            type: array
            items:
              type: string

[#step-7]
=== Step 7: The two release scripts

Two checks decide what a release does: a changed contract must have a new version, and a version is released once.
Git tags record what was released, one per contract version, named `<target>-v<version>`.

.scripts/check-versions.sh
[source,bash]
----
#!/usr/bin/env bash
# Fails when a contract changed since <ref> but its version is already released.
set -euo pipefail
since="$1"

status=0
for target in $(npm run --silent apionly -- changed --since "$since" --quiet); do
  version="$(sed -n 's/^version=//p' "specs/openapi/bundles/$target.bundle.properties")"
  if git rev-parse --quiet --verify "refs/tags/$target-v$version" > /dev/null; then
    echo "::error title=Contract version not raised::$target changed, but $target $version is already released. Raise its version."
    status=1
  fi
done
exit "$status"
----

.scripts/release.sh
[source,bash]
----
#!/usr/bin/env bash
# Publishes every contract whose current version has no release tag yet, and tags it.
# Run after `npm run apionly -- build`.
set -euo pipefail

for target in $(npm run --silent apionly -- targets | grep -v '(publish: false)' | awk '{print $1}'); do
  version="$(sed -n 's/^version=//p' "specs/openapi/bundles/$target.bundle.properties")"
  tag="$target-v$version"
  if git rev-parse --quiet --verify "refs/tags/$tag" > /dev/null; then
    continue
  fi
  npm run --silent apionly -- publish --target "$target"
  git tag "$tag"
  echo "Released $target $version"
done
----

Make both executable, commit, and try them.

The first release publishes everything, because nothing is tagged yet:

[source,console]
----
npm run apionly -- build
./scripts/release.sh
----

[source]
----
Released orders 1.0.0
Released payments 1.0.0
----

A second run releases nothing.

Now change the `orders` contract without raising its version.
Add a description to the operation in `Orders.yaml`, below its `summary`:

.specs/openapi/paths/Orders.yaml (addition)
[source,yaml]
----
  description: Lists every order, newest first.
----

Commit, and check against the commit before the change:

[source,console]
----
./scripts/check-versions.sh HEAD~1
----

[source]
----
::error title=Contract version not raised::orders changed, but orders 1.0.0 is already released. Raise its version.
----

Raise `version` in `orders.bundle.properties` to `1.1.0`, and commit.
The check against the commit before the change, now `HEAD~2`, passes:

[source,console]
----
./scripts/check-versions.sh HEAD~2
----

In a pull request, that commit is the base branch, which is what the workflow in step 9 passes.
The next release publishes `orders` 1.1.0 and tags `orders-v1.1.0`, and leaves `payments` alone:

[source,console]
----
npm run apionly -- build
./scripts/release.sh
----

[source]
----
Released orders 1.1.0
----

.Considerations
* **Why tags, and not "whatever changed in the last commit".**
A release job that publishes the untagged versions recovers by itself from a failed run, and releases exactly what the version files say.
* **The version file path in the scripts** assumes each contract's version sits beside an OpenAPI bundle root in `specs/openapi/bundles/`.
Adjust the path if a contract has only an AsyncAPI document, or a `versionFile` of its own.
* **A shared fragment** changes every contract that reaches it, so `check-versions.sh` asks for each of them to get a new version.

[#step-8]
=== Step 8: Point the channel at the Maven repository

.apionly.yaml (channels)
[source,yaml]
----
channels:
  maven:
    groupId: com.example.contracts
    repository: https://maven.example.com/repository/contracts
    tokenEnv: MAVEN_TOKEN
----

For a URL, the Publisher uploads each file with an HTTP `PUT`, and sends the token from the environment variable `tokenEnv` names as a bearer token: `Authorization: Bearer <token>`.
The token is never written in `apionly.yaml`, which is committed.

.Considerations
* **Check that your repository accepts that upload** before the first real release: publish a throwaway version of a throwaway target from a local shell, with `MAVEN_TOKEN` set, and delete it again.
A `401` or `403` names the variable to check.
* **A remote repository usually refuses to overwrite a released version**; a directory does not.
The release script never republishes a tagged version, so neither case arises in normal operation.

[#step-9]
=== Step 9: Run it in CI

A pull request builds, lints and checks the versions:

..github/workflows/check.yml
[source,yaml]
----
name: check

on:
  pull_request:

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: actions/setup-node@v6
        with:
          node-version: 24
      - run: npm ci
      - name: Build and lint every contract
        run: |
          npm run apionly -- build
          npm run apionly -- lint
      - name: Every changed contract has a new version
        run: ./scripts/check-versions.sh "origin/$GITHUB_BASE_REF"
      - name: Upload the lint reports
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: api-lint-reports
          path: build/reports/lint/
----

The main branch releases:

..github/workflows/release.yml
[source,yaml]
----
name: release

on:
  push:
    branches: [main]

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: actions/setup-node@v6
        with:
          node-version: 24
      - run: npm ci
      - name: Build and lint every contract
        run: |
          npm run apionly -- build
          npm run apionly -- lint
      - name: Publish every contract whose version is not released yet
        env:
          MAVEN_TOKEN: ${{ secrets.MAVEN_TOKEN }}
        run: ./scripts/release.sh
      - name: Push the release tags
        run: git push origin --tags
----

.Considerations
* **`fetch-depth: 0`** gives both jobs the history and the tags the scripts read.
* **`MAVEN_TOKEN`** is a repository secret holding a token that can upload to the Maven repository.

[#step-10]
=== Step 10: Pre-releases

An implementation usually starts before a contract is finished.
Publish a pre-release of the version the contract is heading for, without editing its version file:

[source,console]
----
npm run apionly -- build --target orders --pre-release rc.1
npm run apionly -- publish --target orders --pre-release rc.1
----

With `version=1.1.0` in `orders.bundle.properties`, that publishes `orders` `1.1.0-rc.1`.
A consumer builds against it only when its subscription sets `allowPrerelease = true`, so an unfinished contract never satisfies a build by accident.

=== Step 11: Declare the version, and write the contract test first

.gradle.properties
[source,properties]
----
# The version of the orders contract this project implements.
apiContractVersion=1.1.0
----

.build.gradle
[source,groovy]
----
plugins {
    id 'java'
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation platform('org.junit:junit-bom:6.1.3')
    testImplementation 'org.junit.jupiter:junit-jupiter'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}

tasks.named('test') {
    useJUnitPlatform()
    // The contract version this project implements, for ApiContractTest.
    systemProperty 'apiContractVersion', providers.gradleProperty('apiContractVersion').get()
}
----

.src/test/java/com/example/orders/ApiContractTest.java
[source,java]
----
package com.example.orders;

import org.junit.jupiter.api.Test;

import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertTrue;

class ApiContractTest {

    @Test
    void theContractThisProjectImplementsIsOnTheClasspath() throws IOException {
        try (InputStream document = getClass().getResourceAsStream("/openapi.yaml")) {
            assertNotNull(document, "openapi.yaml is not on the test classpath");
            String text = new String(document.readAllBytes(), StandardCharsets.UTF_8);
            String version = System.getProperty("apiContractVersion");
            assertTrue(text.contains("version: " + version),
                "openapi.yaml does not declare version " + version);
        }
    }
}
----

`./gradlew test` fails, and the test report says why: `openapi.yaml is not on the test classpath`.

[#step-12]
=== Step 12: Subscribe

Add the plugin, the repository and the subscription to `build.gradle`:

.build.gradle (additions)
[source,groovy,subs="attributes+"]
----
plugins {
    id 'java'
    id 'com.arc-e-tect.api-only-subscriber' version '{api-only-subscriber-version}'
}

repositories {
    mavenCentral()
    maven {
        name = 'apiContracts'
        url = uri('https://maven.example.com/repository/contracts')
        // The user name and password come from the Gradle properties
        // apiContractsUsername and apiContractsPassword: see below.
        credentials(PasswordCredentials)
    }
}

apiOnlySubscriber {
    channel {
        type = 'maven'
        groupId = 'com.example.contracts'
    }
    // At the version apiContractVersion in gradle.properties declares.
    subscribe('orders')
}
----

`credentials(PasswordCredentials)` without a block tells Gradle to take the user name and password from two Gradle properties.
It names them after the repository: `<name>Username` and `<name>Password`.
With `name = 'apiContracts'`, those are `apiContractsUsername` and `apiContractsPassword`.
The build file names only the repository, so the credential never ends up in a commit.

Put the two properties in the `gradle.properties` in your Gradle user home, `~/.gradle/gradle.properties` (`%USERPROFILE%\.gradle\gradle.properties` on Windows, or wherever `GRADLE_USER_HOME` points).
Never put them in the project's own `gradle.properties`, beside `apiContractVersion`: that one is committed.

.~/.gradle/gradle.properties
[source,properties]
----
# Read access to the contracts' Maven repository. Personal: never commit this file.
apiContractsUsername=<your user name in the Maven repository>
apiContractsPassword=<a token with read access to it>
----

The values are whatever your Maven repository accepts for reading: usually your user name and an access token, never your login password.
<<gitlab-consumer,On GitLab §>> says what they are for GitLab.
When either property is missing, Gradle stops before the build runs, naming the properties it could not find.

Then run `./gradlew check`:

[source]
----
> Task :fetchApiSpecOrders
Subscribed to orders 1.1.0
> Task :test
> Task :verifyApiSpecOrders

BUILD SUCCESSFUL
----

`ApiContractTest` passes.
Commit `apionly.lock`:

.apionly.lock
[source]
----
# apionly.lock -- the published contracts this project builds against.
# Generated by the Arc-E-Tect API-Only Subscriber. Commit it; do not edit it.
# Run `verifyApiSpec` to check that what is on disk still matches.
format 1

target orders
version 1.1.0
channel maven
sha256 ab7b2899eed2ec77158f50da8775f0264f8048c03e014cffe1bd1c9a292eeb01 openapi.yaml
----

In CI there is no `~/.gradle/gradle.properties`, so set the same two properties as environment variables, with the prefix `ORG_GRADLE_PROJECT_`: `ORG_GRADLE_PROJECT_apiContractsUsername` and `ORG_GRADLE_PROJECT_apiContractsPassword`.
Gradle reads an environment variable with that prefix as the property after it, so `build.gradle` stays the same everywhere.
Store both as secret, masked variables of the CI system.
link:../4-implementing-a-published-contract/tutorial.adoc[Provider use case 4's tutorial →] covers the implementing side in full, and link:../../client/3-specification-library-in-another-repository/tutorial.adoc[client use case 3's tutorial →] the calling side: CI, pre-releases, taking a new version, and each guard.

[#step-13]
=== Step 13: Before the first release

An implementing project can start before anything is released, from a local checkout of the contracts repository, through the `file` channel.

In the contracts repository, add a `file` channel beside `maven`, and publish a pre-release to it:

.apionly.yaml (channels)
[source,yaml]
----
channels:
  maven:
    groupId: com.example.contracts
    repository: https://maven.example.com/repository/contracts
    tokenEnv: MAVEN_TOKEN
  file:
    directory: build/publish
----

[source,console]
----
npm run apionly -- build --target orders --pre-release rc.1
npm run apionly -- publish --target orders --pre-release rc.1 --channel file
----

In the implementing project, read that directory instead of the Maven repository, and allow the pre-release:

.build.gradle (temporary)
[source,groovy]
----
apiOnlySubscriber {
    channel {
        type = 'file'
        directory = '../contracts/build/publish'
    }
    subscribe('orders') {
        // Deliberate and temporary: remove at the first release.
        allowPrerelease = true
    }
}
----

with `apiContractVersion=1.1.0-rc.1`.
`./gradlew check` now takes the pre-release from the directory:

[source]
----
> Task :fetchApiSpecOrders
Updated orders from 1.1.0 to 1.1.0-rc.1
----

At the first release, the channel block goes back to `maven`, `allowPrerelease` goes, and the version becomes the released one.
In the contracts repository, remove the `file` channel again, or the release job publishes to it as well.

.Considerations
* **This works only while both repositories are checked out side by side.**
CI has neither your checkout nor your pre-releases, so release early and switch.

== On GitLab: publishing to the project's package registry

Everything above works with any Maven repository.
When the contracts repository is a GitLab project, its own package registry can be that repository, and GitLab CI can run the release.
This section changes steps 8, 9 and 12 for that.

[NOTE]
.What was checked
====
This section was not run as part of this tutorial.
The channel settings, tokens and headers are the ones link:../../../guides/publishing-to-gitlab/overview.adoc[the guide to publishing to GitLab →] describes, and the guide's reference pipeline ran on gitlab.com with them.
The Gradle side follows https://docs.gitlab.com/user/packages/maven_repository/[GitLab's Maven repository documentation ↗].
====

The values used below:

[cols="1,2", options="header"]
|===
|What |Example

|GitLab
|`https://gitlab.example.com`

|The contracts project, and its numeric ID
|`example/contracts`, `1234`, as the project's overview page shows

|Maven repository URL
|`https://gitlab.example.com/api/v4/projects/1234/packages/maven`
|===

[#gitlab-channel]
=== Which channel: `maven`

GitLab has several package registries, and the Publisher can publish to more than one, but only one of them is something the Subscriber can read:

[cols="1,2,1,3", options="header"]
|===
|Publisher channel |GitLab registry |The Subscriber reads it |Use it for

|`maven`
|Maven registry
|Yes
|Every Gradle or Maven build that implements or calls the contract.
*This is the one to use with the Subscriber.*

|`gitlab-package`
|Generic Package Registry
|No
|Builds that are not Gradle, which download the archive with `curl` and check it against its `manifest.json`.
Also what creates the GitLab release, and with it the release tag (<<gitlab-ci,Step 9 on GitLab §>>).

|`npm`
|npm registry
|No
|JavaScript consumers only.
The Subscriber reads only its `maven` and `file` channels.
|===

So publish with the `maven` channel, aimed at the project's Maven registry, and add `gitlab-package` beside it for the release tags.

[#gitlab-step-8]
=== Step 8 on GitLab: point the channels at the project

The channels below need the Publisher at 0.15.0 or later.
Pin a current release, as step 1 does:

[source,console]
----
npm install --save-dev --save-exact @arc-e-tect/api-only-publisher@<version>
----

.apionly.yaml (channels)
[source,yaml]
----
channels:
  maven:
    groupId: com.example.contracts
    repository: https://gitlab.example.com/api/v4/projects/1234/packages/maven
    tokenEnv: CI_JOB_TOKEN
    tokenHeader: Job-Token
  gitlab-package:
    tokenEnv: CI_JOB_TOKEN
    tokenType: job
    release: true
----

.Considerations
* **The URL needs the project's numeric ID**, not its path: Gradle reads `%2F` in a URL path as `/`, so `example%2Fcontracts` would not resolve.
* **The job token, `CI_JOB_TOKEN`**, exists in every GitLab CI job, only while the job runs, and reaches the pipeline's own project.
There is nothing to store or rotate.
GitLab's Maven registry takes it in the `Job-Token` header, which `tokenHeader` names; without `tokenHeader`, the Publisher sends any token as a bearer token.
* **`tokenEnv` and `tokenType` on `gitlab-package`** make it use the job token even when the job inherits a `GITLAB_TOKEN` variable from the group or the instance, which it would otherwise prefer (link:../../../guides/publishing-to-gitlab/overview.adoc#token-shadowed[When the job fails with 401 or 403 →]).
* **`release: true`** creates a GitLab release per published contract version, tagged `<target>-v<version>`: the same tags step 7 creates with `git tag`.
* **Turn off _Allow duplicates_** for Maven and Generic packages, in the group's *Settings › Packages and registries*.
GitLab otherwise accepts a different file under a released version.
The Publisher never replaces one, but other clients might (link:../../../guides/publishing-to-gitlab/overview.adoc#duplicates[Turn off "Allow duplicates" →]).

[#gitlab-ci]
=== Step 9 on GitLab: run it in GitLab CI

The two scripts from step 7 work in GitLab CI too, except for one step: a job token cannot `git push` the release tags by default.
The Publisher has both checks built in, so on GitLab it does without the scripts:

* `check` fails on a changed contract whose version was not raised, as `check-versions.sh` does, against the release tags.
* `publish` checks the same before it sends anything, publishes each contract version that is not published yet, and leaves the ones that are alone, as `release.sh` does.
`gitlab-package` then creates the release tag through GitLab's API, with the job token.

link:../../../../api-only-publisher/README.adoc#version-guard[A changed target needs a new version →] describes both.

..gitlab-ci.yml
[source,yaml]
----
default:
  image: node:24
  before_script:
    - npm ci
    # The release tags and the default branch, which check and publish compare with.
    - git fetch --quiet --tags origin "+refs/heads/$CI_DEFAULT_BRANCH:refs/remotes/origin/$CI_DEFAULT_BRANCH"

variables:
  # The full history: the version check reads it.
  GIT_DEPTH: "0"

check:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - npm run apionly -- build
    - npm run apionly -- lint
    - npm run apionly -- check
  artifacts:
    when: always
    paths:
      - build/reports/lint/

release:
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  script:
    - npm run apionly -- build
    - npm run apionly -- lint
    - |
      status=0
      npm run apionly -- publish > publish.log 2>&1 || status=$?
      cat publish.log
      # publish exits 0 when a registry did not take a version; fail the job on that too.
      if [ "$status" -ne 0 ] || grep -q 'Channel problems:' publish.log; then
        echo "Not every contract version was published; run the pipeline again." >&2
        exit 1
      fi
----

.Considerations
* **The merge request is where a missing version bump is caught.**
`check` runs there; `publish` on the default branch refuses it again, before anything is sent.
* **A failed release run is completed by the next one.**
`publish` reads back what each registry has, and uploads only what is missing, so run the pipeline again.
* **The default branch is `main` here.**
When it is not, set `versioning` in `apionly.yaml` to name it, as link:../../../../api-only-publisher/README.adoc#version-guard[the Publisher's README →] describes.

[#gitlab-consumer]
=== Step 12 on GitLab: subscribe from the project's Maven registry

The Subscriber needs nothing specific to GitLab: `type = 'maven'` and the `groupId` stay exactly as in step 12.
What changes is Gradle's `repositories` entry: the URL, and that Gradle sends the credentials with its first request:

.build.gradle (repositories)
[source,groovy]
----
repositories {
    mavenCentral()
    maven {
        name = 'apiContracts'
        url = uri('https://gitlab.example.com/api/v4/projects/1234/packages/maven')
        credentials(PasswordCredentials)       // apiContractsUsername, apiContractsPassword
        authentication {
            basic(BasicAuthentication)         // send them up front, as GitLab's documentation does
        }
    }
}
----

Without `authentication`, Gradle sends credentials only after the server asks for them with a `401`.
A private GitLab project may answer an anonymous request with `404` instead, and then Gradle never sends them.

`apiContractsUsername` and `apiContractsPassword` are set as step 12 describes; for GitLab they hold:

[cols="2,2,2,3", options="header"]
|===
|Where the build runs |`apiContractsUsername` |`apiContractsPassword` |Notes

|A workstation, in `~/.gradle/gradle.properties`
|The deploy token's user name, such as `gitlab+deploy-token-42`
|The deploy token
|A deploy token of the contracts project, with the `read_package_registry` scope only, created in its *Settings › Repository › Deploy tokens*.
A personal access token works too, with your GitLab user name; https://docs.gitlab.com/user/packages/maven_repository/[GitLab's Maven documentation ↗] says which scope it needs.

|A GitLab CI job of the implementing project
|`gitlab-ci-token`
|`$CI_JOB_TOKEN`
|The contracts project must admit the implementing project, in its *Settings › CI/CD › Job token permissions*.

|Any other CI
|The deploy token's user name
|The deploy token
|As masked secrets, in `ORG_GRADLE_PROJECT_apiContractsUsername` and `ORG_GRADLE_PROJECT_apiContractsPassword`.
|===

Give each consuming team a deploy token of its own, so one can be revoked without the others.

In the implementing project's own GitLab CI, the job token needs no secret at all:

..gitlab-ci.yml of the implementing project
[source,yaml]
----
check:
  image: eclipse-temurin:21
  variables:
    ORG_GRADLE_PROJECT_apiContractsUsername: gitlab-ci-token
    ORG_GRADLE_PROJECT_apiContractsPassword: $CI_JOB_TOKEN
  script:
    - ./gradlew check
    # The build must not have changed what the project is locked to.
    - git diff --exit-code apionly.lock
----

[#what-you-have]
== What you have now

* A contracts repository that releases each contract on its own, exactly when its version is new.
* Pull requests that fail on a changed contract under a released version, and on a fragment no contract references.
* A tag per released contract version.
* Implementing projects that build against the version they declare, verified against their own lockfiles.

[#watch-for]
== What to watch for

* **Publishing is passive.**
Nothing tells a consumer that a new version exists.
Tell your consumers, or have them configure an update bot that reads `apiContractVersion`.
* **The fragments are unreachable for consumers**, which is the point.
Make the documents readable somewhere, such as a documentation site built from `build/dist/`, so nobody asks for read access to the fragments instead.
* **Deleting a released version** breaks every consumer that locked it.
Leave released versions in the repository.
