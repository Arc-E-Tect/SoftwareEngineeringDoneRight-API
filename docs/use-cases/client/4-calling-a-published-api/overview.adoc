[#in-short]
== In short

Your project calls one or more APIs whose contracts other teams or companies publish.
You cannot change those contracts and you have no access to where they are written; they reach you as artifacts in a Maven repository.

The API-Only Subscriber fetches each contract at the version your project calls, checks every document against the archive's own manifest, records the versions and the hashes in a committed lockfile, and puts each contract on the classpath under `contracts/<target>/`.
Every `./gradlew check` verifies that what your build calls is still what you locked.

Nothing in this use case runs the API-Only Publisher: the other side runs it.

[#fits]
== When this fits

* Your project calls APIs; it does not implement them.
* Their contracts are published as archives built by the API-Only Publisher, to a Maven repository your build can read.
* You have no access to the repositories the contracts come from, or no need for it.
* You want your build to state exactly which version of each API it calls, and to fail rather than drift when one changes.

[#does-not-fit]
== When it does not

* **Your project implements the API.**
That is link:../../provider/4-implementing-a-published-contract/overview.adoc[provider use case 4 →].
* **You can check out the repository the contracts come from**, and want to build against a change before it is released.
That is link:../3-specification-library-in-another-repository/overview.adoc[client use case 3 →].
* **The contract lives in your own repository.**
That is link:../1-contract-in-the-calling-project/overview.adoc[client use case 1 →] or link:../2-specification-library-in-the-same-repository/overview.adoc[client use case 2 →].
* **Your project also implements a contract.**
See link:../../both/implementing-and-calling/overview.adoc[implementing one contract and calling others →].

link:../../../README.adoc[The documentation's entry point →] compares every use case.

[#what-you-get]
== What you get

* A build that cannot silently start calling a different version of an API.
* A committed `apionly.lock` that answers "which version of their API do we call?" for every API, by reading your own repository.
* A test that proves each contract reaches your code, for example the client generator that reads it.
* A build failure, not a production surprise, when a fetched document is edited or a released version is republished with different bytes.

[#what-you-do-not-need]
== What you do not need

Node.js, the Publisher, or access to the fragments the contracts are built from.

[#adoption]
== Adoption in broad strokes

. **Get the coordinates from each provider**: the Maven repository's URL, the group id, the target name of each API, and the versions available.
. **Declare the version of each API the project calls** in `gradle.properties`, as `<target>ApiVersion`.
. **Write the contract test first**: a test that fails until each contract, at its version, is on the classpath under `/contracts/<target>/`.
. **Apply the Subscriber**: the Maven repository with its credentials read from outside the build file, the `maven` channel, and a `subscribeAsClient` per API, each with its own `apiContractVersion`.
. **Run `./gradlew check`**, and commit `apionly.lock`.
. **Run the same `./gradlew check` in CI**, with the repository credentials in the environment, and fail the build when the lockfile changed.

[#day-to-day]
== Day to day

* **Taking a new version of an API**: change its `<target>ApiVersion`, run `./gradlew check`, and commit the updated `apionly.lock` with the change; the other APIs stay where they are.
* **Working against an unfinished version**: subscribe to the provider's pre-release and set `allowPrerelease = true` on that subscription, visibly and temporarily.
* **An API from another provider**: set `groupId` on its subscription, and add that provider's Maven repository to `repositories`.
* **Noticing new releases**: publishing is passive, so watch the providers' releases, or configure an update bot to read the version properties.
