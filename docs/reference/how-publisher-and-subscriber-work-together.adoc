This document explains how the two tools fit together: which of their settings, commands, tasks and files correspond, what each check guarantees, and where in the code each part lives.
It is written to be read front to back by a person, and to be looked up section by section by a person or an AI assistant working on either tool.
Every correspondence between the two tools, every Subscriber task and every check is listed; the tools' READMEs list each tool's remaining options.

It describes the Publisher and the Subscriber as they are on this repository's main branch; the badges at the top of link:../../api-only-publisher/README.adoc[the Publisher's README →] and link:../../api-only-subscriber/README.adoc[the Subscriber's README →] show each one's latest release.

[#at-a-glance]
== At a glance

The Publisher turns a library of API description fragments into one bundled document per contract, stamps the contract's version into it, and ships it as an archive with a manifest of hashes.
The Subscriber, in a consuming Gradle build, fetches that archive at the version the build declares, checks it against the manifest, records what it fetched in a lockfile, and verifies the documents against that lockfile afterwards.

The two tools share exactly one thing: the archive and its manifest.
Neither reads the other's configuration, and either can be replaced by anything that produces or reads the same archive.

[source]
----
 Publisher (Node.js)                                    Subscriber (Gradle)
 ──────────────────                                     ───────────────────
 fragments + apionly.yaml + version file
        │ build: stage, substitute, bundle, stamp, lint
        ▼
 bundled document(s)
        │ publish: pack with manifest.json, ship to a channel
        ▼
 <target>-<version>.tgz  ─────── channel ───────▶  fetchApiSpec<Target>: resolve, check manifest, unpack, lock
                          (a directory, or a                    │
                           Maven repository)                    ▼
                                                  build/api-spec/<target>/ + apionly.lock
                                                                │ verifyApiSpec<Target>
                                                                ▼
                                                  documents still match the lock
----

[#vocabulary]
== Vocabulary

[cols="1,3,2", options="header"]
|===
|Term |Meaning |Where it appears

|Fragment
|A YAML file holding part of an API description: a path, a schema, a response.
|Under `sources.root`

|Bundle root
|The fragment that is a contract's table of contents, `$ref`ing the rest.
|`targets.<name>.openapi.bundle`, `targets.<name>.asyncapi.bundle`

|Target
|A contract: whatever gets its own bundled document and its own version.

|`targets:` keys; `subscribe('<target>')`; archive and task names

|Closure
|Every file a target's bundle root reaches through `$ref`, transitively.
|`closure`, `changed`, `lint`; `closureSha256` in the manifest

|Version file
|The file holding a target's release version.
|`<target>.bundle.properties`, or `targets.<name>.versionFile`

|Archive
|`<target>-<version>.tgz`: the bundled documents plus `manifest.json`.
|Written by `publish`, read by the fetch

|Manifest
|`manifest.json`: which target and version the archive holds, where it came from, and a SHA-256 per document.
|Inside the archive, and beside it in a channel

|Channel
|Where archives are shipped to and fetched from.
|`channels:` in `apionly.yaml`; `channel { }` in the Subscriber

|Subscription
|A consuming build's declaration that it builds against a target at a version: the one contract it implements, or an API it calls.
|`apiOnlySubscriber { subscribe(...) }`, `subscribeAsClient(...)`

|Lockfile
|`apionly.lock`: per subscription, the version, the channel and a SHA-256 per document, as fetched.
|Beside the consuming build file, committed

[#lifecycle]
== The lifecycle of a contract version

[cols="1,1,2,2,2", options="header"]
|===
|Stage |Tool |What happens |Reads |Writes

|1. Author
|--
|Someone edits fragments and raises the target's version.
|--
|Fragments, version file

|2. Build
|Publisher `build`
|Copies the source root to a staging directory, substitutes `{{token}}` placeholders, bundles each target with Redocly CLI or AsyncAPI CLI, stamps the version into `info.version`, and lints the result.
|`apionly.yaml`, fragments, version files, `toolchain`
|`<build.staging>/`, `<build.dist>/<target>/`

|3. Lint
|Publisher `lint`
|Lints every built document again, writes a report per document, and fails on fragments no target reaches.
|`<build.dist>/`, `<sources.root>/`
|`<reports.lint>/<target>/<kind>.txt`, `<reports.lint>/unreferenced.txt`

|4. Pack
|Publisher `pack`, or `publish`
|Checks that each document's `info.version` is the version being packed, writes `manifest.json`, and archives the documents with it.
|`<build.dist>/<target>/`
|`<target>-<version>.tgz`, in `build/packages/`

|5. Publish
|Publisher `publish`
|Ships the same archive to every configured channel, or to `--channel`.
|The archive
|The channel's layout

|6. Fetch
|Subscriber `fetchApiSpec<Target>`
|Resolves the archive at the subscription's version, checks the pre-release rule, unpacks it, checks every document against the manifest, refuses a locked version whose bytes changed, and records the result.
|The channel, `apionly.lock`
|`build/api-spec/<target>/`, `apionly.lock`

|7. Verify
|Subscriber `verifyApiSpec<Target>`
|Hashes the documents on disk and compares them with `apionly.lock`.
|`build/api-spec/<target>/`, `apionly.lock`
|--
|===

[#the-archive]
== The archive and its manifest

[source]
----
orders-1.1.0.tgz
├── openapi.yaml          the bundled OpenAPI document, if the target has one
├── asyncapi.yaml         the bundled AsyncAPI document, if the target has one
└── manifest.json
----

.manifest.json
[source,json]
----
{
  "schemaVersion": 1,
  "target": "orders",
  "version": "1.1.0",
  "producedAt": "2026-09-13T12:00:00Z",
  "closureSha256": "…",
  "source": {
    "repository": "git@example.com:example/contracts.git",
    "commit": "…"
  },
  "files": [
    { "path": "openapi.yaml", "sha256": "…" }
  ]
}
----

[cols="1,3,2", options="header"]
|===
|Field |Meaning |Used by

|`schemaVersion`
|The manifest format, `1`.
A reader that does not understand a version must refuse the archive.
|Subscriber

|`target`, `version`
|What the archive holds.
|Subscriber: a `version` different from the resolved one is refused

|`producedAt`
|When the archive was packed, in UTC.
|People

|`closureSha256`
|A hash over the target's closure after placeholder substitution.
|People and release tooling comparing what was published

|`source.repository`, `source.commit`
|The git remote and commit the archive was built from; `null` outside a git checkout.
|People

|`files[].path`, `files[].sha256`
|Every document in the archive, and its SHA-256.
|Subscriber: every listed file must exist and match
|===

The manifest is the entire coupling between the two tools.
Changing its shape means changing the Publisher's `src/pack.js` and the Subscriber's `Manifest.java` together, and raising `schemaVersion` whenever an older reader could misread the new shape.

[#version-resolution]
== Where a version comes from

On the Publisher side, the version of a target is read, by `build`, `pack` and `publish`, from one place:

. `targets.<name>.versionFile`, relative to `apionly.yaml`, when it is set;
. otherwise `<target>.bundle.properties`, in the directory of the target's first bundle root, OpenAPI before AsyncAPI.

The file uses Java properties syntax, and its `version` must be a semantic release version.
`--pre-release <ids>` appends `-<ids>` to it.
Every version a command needs is resolved before the command builds or ships anything.
A `publish: false` target needs no version file.

On the Subscriber side, `apiContractVersion` is the version of the contract a project implements, and the first of these that is set is resolved:

. `-PapiContractVersion=...` on the command line, which overrides every other;
. the subscription's own `apiContractVersion`;
. `apiOnlySubscriber.apiContractVersion`;
. the `apiContractVersion` property of the project the plugin is applied to: from that project's own `gradle.properties`, from the build script's `ext`, or from `ORG_GRADLE_PROJECT_apiContractVersion`.

A subscription for an API the project calls, declared with `subscribeAsClient`, takes only its own `apiContractVersion`, and the command line does not change it: the others are the version of the contract the project implements.
link:../../api-only-subscriber/README.adoc#version-precedence[Where a subscription's version comes from →] has the details.

[#gradle-wiring]
== How a build wires the two together

A project implements at most one contract, and may call any number of APIs.
The Subscriber registers, for every subscription:

* `fetchApiSpec<Target>`, whose inputs are the resolved archive, the target, the version and the channel, and whose output is the unpacked directory; it is up to date only while `apionly.lock` records its target at that version and channel, because the lockfile is shared by every subscription and so is no single fetch's output, which is also why the task is not cacheable; a project's fetches and verifications take turns through the `LockfileAccess` build service, so none reads the lockfile while another writes it;
* `verifyApiSpec<Target>`, ordered after the fetch but deliberately not depending on it, so that it can report a hand edit instead of repairing it;
* the aggregates `fetchApiSpec` and `verifyApiSpec`, with `check` depending on `verifyApiSpec`;
* with the `java` plugin, `processResources` depending on the fetch, and the documents on the classpath: for the implemented contract, the unpacked directory as a resources directory, so its documents sit at the root; for an API the project calls, a copy under `contracts/<target>/`.

A `file` channel's archive path is resolved while the build is planned, and only checked for when the fetch runs.
That is what lets a build publish its own contract and fetch it in one invocation: a task that runs the Publisher's `publish` writes the archive, and the fetch task depends on it.
The use-case tutorials wire it with Gradle `Exec` tasks:

[source]
----
installApiOnlyPublisher  (npm ci)
        │
buildApiContract         (npm run apionly -- build --target <t>)
        │
publishApiContract       (npm run apionly -- publish --target <t> --channel file)
        │
fetchApiSpec<Target>     ── processResources ── test
        │
verifyApiSpec<Target>    ── check ── lintApiContract (npm run apionly -- lint)
----

Because `verifyApiSpec` runs after the fetch in such a build, a hand-edited fetched document is restored by the fetch before it is verified; `verifyApiSpec` on its own reports it.
Every Publisher run rebuilds its staging directory, so builds that run the Publisher for several targets serialise those runs with a shared Gradle build service.

[#invariants]
== Invariants

These hold across both tools, and a change that breaks one is a change to the design, not a detail.

. **One archive holds one target at one version**, and its manifest says which.
. **One project implements at most one contract.** It may call any number of APIs, each with every check the implemented contract gets; the Subscriber refuses a second implemented contract.
. **The manifest is the only thing the tools share.**
. **A version is never taken from the command line.** It comes from the library, and a pre-release only appends to it.
. **A version names one set of documents.** The Subscriber never silently re-locks a locked version whose documents changed.
. **`verifyApiSpec` never fetches.**
. **Nothing either tool generates is written under `src/`.**
. **Credentials are read from the environment**, never from a committed file.
. **Every channel ships the same packed bytes.** Nothing is rebuilt per channel.
