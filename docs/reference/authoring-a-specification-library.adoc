This document collects the rules that make a specification library work well with the API-Only Publisher and the API-Only TranscriberJ, and says plainly what the two will not do.
Both tools already report most problems while they build; this is where each report comes from, so a team can follow the rule before a warning tells them they did not.

Every rule has a heading, its reason, and -- where a tool checks it -- the message that tool prints, quoted exactly as the code emits it, with the variable parts in angle brackets.
Search this page for the text in your build log.

It describes the tools as they are on this repository's main branch.
Option lists are not repeated here: link:../../api-only-publisher/README.adoc[the Publisher's README →] and link:../../api-only-transcriberj/README.adoc[the TranscriberJ's README →] are the reference for every setting.

[#versions]
== Versioning

[#version-in-the-filename]
=== Put a schema's version in its fragment's filename

`UserV1.yaml`, not `v1/User.yaml`.

Versions belong to components, not to the library::
`UsernameV1` and `UserV2` exist side by side, each evolving at its own pace.
A version directory would force the two apart, or force every schema in it to a new version together.

The version travels into the code::
A generated class is named after its fragment's file, so `UserV1.yaml` is `UserV1` and `UserV2.yaml` is `UserV2`: two classes in one package, and a test says which one it means.

A schema that gains a version does not move::
Every component carries `x-fragment-path`, the path of the fragment it came from, and the TranscriberJ carries it into `FRAGMENT_PATH` and into the hash `FRAGMENT_SHA256`.
A version directory changes that path whenever the version changes, so the provenance of a schema changes for no reason but its version.

A version directory renames classes that did not change::
With only `v1/User.yaml`, the class is `User`.
Add `v2/User.yaml`, and the two collide; the TranscriberJ tells colliding fragments apart by the nearest directory in which their paths differ, so the existing class becomes `V1User` and the new one `V2User`.
Every test that named `User` stops compiling, although that schema did not change.
Only colliding classes are renamed, so a version in the filename never causes this.

What is not versioned this way::
A bundle root is the document itself, versioned by its target's version file (link:../../api-only-publisher/README.adoc#versions[Versions →]).
Fragments that are not components -- the reference library's `openapi/shared/info.yaml` and `servers.yaml` -- never become classes, and need no version in their name.

[#new-version-for-breaking-changes]
=== Give a schema a new version only for a breaking change

A new version -- `UserV2` beside `UserV1` -- is for a change a consumer cannot absorb: a member removed or renamed, a type changed, a constraint tightened, a member made required.

Adding an optional member does not earn one.
A consumer that does not expect the member ignores it, so the schema's promise to existing consumers still holds.
It still changes the contract, so document it, raise the contract's minor version in its version file, and tell the teams that consume it.

Neither tool polices breaking changes: see <<breaking-changes,Breaking changes are not detected §>>.

[#generation]
== Keeping generation clean

The TranscriberJ reports what it could not generate cleanly in its report, `build/reports/transcriberj/<contract>.txt`; <<reading-the-reports,Reading the reports §>> explains every section.

[#name-your-schemas]
=== Name your schemas

Write a request or response schema as a component in a fragment of its own, and `$ref` it from the operation.

Named fragments are reusable, reviewable on their own, and can be referred to from anywhere in the library.
A schema written inline in an operation is still generated, but its class is named after the operation and its status -- `GetRootResponse200` -- rather than after anything the schema means, and it changes name when the operation does.

The TranscriberJ recommends it, under *Recommendations*:

[source,text]
----
<location>: an inline schema; define it as a schema component and $ref it, so that its class is named after its fragment rather than after the operation
----

[#give-operations-an-operation-id]
=== Give every operation an `operationId`

An operation's class is named after its `operationId`, followed by `Operation`: `getUser` is `GetUserOperation`.
Without one, the operation's classes are named after its method and path, which change when the path does.

Recommended under *Recommendations*, when the operation has inline schemas:

[source,text]
----
<location>: an operation without an operationId; give it one, since its classes are named after its method and path until it has one
----

[#name-the-branches]
=== Name the branches of a `oneOf` or `anyOf`

Write each branch as a component, and refer to it: `oneOf: [{$ref: CardRefundV1.yaml}, {$ref: BankAccountRefundV1.yaml}]`.

A body with several possible shapes cannot be one flat list of fields.
When every branch is a reference, each branch has its own class, with its own `body(...)` and `fields(...)`, and the schema that is nothing but the choice has neither.
When a branch is written inline, the `body(...)` and `fields(...)` of the schema that holds it cannot be generated, and are generated to throw.

The report lists them under *Degraded methods*:

[source,text]
----
<Class>.body(...) [core]: ONE_OF_INLINE_BRANCHES at <location> (oneOf: <inline #1>, <inline #2>); remedy: name the branches in the specification so that each becomes a component
----

The same for `ANY_OF_INLINE_BRANCHES`.
A choice between values rather than objects -- `oneOf: [{type: string}, {type: integer}]` -- is written as a value, and degrades nothing.
link:../guides/hand-written-contract-tests/overview.adoc[The guide to hand-written contract tests →] says what to do when the contract cannot change.

[#keep-bodies-shallow]
=== Keep bodies shallow

A request or response body that nests objects three levels deep -- `order.customer.address` -- is warned about, following references and list items:

[source,text]
----
<Class>: its body nests objects <n> levels deep, at <path>; a body this deep is hard to test and easily designed by accident
----

The warning is about design as much as generation.
A body that deep is usually an accident: a structure that grew one member at a time, and that no consumer needs whole.
Two levels -- `customer.address` -- are not warned about.
Only bodies code outside the generated package can use are checked.

[#keep-cycles-short]
=== Keep reference cycles short

A schema may refer to itself, directly or through others: a tree node's `children`, say.
In field descriptions the TranscriberJ follows a recursive reference `recursionDepth` times, 3 by default, and then describes the rest as a subsection.

A cycle through three or more components is warned about:

[source,text]
----
<location>: a recursive reference through <n> components (<A> -> <B> -> <C> -> <A>); a cycle this long is easily not noticed
----

A cycle through one or two components is not warned about; one through three or more is usually an accident nobody noticed.

Following a recursion more than three times is warned about too, whatever the contract:

[source,text]
----
recursionDepth is <n>; following a recursion more than 3 times suggests the contract nests deeper than a test should need to
----

None of these warnings fails the build.

[#reference-shared-definitions]
=== Reference shared definitions rather than repeating them

A definition used in more than one place -- by two schemas, or by an HTTP response and an event -- belongs in one fragment, referenced from each.

One fragment referenced twice is one thing.
Two definitions that look alike are two things that happen to agree today, and nothing keeps them agreeing.
The Publisher stamps what it builds from a fragment with that fragment's path, in the OpenAPI and the AsyncAPI document alike, and the TranscriberJ generates one class per schema fragment, so a `username` in an event and a `username` in a response are the same class -- when they are the same fragment.

When one fragment is bundled as different bytes in two places -- in the contract's two documents, say -- the TranscriberJ generates its class from the copy it read first, the OpenAPI document's when the fragment is in both, and lists it under *Undecided constructs*:

[source,text]
----
<location>: FRAGMENT_BUNDLED_DIFFERENTLY (<fragment path>)
----

Neither tool detects a definition *repeated* in several places, since each copy is a legitimate schema of its own; see <<repeated-definitions,Repeated definitions are not detected §>>.

[#describe-everything]
=== Describe every schema and field that documentation will show

With `generateDocs = true`, a class or field is described with the contract's text.
One the contract does not describe is documented with the placeholder, and recommended under *Recommendations*:

[source,text]
----
<location>: no description; give it one, since generateDocs is on and it is documented with the placeholder until then
----

Without `generateDocs`, descriptions are not read, and nothing is recommended.

[#use-typed-keywords]
=== Prefer keywords the generator types

The TranscriberJ's model types the keywords generation needs, keeps the annotations, and lists every other keyword under *Undecided constructs*, as does a type naming several types and a schema written as `true` or `false`:

[source,text]
----
<location>: MULTIPLE_TYPES (type: string, null)
<location>: BOOLEAN_SCHEMA (<true or false>)
<location>: UNMODELLED_KEYWORD (<keyword>)
<location>: UNMODELLED_COMPONENT_TYPE (<component type>)
----

An undecided construct is kept, and does not fail the build.
Several types, or a literal schema, also degrades any `body(...)` or `fields(...)` that reaches it; one nothing reaches -- inside a map's values, say -- degrades nothing.
link:../../api-only-transcriberj/README.adoc#unrepresentable[Constructs no rule represents yet →] lists which keywords are typed.

`type: [string, 'null']` is the one most libraries meet.
Where a member that has no value can simply be left out, leave it out of `required` instead of allowing `null`: the model types that.

[#leave-no-fragment-unreferenced]
=== Leave no fragment unreferenced

Every YAML file under the source root is either reached by a target's bundle, or configuration.

A linter checks documents, and a fragment reaches a document only through a `$ref`.
A fragment nothing references is never linted, so it can be wrong for months and nobody finds out, until the day a target starts to use it.
And a definition left behind by a change that stopped using it is dead weight that looks alive.

`lint`, run without `--target`, lists every such file in `<reports.lint>/unreferenced.txt`, and fails:

[source,text]
----
Error: <n> fragment(s) not reachable from any target, so nothing lints them:
  <file>
Reference each one from a target's bundle, or delete it.
----

`lint.unreferenced: warn` prints the same without failing; `off` does not look.
The configuration files of lint tools, and the lint configuration `apionly.yaml` names, are skipped wherever they are (link:../../api-only-publisher/README.adoc#unreferenced[A fragment no target reaches fails the lint →]).

[#give-every-operation-an-example]
=== Give every operation an example

An operation with no example is an operation nobody has worked through concretely.
Writing one forces a decision about the data -- what a real username looks like, what a real event's payload holds -- during design, which is where that decision is cheapest.
Leaving it for later usually means leaving it for whoever hits the gap downstream.

Microcks is what makes the omission visible, not what makes it a problem: it builds its async mocks and its conformance tests from a message's own `examples`, so a message with none cannot be used for Microcks-based conformance testing at all.
Both specifications make examples optional, and Redocly CLI and AsyncAPI CLI are right to accept their absence -- this is not a specification-validity rule, is never run as a Redocly plugin or a Spectral ruleset, and is reported apart from either linter's own findings.
`build` prints it after lint, once per operation, naming the fragment where provenance makes that possible:

[source,text]
----
AsyncAPI operation '<operationId>': message '<messageKey>' (<fragment, or where in the bundle>) carries no example, so this bundle cannot be used for Microcks-based conformance testing.
OpenAPI operation '<operationId>': request body (<fragment, or where in the bundle>) carries no example, so the TranscriberJ's contract cases send generated values rather than ones the contract chose, and the generated documentation is harder to read.
OpenAPI operation '<operationId>': response <status> (<fragment, or where in the bundle>) carries no example, which makes the generated documentation harder to read.
----

The messages claim different things on purpose.
The TranscriberJ processes an OpenAPI body without an example perfectly well, so no OpenAPI message says the bundle cannot be used.
For a request body it says what an example would change: the contract cases send the example the media type names, or values from the schemas' own examples, instead of values the generator makes up (link:../../api-only-transcriberj/README.adoc#example-data[Example data in the TranscriberJ's README →]).
Nothing reads a response's example, so its message says only that the generated documentation is weaker without one.
Overstating either would be the failure mode: a warning that cries wolf gets suppressed, and the AsyncAPI one gets suppressed alongside it.

Where the contract gives no example for a value, the TranscriberJ generates the smallest value the contract allows: a title `a`, one page.
Such a value proves a contract is kept, and tells a reader nothing.
An example the contract gives is written for a reader, and the TranscriberJ sends it instead, so the contract cases read like the contract's own documentation; for documentation beyond that, write link:../guides/documentation-tests/overview.adoc[documentation tests →].

An AsyncAPI message counts as having an example when its own `examples` array (an array of `{name, summary, payload}`, sibling to `payload`) is not empty -- a payload schema's property-level `examples`, used for documentation, is a different field and does not count.
An OpenAPI request body or response counts as having one when a media type declares `example` or `examples` directly, or when the schema its `schema` resolves to carries its own top-level `examples` -- a property inside that schema does not count.
A body or response with no `content` at all, such as a `204`, has nothing to exemplify and is never reported.

Both default to `warn`: examples are never mandatory, and a library that has not adopted the Microcks path should not fail its publish over an omission the specification permits.
`lint.examples.asyncapi: error` and `lint.examples.openapi: error` make either fail the build instead -- for a library that *has* adopted Microcks, publishing a bundle its own toolchain cannot use is a real defect.
`off` does not look.

[source,yaml]
----
lint:
  examples:
    asyncapi: error   # this library ships Microcks-based conformance tests
    openapi: warn      # the default; omit the key to get it
----

link:../../api-only-publisher/README.adoc#examples-check[An operation with no example is reported apart from lint →].

[#testable]
== Writing a contract that can be tested

The API-Only TranscriberJ derives a contract test for every response the contract alone determines, and its WireMock emitter a stub for each.
What it can derive depends on what the contract declares.
The rules below say what to declare, and each quotes what the report prints when a contract does not; <<generation-report,The TranscriberJ's generation report §>> explains where.
None of them stops a build: a contract that breaks one gets fewer tests, and the report says which and why.

The before-and-after examples come from one small contract, generated with API-Only TranscriberJ 0.13.0 before and after each fix.

[#declare-every-response]
=== Declare every response you want tested

A case is derived only for a status the operation declares *exactly*.
A range -- `2XX`, `4XX` -- and `default` are too broad to provoke, so they generate nothing.

Before:

[source,yaml]
----
responses:
  '2XX':
    description: Created.
  default:
    description: Anything else.
----

The report's response coverage:

[source,text]
----
  CreateThingContractCases 2XX: uncovered, range status or default -- 2XX is not one status
  CreateThingContractCases default: uncovered, range status or default -- default is not one status
----

After:

[source,yaml]
----
responses:
  '201':
    description: Created.
  '400':
    description: The request does not match the contract.
----

[source,text]
----
  CreateThingContractCases 201: covered by success-201-required
  CreateThingContractCases 400: covered by body-required, body-name-required, body-type, body-name-type, body-name-null, body-name-maxLength
----

The response coverage lists every declared response, and is the list of what is tested and what is not; a response not declared at all is not in it.

[#declare-invalid-request-response]
=== Declare the invalid-request response on every operation that takes constrained input

A contract that declares a response for an invalid request makes a promise about every constraint on the operation's input, and each constraint then gets a case.
An operation that constrains its input and does not declare that response is a *gap*: it gets no invalid-request case at all.

The status is `400` by default.
A project that answers invalid requests otherwise sets `invalidRequestStatus` on its subscription; the operation must then declare exactly that status.
Whatever the status, the response a case expects -- its content type and its body's fields -- always comes from the contract.

The report lists every gap:

[source,text]
----
Gaps -- these operations constrain their request input but declare no invalid-request status:
  /paths/~1things/post (CreateThingContractCases): declare a 400 response, so that its 6 constraint(s) on request input can be tested with invalid requests
----

and every constraint of such an operation as uncovered:

[source,text]
----
  CreateThingContractCases body application/json /name maxLength (/components/schemas/OpenThingV1/properties/name): uncovered, operation declares no invalid-request status -- declare a 400 response
----

Declaring `400`, as in the rule above, covers them all.

[#contract-versus-domain]
=== Reject what the contract forbids with `400`, and what the domain refuses with `422`

A request the contract forbids -- a member missing, a value too long, a member it does not declare -- is a *contract violation*.
The service can see it without knowing anything but the contract, so its inbound adapter rejects it before the port is called, with the invalid-request status.
The TranscriberJ derives a case for each.

A request the contract allows and the domain still refuses -- a book whose ISBN is taken, a refund larger than what is left -- is a *domain violation*.
Only the domain can see it, and it needs state: the book that already exists.
So it reaches the domain, is rejected there, and answers with a status of its own, such as `409` or `422`.
No case is derived, since the contract does not say what provokes it:

[source,text]
----
  AddContactContractCases 422: uncovered, depends on behaviour or state the contract does not describe -- the contract does not say what provokes 422
----

It is tested by one hand-written contract test, and the rule behind it by behaviour tests: link:../guides/hand-written-contract-tests/overview.adoc#how-many[How many tests, and where →].

Declare the two apart.
A contract that answers contract violations with `422` makes the adapter's job look like the domain's, and a generated test that expects `400` and receives `422` says so: "A contract violation was treated as a domain violation."

[#declare-404-406-415]
=== Declare `404`, `406` and `415` where they apply

Each is generated when the operation declares it and the contract leaves room to provoke it:

[cols="1,3", options="header"]
|===
|Status |What it requires

|`404`
|A path parameter with a second valid value, so that one value names a resource that exists and another one that does not.

|`406`
|Declared response media types that leave room for one that does not match: no `*/*`, no range that covers every candidate.

|`415`
|A request body, and declared request media types that leave room for one that does not match.
|===

Before -- a path parameter with one valid value, and a response of any media type:

[source,yaml]
----
parameters:
  - name: kind
    in: path
    required: true
    schema:
      type: string
      enum: [widget]
responses:
  '200':
    description: The things.
    content:
      '*/*':
        schema:
          $ref: ../components/schemas/OpenThingV1.yaml
  '404':
    description: No such kind.
  '406':
    description: Not acceptable.
----

[source,text]
----
  GetThingsOfKindContractCases 404: uncovered, 404 without a second valid path value -- path parameter kind has no valid value but widget
  GetThingsOfKindContractCases 406: uncovered, 406 or 415 with no media type left to choose -- the responses' media types [*/*] match every candidate [application/vnd.apionly.not-acceptable, text/vnd.apionly.not-acceptable]
----

After -- `enum: [widget, gadget]`, and `application/json` instead of `*/*`:

[source,text]
----
  GetThingsOfKindContractCases 404: covered by not-found
  GetThingsOfKindContractCases 406: covered by not-acceptable
----

A `404` on an operation without a path parameter, and a `415` on one without a request body, are reported too:

[source,text]
----
  AddContactContractCases 404: uncovered, 404 without a path parameter -- /contacts names no resource by a path parameter
  ListContactsContractCases 415: uncovered, 415 without a request body -- the operation declares no request body
----

Such a `404` depends on something other than a path parameter -- a resource named in the body -- and is hand-written, or not declared.

[#close-request-objects]
=== Close your request objects

A request object accepts the members it declares, and no others.

* *Strict by default.* With `strictRequests` on, the default, an object that does not declare `additionalProperties` is taken to forbid the members it does not declare, and gets an unknown-member case.
* *An explicit `additionalProperties: false`* is the contract's own, and always has its case.
* *To open an object*, declare it: `additionalProperties: true`, an `additionalProperties` schema, or `patternProperties`.
No unknown-member case is derived for it.
* *An `allOf` is judged as a whole*: a member one branch declares is known to the object.

The reason is security.
A service that binds unknown members is open to mass assignment -- https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/[OWASP API3:2023 Broken Object Property Level Authorization ↗] -- and one that passes them on, to https://owasp.org/API-Security/editions/2023/en/0xaa-unsafe-consumption-of-apis/[OWASP API10:2023 Unsafe Consumption of APIs ↗].
And a lenient JSON binder ignores unknown members by default, so only a test that sends one finds out.

Before -- an object opened on purpose, `additionalProperties: true` -- its operation's `400` is covered by six cases, and none sends an unknown member.
After -- `additionalProperties: false`, or none at all:

[source,text]
----
  AddContactContractCases body application/json additionalProperties (/components/schemas/ContactV1): covered by body-unknown-member
----

Turning strictness off for a whole subscription, `strictRequests = false`, prints on every generation:

[source,text]
----
API-Only TranscriberJ: rules 1.1.0: warning: WARNING: strictRequests is off for contract 'rules'. No request is tested for unknown members, so the service may accept them unnoticed: mass assignment (OWASP API3:2023 Broken Object Property Level Authorization) and unvalidated input passed on (OWASP API10:2023 Unsafe Consumption of APIs). Turn strictRequests back on; where a contract deliberately allows unknown members, declare additionalProperties: true instead.
----

[#give-formats-a-pattern]
=== Give well-known formats a `pattern`

What a `format` accepts differs between validators: one takes `a@b` as an email, another does not.
A `pattern` says exactly what is valid, so the TranscriberJ generates a value from it, vouches for it, and derives a case that breaks it.
For every well-known format without a pattern, the report says:

[source,text]
----
Format recommendations:
  /components/schemas/ContactV1/properties/email: format email has no pattern; declare one, since what email accepts differs between validators, and a pattern says exactly
----

The TranscriberJ recommends a pattern, and does not give one: which one is right is the contract's decision.
Two that were generated with it:

* A lower-case UUID, from link:../../examples/transcriberj/generated-contract-tests/README.adoc[the generated contract tests example →]:
+
[source,yaml]
----
include::../../examples/transcriberj/generated-contract-tests/src/main/api/openapi/components/schemas/BookIdV1.yaml[]
----
+
Its valid value is `aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa`, and the not-found case's `aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaab`.
It accepts any hexadecimal digits in the version and variant positions, so it is the shape of a UUID, not a check of its version; and it refuses upper case, which RFC 9562 allows on input.
* An email address, in place of `format: email`:
+
[source,yaml]
----
email:
  type: string
  pattern: '^[^@\s]+@[^@\s]+\.[^@\s]+$'
  minLength: 6
  maxLength: 254
----
+
Its valid value is `a@a.aa`; the pattern case sends `%%%%%%`.
It is text around one `@`, with a dot after it: it accepts much that no mail server delivers to, and refuses a local address such as `user@localhost`.

A pattern is the contract's promise, so it must be one the service keeps: a service that checks more strictly than its pattern rejects a value the contract calls valid, and its success test fails.
A `format` beside a `pattern` is ignored, and with `validateFormats` naming it, a warning says so.

[#constraints-break-alone]
=== Write constraints a value can break alone

A case breaks one constraint and nothing else, so that its failure has one cause.
Where every value that breaks a constraint breaks another one too, there is no case, and the report names the other:

[source,text]
----
  InitiateUserRegistrationContractCases body application/json /emailAddress minLength (/components/schemas/UserRegistrationRequestV1/properties/emailAddress): uncovered, not isolatable -- conflicting keyword format: every value found that breaks minLength breaks format too
----

That is the reference library's `emailAddress`: `format: email` with `minLength: 6`.
The shortest address a strict validator accepts, `a@b.co`, is six characters long, so every shorter value is not an email either.

Rewritten with the pattern above, `minLength: 6` can be broken alone -- `a@a.a` is five characters and matches the pattern -- and the constraint has its case:

[source,text]
----
  AddContactContractCases body application/json /email minLength (/components/schemas/ContactV1/properties/email): covered by body-email-minLength
----

Some pairs cannot be separated, and need not be: the `type` of an enum is broken by every value that breaks the enum too, and the enum's own case covers it.

[#conditionals-not-covered]
=== Conditionals are not covered yet

`if`, `then`, `else`, `dependentRequired` and `dependentSchemas` are valid OpenAPI 3.1.
The TranscriberJ's model does not type them yet, so it never guesses what they allow.
A schema whose validity depends on one has no valid value -- a valid value could be wrong -- and so gives no case, of any kind, to the operations that send it.
Nothing is dropped silently; each is reported:

[source,text]
----
Undecided constructs -- no generation rule exists for these yet:
  /components/schemas/ContactV1: UNMODELLED_KEYWORD (dependentRequired)
  /components/schemas/ContactV1: UNMODELLED_KEYWORD (if)
  /components/schemas/ContactV1: UNMODELLED_KEYWORD (then)
----

[source,text]
----
  AddContactContractCases body application/json dependentRequired (/components/schemas/ContactV1): uncovered, keyword not modelled -- dependentRequired is not typed by the model
  AddContactContractCases 201: uncovered, no valid value -- validity depends on dependentRequired, which the model does not type, so no value is generated rather than one guessed at at /components/schemas/ContactV1
----

Use a conditional where the API needs one, and test the operations it reaches by hand until a release types it; the changelog says when one does.

[#errors]
== What stops a build

These are errors: the build stops, because what it would produce would be wrong.

None of the rules in <<testable,Writing a contract that can be tested §>> is one: a contract that breaks them builds, generates, and gets fewer contract tests, and the report says which.

[#publisher-errors]
=== From the Publisher

The Publisher prints each as `Error: <message>` and exits with 1.
Those an author causes:

[cols="3,2", options="header"]
|===
|Message |Cause, and what to do

|`target '<t>': <fragment> declares x-fragment-path; the Publisher sets that key and a fragment may not`
|A fragment writes the key itself. Remove it; only the Publisher sets it.

|`target '<t>': a component's fragment is also inlined elsewhere, so x-fragment-path would appear off its component: <location> (<fragment>)`
|A fragment that becomes a component is also inlined somewhere in the same document. Refer to the component there instead.

|`target '<t>': x-fragment-path names a fragment that is not in the library: <location> (<fragment>)`
|An AsyncAPI stamp arrived where no library file explains it, which means the bundler moved it. Report it, with the library that reproduces it.

|`<file>: no Markdown file found for {{<token>}}. Searched for <token>.md under <root>.`
|A placeholder has no snippet. Add `<token>.md` under the source root, or fix the token.

|`$ref target does not exist: <file>`
|A `$ref` points at a file that is not there. `lint`, `closure` and `changed` say so in these words; `build` fails in the bundler, whose output it prints.

|`target '<t>': no version file at <file>. Create it with a line such as 'version=1.0.0', or point targets.<t>.versionFile at the file that holds its version.`
|A published target has no version file.

|`target '<t>': <file> declares '<version>', but a version file holds a release version. Declare the release it leads to, and cut the pre-release with --pre-release <identifiers>.`
|The version file holds a pre-release.

|`target '<t>': <file>: '<version>' is not a semantic version. Contracts are versioned with semver so that consumers can reason about what a bump means.`
|The version file holds something that is not semver.

|`target '<t>': <file> declares no version`
|The version file has no `version` line.

|`<n> operation(s) in <file> have no example (lint.examples.<kind> is error):`
|`lint.examples.<kind>` is `error`, and an AsyncAPI message, or an OpenAPI request body or response, has no example. Each finding is listed below the line, worded as in <<give-every-operation-an-example,Give every operation an example §>>. Add the example, or set the key to `warn`.

|`lint failed for <n> document(s): <target> (<kind>); ...`
|A lint rule the library's configuration sets to `error` failed. The linter's output, printed above the message, names it.
|===

[#limits]
== What the tools will not do

[#constraints-are-constants]
=== Constraints are constants, not checks

`MAX_LENGTH`, `PATTERN` and the other constraint constants are there to build tests from.
A generated `body(...)` writes the arguments it is given; a body built from arguments that break a constraint breaks it too.

The constants are still constants.
From the same constraints, the TranscriberJ now also derives the contract cases: a valid request, and one invalid request per constraint, each breaking it alone (link:../../api-only-transcriberj/README.adoc#invalid-requests[Invalid requests →]).

[#fields-are-a-projection]
=== Field descriptions are a projection

A field is a path, a JSON type, whether it is optional, and a description.
A test that checks a payload against them proves that the payload has the fields the contract describes, of those types.
It does not prove that the payload is valid against the schema, and nothing here claims it does.

[#degradation-is-per-method]
=== Degradation is per method

A construct no rule represents makes the methods that reach it throw `UnsupportedOperationException`, with the reason and, where there is one, the remedy.
It never fails the build and never skips a class: the class, its constants and every other method are still generated.

[#verification-is-of-the-document]
=== Contract verification proves the document; generated contract tests verify the implementation

The Subscriber's lock and the TranscriberJ's `verifyContractSources<Contract>` prove that the document in the build is the one that was published, and that the generated classes were generated from it.
They prove nothing about the implementation.

The generated contract tests are the first thing in the toolchain that verifies the implementation: run against the service, they prove it answers every case as the contract declares, for everything the contract expresses -- the success responses, `404`, `406`, `415`, and every constraint on request input.
What the contract does not express, they cannot verify: a response that depends on behaviour, such as a `409`, is tested by hand.
And the generated stateless tests are not independent of each other, so a red run is read from its first failure: link:../../api-only-transcriberj/README.adoc#testing-principle[Generated stateless contract tests are not independent of each other →].

Whether every documented operation is implemented, and every implemented one documented, the tests do not say either.
That is what the https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-Gradle#readme[API-Only Suite ↗] is for: its Shadow, Mirage and Doppelganger API Detectors find the implemented-but-undocumented, the documented-but-unimplemented, and the implemented-but-unverified.

[#breaking-changes]
=== Breaking changes are not detected

Neither tool compares a contract with its previous release.
A breaking change is declared where it is made: a new schema version, and the contract's major version in its version file, in the same commit as the fragments it breaks.
The Publisher's `changed` command and each manifest's closure hash are the hooks a gate would need; the gate itself is deliberately not built (link:../../api-only-publisher/README.adoc#breaking-changes[Breaking changes →]).

[#repeated-definitions]
=== Repeated definitions are not detected

Two fragments that define the same thing, or a property written out again in several schemas, are each a legitimate schema.
Neither tool notices, so neither tool notices when the copies drift apart.
<<reference-shared-definitions,Reference shared definitions rather than repeating them §>> is a rule a review has to keep.

[#reading-the-reports]
== Reading the reports

[#lint-reports]
=== The Publisher's lint reports

`build` lints every document it builds, and says nothing about it unless the lint fails; then it prints the linter's output.
`lint` lints what is already built, prints the linter's output for every document, and writes it to `<reports.lint>/<target>/<kind>.txt` -- `build/reports/lint/orders/openapi.txt` by default.
Run without `--target`, it also writes `<reports.lint>/unreferenced.txt`.
So a lint *warning* is seen only by running `lint`: run it in CI, and read its reports.
The findings of <<give-every-operation-an-example,Give every operation an example §>> are different: `build` prints them in its log, `lint` does not run that check, and no report file is written.

What is in a lint report comes from Redocly CLI or AsyncAPI CLI, under the lint configuration `defaults.<kind>.lint` names:

* a rule the configuration sets to `error` fails the command: fix it now;
* a rule set to `warn` is reported and does not fail: it is the library's own backlog, and the library's policy decides when to act on it.

`unreferenced.txt` lists one file per line, and is empty when every fragment is reached.

Its lint reports also carry warnings from its own configuration -- `operation-4xx-response` and `required-string-property-missing-min-length` -- which that configuration sets to `warn` on purpose, as documentation-quality rules it does not yet enforce.
