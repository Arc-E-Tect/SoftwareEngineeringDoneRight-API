# Migrate a checked-in API document to a generated one

Help me replace API description documents that are committed under `src/main/resources` (or somewhere similar) with documents generated by the API-Only Publisher. Work in four phases, and **stop for my review at the end of each one**. The migration must never change what a consumer sees without my knowing.

Reference manual (read it if you can reach the web; the facts below are enough if you cannot):
https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-API/blob/main/docs/migrating-a-checked-in-document.adoc

## Principles

- **Phase 1 changes nothing downstream.** It proves that the generated document matches the committed one. If they differ in content rather than formatting, stop and show me. Never make the diff empty by editing the source until it matches.
- **Build only what is needed today.** Same project: direct file access. Same repository, different projects: the `file` channel into a committed directory. A registry only if I confirm the consumers live in other repositories.
- Migrating and refactoring are separate commits. Do not extract fragments or introduce placeholders during the migration.
- In phase 3, switch one consumer per commit.
- The `distribution` block is temporary and is deleted in phase 4.

## Facts: API-Only Publisher (do not invent options beyond these)

- npm package `@arc-e-tect/api-only-publisher`, pinned exactly to `0.0.2`. Requires Node 22+ and npm 10+.
- Run it **only** through an npm script: `"scripts": { "apionly": "api-only-publisher" }`, invoked as `npm run apionly -- <command>`, or `npm run --silent apionly -- ...` from Gradle or when capturing output. **Never run `npx api-only-publisher`**: that unscoped name is not the package. The one exception is the scaffold, `npx @arc-e-tect/api-only-publisher@0.0.2 init <dir>`.
- `apionly.yaml` (`schemaVersion: 1`): `sources.root`, `sources.openapi`, `sources.asyncapi`; `defaults.openapi.lint`, `defaults.<kind>.outputName`, `defaults.placeholders.strict`; `build.staging`, `build.dist`; `toolchain.redocly` (`"@redocly/cli@2.52.0"`), `toolchain.asyncapi` (`"@asyncapi/cli@6.0.2"`); `targets.<name>.openapi.bundle` / `.asyncapi.bundle`; `channels`; and the transitional `distribution`.
- `distribution: { root: <dir relative to apionly.yaml>, layout: "<path containing {target}>" }` makes `build` copy each built document into that directory. The directory must already exist.
- A bundle path is relative to `<sources.root>/<sources.<kind>>`. The built document is `<build.dist>/<target>/<outputName>`, fully bundled.
- `build --version <v>` stamps `info.version`. A bundle root that `$ref`s nothing is valid.
- The tool being replaced may have emitted `*MISSING CONTENT*` for an unresolved placeholder. The Publisher fails instead.

## Facts: API-Only Subscriber (destinations B and C)

- Gradle plugin `com.arc-e-tect.api-only-subscriber` version `0.0.2`, configured as `apiOnlySubscriber { channel { ... }; subscribe('<target>') { version = '...' } }`. It fetches into `build/api-spec/<target>/`, writes `apionly.lock` (committed), and runs `verifyApiSpec` as part of `check`.
- `channel { type = 'file'; directory = '...' }` reads `<directory>/<target>/<version>/<target>-<version>.tgz`, which is exactly what the Publisher's `publish --channel file` writes. `channel { type = 'maven'; groupId = '...' }` resolves through `repositories`.
- `subscription('<target>').openapi` always points at `openapi.yaml`, so keep the Publisher's default `outputName`.
- With two or more subscriptions and the `java` plugin, 0.0.2 fails `processResources` on a duplicate `manifest.json`. If that applies, stop and ask me.

## Phase 0: Investigate, then propose (do not edit anything yet)

Report:

1. Every committed API document: its path, format, `info.version`, and the project it belongs to (use `git ls-files` and look for OpenAPI/AsyncAPI files).
2. How each got there: a script, a build step, or by hand. Name the script if there is one.
3. Whether copies of the same API differ from each other (diff them).
4. The destination layout that fits, and why. Ask me to confirm:
   - **A**: the description lives in the implementing project (the `src/main/api/` library).
   - **B**: a specification library directory in this repository that publishes versioned archives into a committed `published/` directory; projects subscribe through the `file` channel.
   - **C**: a separate repository with published artifacts.
5. The target names.

Wait for my go-ahead.

## Phase 1: Reproduce what exists

1. Copy each committed document to `.migration/golden/<target>.yaml`.
2. Create the library: `npx @arc-e-tect/api-only-publisher@0.0.2 init <dir>`, plus a `package.json` with the pinned Publisher and the `apionly` script, then `npm install`. Put each existing document in whole as its target's bundle root.
3. Run `npm run apionly -- build --version <golden info.version>` and diff each result against its golden file. Classify every difference as one of:
   - `$ref` resolved (expected);
   - version (fix it with `--version`);
   - formatting only (confirm with a normalised comparison such as `diff <(yq -S . a) <(yq -S . b)`);
   - a `*MISSING CONTENT*` marker (a real defect; report it);
   - a real content difference (**stop and report**).
4. Add a `verify-golden.sh` script to the library that builds and diffs, and run it.

**Stop.** Show me the diffs and the script output, and wait.

## Phase 2: Generate into the existing locations

1. Add a `distribution` block so that `build` copies each document to where it is committed today.
2. Remove the old copying script or build step.
3. Run the build, and confirm that `git status` shows no content change to the committed documents.

**Stop and wait.**

## Phase 3: Switch consumers one at a time

Do the first consumer only, unless I tell you otherwise.

- **Destination A:**
  1. Build, and confirm the built document is identical to the committed copy.
  2. In **one commit**: delete the committed copy; add a Gradle `Exec` task `buildContract` that runs `npm run --silent apionly -- build`, with the fragment directory and `apionly.yaml` as inputs and the target's dist directory as output; add a single provider `def contract = buildContract.map { <dist dir provider>.get().file('openapi.yaml') }` and wire every consumer of the document to it; add `sourceSets.main.resources.srcDir(buildContract)` and `tasks.named('processResources') { dependsOn buildContract }`; and remove this consumer from the `distribution` layout.
- **Destination B:**
  1. Add `channels: { file: { directory: published } }` to `apionly.yaml` if it is missing, and make sure `published/` is **not** gitignored. Publish the version the consumer uses today: `build --version <v> --target <t>`, then `publish --version <v> --target <t> --channel file`. Commit the new `published/<t>/<v>/` directory.
  2. In the consumer, apply the Subscriber with `channel { type = 'file'; directory = "${rootDir}/<relative path to library>/published" }`, subscribe at `<v>`, and run `./gradlew fetchApiSpec`.
  3. Confirm `build/api-spec/<t>/openapi.yaml` is identical to the committed copy.
  4. In **one commit**: delete the copy, add `def contract = apiOnlySubscriber.subscription('<t>').openapi` and wire consumers to it, commit `apionly.lock`, and remove this consumer from the `distribution` layout.
- **Destination C:**
  1. Add `channels.maven` to `apionly.yaml` and publish the consumer's current version.
  2. Apply the Subscriber in the consumer, subscribe, and run `./gradlew fetchApiSpec`.
  3. Confirm `build/api-spec/<target>/openapi.yaml` is identical to the committed copy.
  4. In **one commit**: delete the copy and commit `apionly.lock`.

Run `./gradlew clean check` in the consumer and show the output.

**Stop and wait** before moving to the next consumer.

## Phase 4: Remove the scaffolding

Only once every consumer has been switched:

1. Delete the `distribution` block, `.migration/`, and `verify-golden.sh`.
2. Make sure `build/`, `dist/` and `node_modules/` are gitignored.
3. Show that `git ls-files '*/src/main/resources/*openapi*' '*/src/main/resources/*asyncapi*'` returns nothing.
4. For destinations B and C, remind me that the versioning policy still has to be written down.

## Finally

Summarise what changed across all phases. Then offer to record the conventions in `CLAUDE.md` or `AGENTS.md`, and ask before writing.
