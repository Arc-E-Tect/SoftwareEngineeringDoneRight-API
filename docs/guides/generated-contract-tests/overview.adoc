[#in-short]
== In short

From a contract, the API-Only TranscriberJ derives a *contract case* for every response the contract alone determines: a request, and the response the contract declares for it.
Its REST Docs emitter renders every case as a contract test, and its WireMock emitter as a stub.

So you no longer write a contract test for a success response, for a `404`, a `406` or a `415`, or for any declared constraint of a request.
You write the fixture each test needs, run the same tests against your service and against a double, and fix what they find.

A green run proves that the service answers every generated case as the contract declares: the status, the content type, and a body with the fields the contract describes.

It does not prove two things:

* *Nothing a generated test writes is documentation.*
The tests call `document()` to check a response, and the snippets that writes are never published: <<document,`document()` in contract tests §>>.
* *A response that depends on behaviour the contract does not describe is never generated.*
A `409`, a `422`, a `429`, a `401` or a `403` stays a hand-written contract test: <<hand-written,What stays hand-written §>>.

This guide builds on link:{example-dir}/README.adoc[the generated contract tests example →], a catalogue of books whose contract has three operations.

[#case-kinds]
== The case kinds

[cols="1,2,1,1", options="header"]
|===
|Kind |What it sends |Expects |Needs state

|Success
|A valid request: the required one, the full one, and the one without an optional body where there is one
|Each exact `2xx` the operation declares
|Yes

|Not found
|The valid request, naming a resource by other valid path values
|`404`
|Yes

|Not acceptable
|The valid request, with an `Accept` no declared response offers
|`406`
|No

|Unsupported media type
|The valid body, with a `Content-Type` the request body does not accept
|`415`
|No

|Invalid request
|The smallest valid request with exactly one constraint broken, one case per constraint
|The invalid-request status, `400` by default
|No
|===

A case is derived only for a status the operation declares exactly.
link:../../../api-only-transcriberj/README.adoc#contract-cases[Contract cases →], in the TranscriberJ's README, says how each is derived.

----

Read it as your list of contract tests.
Every covered response is a generated test; every uncovered one is either a response you write a test for by hand, or a change the contract needs.

An uncovered response has one of a closed list of reasons, in link:../../../api-only-transcriberj/README.adoc#response-coverage[Response coverage →].
The ones that point at the contract -- a range such as `4XX`, a `404` without a path parameter, an operation that does not declare the invalid-request status -- are rules for the contract's author, in link:../../reference/authoring-a-specification-library.adoc#declare-every-response[Authoring a specification library →].
The one that points at you is _depends on behaviour or state the contract does not describe_: here, the `409`.

[#pure-contract-tests]
== Pure contract tests: one test, two targets

The REST Docs emitter generates, for every operation with a case, an interface, `<Operation>ContractTests`, with one test per case.
The tests hold every value; what they do not hold is *which* implementation they test, and *what state* it is in.
A class implements the interface for each target, and supplies both:

* `client()`, a `WebTestClient` bound to the target and configured for Spring REST Docs;
* `arrangeState(ContractCase)`, called before every success and not-found case;
* `arrangeStatelessCase(ContractCase)`, called before every other case.

[cols="1,2,2", options="header"]
|===
|Hook |Default |What a target does with it

|`arrangeState`
|Throws `FixtureNotImplementedException`, which fails the test with the case, what it needs, and a suggested implementation to paste in.
|The real service: puts it in the state the case needs.
The double: nothing, since every case already has a stub.

|`arrangeStatelessCase`
|Does nothing.
|The real service: nothing, since it refuses the request before any state is consulted.
A double registering stubs from Java: registers the case's stub.
|===

A project compiles and runs straight after generation: every stateless test runs as it will for good, and every stateful one fails, saying what it waits for, until its target implements `arrangeState`.

[#testing-principle]
== The testing principle, and where generated tests break it

[WARNING]
.Generated stateless contract tests are not independent of each other
====
Tests must be independent of each other and idempotent: each passes or fails on its own, in any order, however often it runs.

*Stateless cases do not meet that principle* -- invalid request, not acceptable, unsupported media type.
They are derived from the contract, not from the implementation, and every case of an operation starts from the same valid request.
An implementation that wrongly accepts one may store what it was sent, and that state stays behind.

*Stateful cases meet it* -- success and not found -- when their `arrangeState` is correct, since it sets exactly the state each case needs, whatever ran before.

So one stateless case wrongly accepted can make later cases, of the same operation or another, answer differently, and differently again on the next run.
A correct implementation accepts no invalid request, so a green run is trustworthy.

When a run is red:

. read the *first* failing stateless test, and treat every later failure as possibly its consequence;
. fix what it points at;
. re-run on fresh state before you diagnose the next failure.

This is a known and accepted limit of generating tests from a contract, not a defect awaiting a fix.
====

*Why stateless cases cannot be independent.*
A stateless case needs nothing from the service: a correct one refuses it before the port is called, and stores nothing.
The generator cannot know what a *wrong* one stores, or how to undo it, because it derives the cases from the contract, not from the implementation.
And every invalid-request case of an operation is the same valid request with one fault, so what one of them leaves behind is exactly what the next one runs into.

*Why stateful cases can be.*
A success or not-found case says what state it needs.
A fixture that sets exactly that state -- inserts the book, deletes the book -- makes the case pass in any order, any number of times.
The example runs its contract tests twice on one database, and in random orders, and they pass every time.

*What it looks like.*

[#where-they-sit]
== Where contract tests sit among the other tests

*Unit and component tests* are scoped: each tests a unit, or one component, and mocks everything else.
That is why they are fast, and fail fast.
It is also why they bypass whatever lies outside their scope, and Spring Boot's JSON mapper lies outside the scope of every one of them.

Only the generated unknown-member case notices -- and an unknown member accepted unnoticed is how mass assignment starts.

*System tests* see the service with its real collaborators: a real database server, the services it calls.
*End-to-end tests* see the system as a user meets it.

So scoped unit and component tests are safe *because* a comprehensive contract test suite and a system test suite exist beside them.
Without those, nothing tests what JSON binding does, and a change in it -- a dependency upgrade, a default flipped -- ships unnoticed.

[#document]
== `document()` in contract tests

Every generated test calls `document()`, because that is where Spring REST Docs checks a response against its fields: `responseFields()` fails the test on a missing required member, an undeclared member of a closed body, or a wrong type.

No generated test calls `requestFields()`.
An invalid request is invalid by design, and a request-fields snippet would fail on the missing or unknown member it holds on purpose; a valid request needs no documentation from a contract test.

Calling `document()` writes snippets, under the prefix `generatedDocumentationPrefix()` returns, and those snippets are *never* published:

* their values are minimal by design -- a book titled `a`, of one page;
* a double's snippets carry the double: WireMock's `Matched-Stub-Id` and `Matched-Stub-Name` headers, which no real response has;
* contract tests exist to fail, not to explain.

The example gives each target a prefix of its own -- `generated-service`, `generated-stubs` -- so that neither overwrites the other, and its published page includes neither.
Published documentation comes from documentation tests written on purpose: link:../documentation-tests/overview.adoc[the guide to documentation tests →].

[#reading-a-failure]
== Reading a failure

*Read the first failing stateless test first*, as <<testing-principle,the warning §>> says.

A test that receives another status fails with a message that names the case and where to look.
It starts `<id> (<kind>: <description>): expected <status>, received <status>.` -- for an invalid request, `<id> (INVALID_REQUEST: <description>, at <location> <keyword>): ...` -- and goes on:

[cols="1,1,3,2", options="header"]
|===
|Kind |Received |Message |Where to look

|Success |`400` |The implementation rejects a request the contract declares valid. Compare its validation with the contract: an anchored or stricter pattern, a stricter length or bound, a member it requires that the contract makes optional, or an optional member of the full request it does not know.
|The inbound adapter's validation.
|Success |`404` |The fixture did not create the resource, or the implementation looks for it somewhere else. Check arrangeState for this case.
|`arrangeState`, then the persistence adapter.
|Success |`409` |State left behind: the fixture did not remove what this request creates. Check arrangeState for this case.
|`arrangeState` for a create.
|Success |another `2xx` |The implementation answers with a status the contract does not declare for this case, or the fixture set up the state for another declared status. Check arrangeState for this case.
|`arrangeState`, and the controller's status.
|Success |`5xx` |The implementation failed on a request the contract declares valid.
|The service's log.
|Not found |`2xx` |The fixture did not remove the resource, or the implementation answers for any identifier. Check arrangeState for this case.
|`arrangeState`, then the lookup.
|Not found |`400` |The implementation rejects an identifier the contract declares valid.
|The identifier's validation.
|Not acceptable |`2xx` |Content negotiation is not enforced: the implementation ignores Accept.
|The controller's `produces`.
|Unsupported media type |`2xx` |The implementation accepts a Content-Type the contract does not declare for this request.
|The controller's `consumes`.
|Unsupported media type |`400` |The implementation parsed the body before checking its media type.
|The order of the adapter's checks.
|Invalid request |`2xx` |The implementation accepted a request the contract declares invalid: `<keyword>` at `<location>` is not enforced.
|The request object's constraints, or the JSON mapper for `additionalProperties`, `type` and `null`.
|Invalid request |`404` |The implementation looked the resource up before validating the request. The inbound adapter should reject contract violations before the port is called.
|The adapter: validate before calling the port.
|Invalid request |`422`, where `400` is expected |A contract violation was treated as a domain violation. It should be rejected by the adapter, not the domain.
|The adapter: the domain never sees a contract violation.
|Invalid request |`5xx` |The implementation failed instead of rejecting the request.
|The adapter's error handling.
|Any |anything else |Nothing more.
|The first failing stateless test, if this one is not it.
|===

A response whose content type is not compatible with one the case declares fails naming the case, too; and `document()` fails on a body whose fields do not match the contract's.

A stateful test that has no fixture yet fails with `FixtureNotImplementedException`, its case, and a suggested `arrangeState` to start from.
The example's link:{example-dir}/README.adoc#try-it[Try it →], step 7, shows one.

[#stubs]
== The stubs

The WireMock emitter's stubs have two purposes.

* *An early, specification-compliant draft of the API, for its consumers.*
The team that implements the API hands them over, or publishes them, so that consumers can start before the implementation exists.
They answer as the contract says: the declared status, the declared content type, a body the contract allows.
* *The reference double for contract tests, in any language.*
The generated contract tests pass against them unchanged, and a team whose implementation is in Go or Python runs its own contract tests against the same archive, or an image built from it.

For every case there is an *exact stub*, which matches only that case's request.
For every other request, each operation has *fallbacks*, of lower priority, tried in this order: `406` for an unacceptable `Accept`, `415` for an unsupported `Content-Type`, the first declared `2xx` for a request its matchers call valid, and the invalid-request status for anything else on the operation's path.

A fallback enforces exactly what WireMock's matchers can:

* the body, by its JSON Schema, exactly -- except `format`, which only `uuid`, `date`, `date-time` and `email` are checked for, by their shape where `validateFormats` names them;
* a parameter by a regular expression derived from its schema, which enforces `required`, `type`, `enum`, `const`, `pattern`, `minLength` and `maxLength`, and never `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, `minItems`, `maxItems` or `uniqueItems`.

So a fallback is looser than the contract for parameters: a parameter only a bound rules out reaches the valid fallback, and gets the `2xx`.
A stub answers by no state: an operation that answers `200` or `201` to the same request gets the first one only.

link:{wiremock-readme}#packaging[Packaging and distribution ↗], in the WireMock emitter's README, says how to package, publish and run them; the example's link:{example-dir}/README.adoc[The stubs as a deliverable →] does it.

[#hand-written]
== What stays hand-written

A response that depends on behaviour the contract does not describe is never generated: `409`, `422`, `429`, `401`, `403`, any `3xx` or `5xx`.
Each gets one hand-written contract test, on the same pattern: a default test in an interface, a hook each target implements, the request built from the generated classes, and the response checked with the generated `*Docs` descriptors.
The example's `409` is one.

Which inputs the domain refuses, and why, is behaviour, and stays in behaviour tests.
link:../hand-written-contract-tests/overview.adoc#how-many[How many tests, and where →], in the guide to hand-written contract tests, states the whole rule.

[#adoption]
== Adoption in broad strokes

. *Read the generation report.* Its response coverage is your list of contract tests; fix the contract where a response is uncovered for a reason the contract causes.
. *Configure the emitters* for their purposes: schema classes wherever the API is exercised, REST Docs in the contract tests, WireMock on no source set.
. *Implement each interface twice*: once for your service, once for the double.
. *Run on the double first.* Every test passes there, or the stubs are wrong.
. *Implement `arrangeState` on your service*, one kind at a time, from the suggestion each failure prints.
. *Run on your service*, and treat every failure as a finding: read the first stateless failure first, fix, re-run on fresh state.
. *Write the responses the contract cannot generate by hand*, on the same pattern.
. *Publish the stubs* for your consumers.
. *Write the documentation tests* that produce your published documentation.
