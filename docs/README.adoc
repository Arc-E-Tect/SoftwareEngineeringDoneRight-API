[#what]
== What the tools do

The **API-Only Publisher** builds API contracts from a library of OpenAPI and AsyncAPI fragments: one bundled, linted document per contract, stamped with that contract's own version, and shipped as an archive with a manifest of hashes.

The **API-Only Subscriber** is a Gradle plugin that fetches such an archive at the version a build declares, verifies it, records it in a committed lockfile, and fails the build when the contract drifts.

Together they make an API contract something a build depends on at a known version, rather than a file someone copies around.

[#assumptions]
== What this documentation assumes

* You design APIs, and you know OpenAPI, and AsyncAPI where you use it.
* You know what bundling is: resolving a document's `$ref`s into one self-contained file, as https://redocly.com/docs/cli/[Redocly CLI ↗] does.
The Publisher uses Redocly CLI for OpenAPI and AsyncAPI CLI for AsyncAPI.
* The projects that implement or consume a contract build with Gradle.

[#which-use-case]
== Which use case is yours?

Answer three questions, in order:

. **Do you only consume a contract that someone else publishes?**
Yes: use case 4.
. **Do the projects that build against the contract live in a different repository from the contract?**
Yes: use case 3.
. **Does one project own its contract alone, or do several projects share a library of fragments?**
One project: use case 1.
Several projects: use case 2.

Every use case has the same four documents, and each stands on its own:

* the **overview** says when the use case fits, what you get, what you do not need, and the adoption in broad strokes;
* the **tutorial** builds it step by step, with every file, every value and what to consider;
* the **Claude Code prompt** and the **Codex prompt** have an AI coding assistant build it in your own project, starting with the checks that prove it works.

Use cases 1 and 2 need no registry: everything happens on the file system.
If you need a registry anyway, for reasons of your own, use case 3 shows how the same setup publishes to one.

[#prompts]
== Using the prompts

Each prompt is a Markdown file that takes an AI coding assistant from nothing to a working setup in your own project.
The assistant investigates first and proposes a plan, writes the checks before the changes that make them pass, runs every check itself, and never commits.

=== Claude Code

Start Claude Code at the root of your project, and paste the prompt; plan mode suits its first step.
To reuse it, save it as a project command, and run it as `/<file name>`:

[source,console]
----
mkdir -p .claude/commands
cp prompt-claude-code.md .claude/commands/api-contract-setup.md
----

=== Codex

Start Codex at the root of your project, and paste the prompt.
Codex also keeps reusable prompts as Markdown files in `~/.codex/prompts/`; how a saved prompt is invoked depends on the Codex version, so check its documentation.
The setup needs network access for `npm install` and for Gradle to resolve plugins, which a sandboxed session may ask you to approve.
