====

A Gradle plugin that generates a Java class tree from a subscribed API contract: bodies, field descriptions and constants for contract tests and stubs, derived from the contract rather than copied from it by hand.

It builds on the other two components.
The link:../api-only-publisher/README.adoc[API-Only Publisher →] bundles the contract and stamps every component with the fragment it came from; the link:../api-only-subscriber/README.adoc[API-Only Subscriber →] fetches it into the build and locks its version.
TranscriberJ reads what the Subscriber fetched, and nothing else: a project never needs access to the specification library.

[TIP]
====
Hand-written test descriptors catch drift between an implementation and the descriptor.
They cannot catch drift between the descriptor and the contract: if a schema gains a field and the test class does not, the contract test passes and documents the previous shape.
Generated from the locked contract, the descriptors change when the contract does.
====

The `J` is for Java.

[#plugin-id]
== Plugin ID

[source]
----
com.arc-e-tect.api-only-transcriberj
----

It applies the API-Only Subscriber, which it depends on.
A project that applies only this plugin gets the Subscriber release this one was built with, and `apiOnlySubscriber` works as that release's README describes.
Each Subscriber release opens a pull request that moves this plugin's dependency to that release, so the next TranscriberJ release brings it.

A contract is one OpenAPI document and, when it also describes events, one AsyncAPI document beside it.
Most contracts have only the OpenAPI document; from those, the TranscriberJ generates the HTTP side alone.
When the published archive also holds an `asyncapi.yaml`, the TranscriberJ reads both into one model and generates the event payloads, channels and operations as well, as <<asyncapi,The AsyncAPI document §>> describes.

[#applying]
== Applying the plugin

.build.gradle
[source,groovy,subs="attributes+"]
----
plugins {
    id 'java'
    id 'com.arc-e-tect.api-only-transcriberj' version '{api-only-transcriberj-version}'
}

apiOnlySubscriber {
    channel {
        type = 'maven'
        groupId = 'com.example.contracts'
    }
    subscribe('orders')
}

apiOnlyTranscriberJ {
    subscription('orders') {
        basePackage = 'com.example.orders.contract'
    }
}
----

The name in `subscription(...)` is the contract's name, exactly as the `apiOnlySubscriber` block subscribes to it, with `subscribe` or `subscribeAsClient`.

[#descriptions]
=== Descriptions

By default every description is the empty string.
The class tree exists for contract testing, and a description exists only for documentation; documentation is usually generated elsewhere, often with text a technical writer owns.

With `generateDocs = true`, descriptions come from the contract:

* A class's `description()` is its schema's description, or, for a reusable response, request body or parameter, the component's own.
* A field's description is its property's.
A `$ref` property is described by the component it refers to, unless the reference carries a description of its own.
* The text is used as the contract writes it, trimmed at both ends; line breaks inside it are kept.
* A class or field the contract does not describe is documented with the placeholder, `descriptionPlaceholder`, which says a description is still to come, and the report names it with the advice to describe it.
It does not fail the build.

[#description-bundles]
==== Descriptions a project owns

A team that writes its own documentation text, or documents a contract in more than one language, supplies a `ResourceBundle` and the generated classes resolve through it.
link:../docs/guides/description-bundles/tutorial.adoc[The description bundles tutorial →] builds it step by step, in English and Dutch, on https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-Library/tree/main/examples/api-only-transcriberj/description-bundles[a worked example ↗]:

[source,groovy]
----
apiOnlyTranscriberJ {
    subscription('orders') {
        basePackage = 'com.example.contract'
        descriptionBundle = 'docs.Descriptions'
    }
}
----

`docs/Descriptions.properties`, anywhere on the test classpath:

[source,properties]
----
UserV1=A user of the shop.
UserV1.username=The name the user signs in with.
UserV1.address.street=The street, house number included.
InvalidRequestProblemV1.errors[].message=What was wrong with the request.
----

A description resolves in one order, at the moment it is asked for:

. the bundle, if it carries the key and its text is not blank;
. what generation produced: with `generateDocs = true`, the contract's text, or the placeholder where it has none; without it, the empty string.

So a bundle is an overlay rather than a third mode: it wins where it has a key, and `generateDocs` decides what a key it lacks falls back to.
A missing bundle, a missing key and a blank entry are all the same thing -- the fallback -- so resolving a description never throws, and with `generateDocs = true` it is never empty.

The keys::
A class's key is its class name.
A field's key is `<ClassName>.<path>`, where the path is the one the field reports: `address.street` for a nested object, `errors[].message` for the members of an array's items.
A field whose type is another class is described by that class, under that class's own key, so a shared schema is described once.
`ContractDescriptions.keys()` lists every key the tree asks for.

Another language::
`description(Locale)` and `fields(String, Locale)` resolve in a locale, so one generated tree documents the contract in as many languages as the bundle has files.
A locale is looked up in its own file, then its parents' -- `nl_BE`, then `nl` -- then the base bundle, and never in the JVM's own locale: asked for English on a machine set to Dutch, the answer is English.
`-Dapionly.descriptions.locale=nl` sets the locale for a whole run, and `-Dapionly.descriptions.bundle=docs.Other` names another bundle, which is how a documentation build renders each language in turn.
Without either, the JVM's locale and the configured bundle apply.

What is not covered yet::
`ContractDescriptions.missing()` lists the keys nothing covers, so their descriptions are the generated text -- a reader's question.
`ContractDescriptions.untranslated(locale)` lists the keys that locale has no text of its own for, whatever it inherits from the base bundle -- a translator's question.
A test of your own can fail on either; nothing here fails a build.
The generation report names the configured bundle and how many keys it may carry.

Without `descriptionBundle`::
Nothing resolves and nothing is generated to resolve with: the classes are the ones generated before bundles existed, with their descriptions compiled in.

[#tasks]
== Tasks

[cols="2,3", options="header"]
|===
|Task |What it does

|`generateContractSources<Contract>`
|Generates the class tree, replacing whatever the output directory held, and writes its report, by default `build/reports/transcriberj/<contract>.txt` (`reportFile`), with the machine-readable report of every valid value beside it, `<contract>.valid-values.json`.
Runs whenever the contract document or the lockfile changes; the fetch runs first.

|`verifyContractSources<Contract>`
|Fails when the generated tree was generated from another version or document than the lockfile names.
`check` runs it.

|`updateApiOnlyTranscriberJDSL`
|Adds the `apiOnlyTranscriberJ` properties a build file does not set yet, with their defaults, to its existing block, keeping the original as `build.gradle.bak`.
`--generateApiOnlyTranscriberJDSL` writes the whole block when the build has none, with a commented example of a subscription; `--cleanupApiOnlyTranscriberJDSL` strips the comments inside the block.
|===

After upgrading the plugin, run `./gradlew updateApiOnlyTranscriberJDSL` to add any new property with its default to the `apiOnlyTranscriberJ {}` block.
It edits Groovy build files, as the Subscriber's `updateApiOnlySubscriberDSL` does, and never adds a subscription: a subscription names a contract and needs a `basePackage`, which only the build can say.

`<Contract>` is the contract's name as the Subscriber's tasks spell it: `user-account` is `UserAccount`.

[#ide]
== In the IDE

The class tree lives in `build/`, so an IDE sees it only once it has been generated.
The plugin therefore tells each IDE what to run on sync, and which directory holds generated code, reacting to whichever IDE plugin the build applies -- it applies none of them itself.

[cols="2,3", options="header"]
|===
|When the build applies |The plugin

|`org.jetbrains.gradle.plugin.idea-ext`
|Registers every `generateContractSources<Contract>` as an `afterSync` trigger, so importing or re-syncing the project in IntelliJ IDEA generates the sources before indexing them.

|`idea`
|Adds each contract's output directory to `idea.module.generatedSourceDirs`, so IntelliJ indexes it as generated code rather than as hand-written source.

|`eclipse`
|Adds every `generateContractSources<Contract>` to `eclipse.synchronizationTasks`, which Buildship runs when it synchronises the project.
|===

IntelliJ's sync hook lives in the https://github.com/JetBrains/gradle-idea-ext-plugin[idea-ext plugin ↗], which is not part of Gradle, so a build that wants it applies it:

[source,groovy,subs="attributes+"]
----
plugins {
    id 'org.jetbrains.gradle.plugin.idea-ext' version '1.4.1'
    id 'com.arc-e-tect.api-only-transcriberj' version '{api-only-transcriberj-version}'
}
----

Nothing else is needed: the plugin finds it, whether it is applied before or after the TranscriberJ.
It applies the `idea` plugin itself, so the generated directories are marked as well.

In a multi-project build, apply it in the root build:
IntelliJ reads the task triggers from the root project's model, so that is where every subproject's generation task is registered, whichever project applies idea-ext.

.Considerations
* **Without idea-ext**, IntelliJ resolves the generated classes after any build that runs the generation task -- `./gradlew generateContractSources<Contract>`, or any `compileTestJava` that depends on it -- and again after every `clean`.
Applying idea-ext, as in the `plugins` block above, is what makes that automatic.
* **Verification stays in `check`.**
Sync generates; it does not run `verifyContractSources<Contract>`, because a lockfile that has moved on should fail a build rather than a project import.
* **Eclipse** needs no extra plugin: `eclipse` is part of Gradle, and Buildship runs its synchronisation tasks.
* **The endpoint index** is a properties file read by other Gradle tasks, not source, so it is not offered to the IDE as a source directory.

[#generated-code]
== What is generated

Everything goes in the base package, flat, whatever directory a fragment was in.

[cols="2,3", options="header"]
|===
|From |A class

|A schema component
|Named after its fragment's file: `UserV1.yaml` is `UserV1`.

|A reusable response, request body or parameter
|Named after its fragment's file, as a schema is.

|An operation
|Named after its `operationId`, or else its method and path, followed by `Operation`: `GetUserOperation`.

|A schema written inline in an operation's request or response
|Named after the operation: `<OperationId>Request`, `<OperationId>Response<Status>`.
An operation without an `operationId` is named after its method and path.
A `oneOf` or `anyOf` whose branches are all references gets no class: each branch already has one.

|A message payload, from the contract's AsyncAPI document
|Named after its fragment's file, exactly as a schema component is: `RegistrationInitiatedEventV1.yaml` is `RegistrationInitiatedEventV1`.

|A channel of that document
|Named after its fragment's file, followed by `Channel`: `AuditV1.yaml` is `AuditV1Channel`.

|An operation of that document
|Named after its `operationId`, followed by `Operation`: `publishRegistrationInitiated` is `PublishRegistrationInitiatedOperation`.
|===

Two fragments with the same file name are told apart by the nearest directory in which their paths differ: `iff/user-account/schemas/UserV1.yaml` and `iff/other/schemas/UserV1.yaml` become `UserAccountUserV1` and `OtherUserV1`.
Only colliding classes are renamed, so adding an unrelated fragment never renames an existing class.
Names that still collide stop generation.

[#coverage]
=== Generated code is not measured for coverage

Every generated class carries `@ExcludeFromJacocoGeneratedCodeCoverage(justification = "Generated by API-Only TranscriberJ")`, from https://central.sonatype.com/artifact/com.arc-e-tect.sedr.utils/sedr-library[`com.arc-e-tect.sedr.utils:sedr-library` ↗].

JaCoCo skips a class annotated with an annotation whose simple name contains `Generated` and that is kept at runtime, and the `com.arc-e-tect.jacoco-exclusion-report` plugin lists the justification with every other exclusion.
Without it, a project that puts the generated tree on a source set it measures -- a service that publishes the payloads its contract describes, say -- would see its coverage fall by the size of a tree nobody wrote and nobody should have to test.
What the generated code does is checked where it is produced: by this plugin's own tests, and by `verifyContractSources<Contract>` in every build that uses it.

The plugin adds `sedr-library` to each configured source set the way it adds an emitter's dependencies: at a version it *prefers*, never forces, so a project already using the library keeps its own.

A class is public when code outside the package needs it: it is a request or response body, a parameter's schema, a non-schema component, something a public `body(...)` takes as an argument, or a branch of a `oneOf` or `anyOf` that a public body is one of.
Otherwise it is package-private, like a base schema only ever composed with `allOf`.

[#asyncapi]
=== The AsyncAPI document

A contract is one contract however its messages travel, so both of its documents are read into one model and generated together.

A message payload is a schema component like any other: it carries the same constants, the same constraints, the same provenance and the same `body(...)` methods a response body does.
What an event needs from its contract is narrower than what an HTTP call does, so a channel's class and an operation's class are narrower too -- no status codes, no path parameters:

[cols="2,3", options="header"]
|===
|Class |Holds

|`<Channel>Channel`
|`ADDRESS`, the address its messages travel over; `LOCATION`; and the provenance every class carries.

|`<OperationId>Operation`
|`OPERATION_ID`; `ACTION`, `send` or `receive`; `CHANNEL_ADDRESS`; `CONTENT_TYPE` and `MESSAGE_NAME` where the operation carries one message, or `CONTENT_TYPES` where it carries several; `LOCATION`; and `OPERATION_SHA256`.
|===

[#shared-fragments]
==== A fragment both documents use is one class

A specification library shares fragments between its two documents: an event payload references the schema of a username the HTTP responses use, so that a username means the same thing over a broker and over HTTP.

Both documents are bundled with `x-fragment-path`, so the same fragment is recognisable in both, and it becomes one class, generated once.
That is what makes the two documents generable into one package at all: generating them apart would produce two classes of the same name.

A fragment the two documents bundle as *different* bytes is reported rather than silently taken from one of them: the class could only match one document, and which one is not the generator's to decide.

The contract's AsyncAPI document needs `defaults.asyncapi.fragmentPaths` left on, as the OpenAPI document needs its own key; the link:../api-only-publisher/README.adoc#fragment-paths-asyncapi[Publisher's README →] describes what it stamps.

[#members]
=== What each class holds

* **Provenance**: `FRAGMENT_PATH` and `FRAGMENT_SHA256`, or, for an inline schema, `LOCATION` and `SCHEMA_SHA256`; and `CONTRACT_VERSION`.
The hash is SHA-256 over the component as bundled, `x-fragment-path` included, in https://www.rfc-editor.org/rfc/rfc8785[RFC 8785 ↗] canonical JSON.
* **Constraints**, as public constants: `MIN_LENGTH`, `MAX_LENGTH`, `PATTERN`, `FORMAT`, `ENUM`, `MINIMUM` and the rest.
An object's are prefixed with the property: `EMAIL_ADDRESS_MIN_LENGTH`.
They are constants only; generated bodies do not enforce them.
* **Where it is sent**, depending on what the class was generated from:
** a reusable request body or response, from `components/requestBodies` or `components/responses`: `CONTENT_TYPES`, every content type it may be sent as, and `CONTENT_TYPE` as well when there is exactly one;
** a parameter: `NAME`, `IN` and `REQUIRED`, and `SCHEMA` when its schema is a reference;
** a schema written inline in an operation: `OPERATION_ID` where the operation has one, `METHOD`, `PATH` and `CONTENT_TYPE`, and, for a response, `STATUS`, as a string;
** a schema component: none of these, even when it is used as a body.
A schema can be sent under more than one content type and status, so those belong to the operation: its class holds `REQUEST_CONTENT_TYPE` and `CONTENT_TYPE_<status>`, as <<operations,Operations §>> shows.
* **`description()`**: the empty string, or, with `generateDocs` on, the contract's description or the placeholder.
* **`body(...)`** and **`fields(prefix)`**, when the schema describes an object.
* **`requiredBody()`** and **`fullBody()`**, when the class is public and has `body(...)`: a valid body, as <<valid-values,Valid values §>> describes.

[#operations]
=== Operations

An operation's class holds what a test needs to call it, so a wrong endpoint fails to compile rather than at run time:

[source,java]
----
public final class GetUserOperation {
    public static final String OPERATION_ID = "GetUser";
    public static final String METHOD = "GET";
    public static final String PATH = "/v1/users/{username}";
    public static final int STATUS_200 = 200;
    public static final String CONTENT_TYPE_200 = "application/json";
    public static final int STATUS_404 = 404;
    public static final String CONTENT_TYPE_404 = "application/problem+json";
    // LOCATION, OPERATION_SHA256, CONTRACT_VERSION, REQUEST_CONTENT_TYPE where there is one

    public static String path(String username) { ... }

    public static ContractRequest requiredRequest() { ... }
    public static ContractRequest fullRequest() { ... }
    // noBodyRequest() where the operation's body is optional
}
----

`path(...)` fills in the placeholders in the order the path names them, and exists only when the path has any.
It uses the values as given, without encoding them, so a pattern such as `.*` stays a pattern in a WireMock matcher.
A status that is not a number, such as `4XX` or `default`, has content-type constants but no `STATUS_` constant.

[source,java]
----
webTestClient.get().uri(GetUserOperation.PATH, "alice")
wireMock.stubFor(get(urlEqualTo(GetUserOperation.path("alice"))))
----

[#endpoint-index]
=== The endpoint index

Tools that read test sources one file at a time, without a classpath, cannot see what `GetUserOperation.PATH` holds.
The generation therefore also writes `build/generated/transcriberj-index/<contract>/contract-endpoints.properties`, with every operation's and inline schema's path keyed `ClassName.PATH`; `endpointIndexFile` names another location.
The subscription exposes it as `endpointIndex`, carrying the generation task, so a tool reads it from there wherever it is written:

[source,groovy]
----
doppelgangerApiDetector {
    propertyFiles.from(apiOnlyTranscriberJ.subscriptions.named('orders').flatMap { it.endpointIndex })
}
----

The https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-Gradle/tree/main/doppelganger-api-detector[Doppelganger API Detector ↗] reads it, from version 2.10.1 on, to resolve `ClassName.FIELD` references in the tests it scans for contract evidence -- as does the https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-Gradle/tree/main/api-only-suite[API-Only Suite ↗] from 3.11.1 on, which applies it and passes its `propertyFiles` through.
Both do so through api-detector-core 1.8.0, which a build does not use directly.

[#bodies]
=== Bodies

`body(...)` writes a JSON body in the shape the contract describes, as compact JSON followed by a newline.

* A property with `const` is a private constant, always written, and never a parameter.
* Every other property is a parameter, in the order the contract declares it, with `allOf` flattened and `required` merged across its branches.
* `body(required...)` takes the required properties.
When there are optional ones, `body(required..., optional...)` takes those too, and leaves out each one that is `null`.
* A required argument that is `null` throws `NullPointerException`, naming it.

[cols="2,3", options="header"]
|===
|Property |Parameter

|`string` |`String`
|`integer` |`int`, or `long` for `format: int64`; boxed when optional
|`number` |`double`; boxed when optional
|`boolean` |`boolean`; boxed when optional
|An object, a `$ref` to one, a `oneOf`, or an untyped schema |`String`: JSON already written, typically by another class's `body(...)`
|An array |`List<String>`, `List<Integer>` and so on for scalar items; `List<String>` of written JSON for object items
|===

So bodies compose:

[source,java]
----
InvalidRequestProblemV1.body("The request is invalid", null, List.of(
        ErrorDetailV1.body("username is too long", "username")));
----

[#fields]
=== Field descriptions

`fields(prefix)` returns a `List<ContractField>`: a path, a JSON type, whether the field is optional, a description, and whether it is a subsection or open to members the contract does not list.

`ContractField` is generated into the base package, so the core classes depend on nothing.
A dialect turns these into its own descriptors: Spring REST Docs' `FieldDescriptor`, say.

A field is optional when the contract does not require it, or when an object it is inside is optional.
A `$ref` to another object delegates to that class; a recursive one is followed `recursionDepth` times and then described as a subsection.
A map, an object with `additionalProperties` and no properties of its own, is a subsection.

[#manifest]
=== The manifest

`ContractManifest` holds the contract's name, title, version and document hash, and an entry for every generated class, operations included, with what it came from.
One test can assert that the whole tree corresponds to the locked contract.

[#valid-values]
=== Valid values

A test of a `409` or a `422` starts from a request the contract accepts and changes one thing about it.
The tree generates that starting point, from the contract's constraints alone -- never from its `example` or `examples` -- so it changes when the contract does:

[cols="2,3", options="header"]
|===
|Member |Returns

|`requiredBody()`, on every public class with `body(...)`
|The smallest body the contract accepts: every required member and nothing else, and exactly `minItems` items in every array.
Compact JSON followed by a newline, as `body(...)` writes.

|`fullBody()`, on the same classes
|A body with every member the contract declares, and at least one item in every array that allows one.

|`requiredRequest()`, on every operation's class
|A `ContractRequest` with every required parameter and, when the operation declares a body, the minimal one -- whether the body is required or not.

|`fullRequest()`, on the same classes
|Every parameter a value is generated for, and the full body.

|`noBodyRequest()`, where an operation declares a body and does not require it
|The required parameters and no body: valid, since the contract says so, and worth a test of its own, as an optional body is often a mistake in the contract.
|===

`ContractRequest` is generated into the base package beside `ContractField`, and depends on nothing.
It holds the method, the path *template* -- the operation's `PATH` -- and, apart from it, the value of each placeholder in the order the path names them; the query parameters and the headers as lists of name and value, since a name may repeat; the content type; and the body as JSON text.
The last two are `null` without a body.
Nothing is encoded, as `path(...)` encodes nothing.

[source,java]
----
ContractRequest request = RegisterUserOperation.requiredRequest();
webTestClient.method(HttpMethod.valueOf(request.method()))
        .uri(RegisterUserOperation.PATH, request.pathParameters().toArray())
        .contentType(MediaType.parseMediaType(request.contentType()))
        .bodyValue(request.body())
        .exchange()
        .expectStatus().isCreated();
----

Every value these members return is valid by construction.
The invalid requests derived from them are in classes of their own: see <<invalid-requests,Invalid requests §>>.
Each returns the same value on every call, and is a constant compiled into the class.

[#valid-value-rules]
==== How a value is chosen

The rules below decide each value, and are what the TranscriberJ's own tests hold it to, checked against an independent JSON Schema 2020-12 validator.

[cols="2,5", options="header"]
|===
|Keyword or type |Value

|`const` |The const value.
|`enum` |The first listed value that satisfies every other keyword of the schema.
|`type: string` |`a`, repeated to `minLength` and at least once -- unless `maxLength` is `0`, which gives the empty string.
Lengths are counted in code points, as JSON Schema counts them, so a character outside the Basic Multilingual Plane is one.
|`pattern` |The shortest value that matches, within `minLength` and `maxLength`.
The pattern is read as ECMA-262 in Unicode mode and, as JSON Schema says, is _found_ anywhere in the value rather than matched against the whole of it: an unanchored match is padded with `a` to reach `minLength`.
Every pattern that applies must match.
A pattern with a backreference, a lookaround, a word boundary or a Unicode property escape has no value generated for it: see <<no-valid-value,When there is no valid value §>>.
|`format`, without `pattern` |A fixed value per format, made longer or shorter where the format allows, to meet `minLength` and `maxLength`:
`email` `user@example.com`; `uuid` `00000000-0000-4000-8000-000000000000`; `date` `2000-01-01`; `date-time` `2000-01-01T00:00:00Z`; `time` `00:00:00Z`; `uri` and `uri-reference` `https://example.com/`; `hostname` `example.com`; `ipv4` `192.0.2.1`; `ipv6` `2001:db8::1`.
Each uses a name or address reserved for documentation -- `example.com`, `192.0.2.0/24` and `2001:db8::/32` -- so a value a test sends never reaches a real host, as a loopback or private address could.
Any other format is a plain string, and the report notes it.
|`format` with `pattern` |The pattern wins, and the format is ignored.
|`type: integer` |`0` when it is valid; otherwise the smallest valid value at or above the lower bound; otherwise the largest at or below the upper bound; a multiple of `multipleOf` in each case.
|`type: number` |As an integer, in exact decimal arithmetic, so `multipleOf: 0.1` from `0.25` gives `0.3`.
Above an exclusive lower bound with no `multipleOf`, the next whole number, or, when that is beyond the upper bound, the midpoint of the two.
|`exclusiveMinimum`, `exclusiveMaximum` |Both forms: the number of OpenAPI 3.1, and the boolean beside `minimum` or `maximum` of 3.0.
|`type: boolean` |`false`.
|`type: array` |`minItems` items in the required body; at least one, where `maxItems` allows it, in the full one.
With `uniqueItems`, each different from the others.
|`type: object` |The required members, in the order they are declared.
When `minProperties` asks for more, the declared optional members first, then members named after a `patternProperties` pattern, then members `additionalProperties` allows, named `additional1`, `additional2` and on.
In the full body, every declared member.
|No `type`, and no keyword implying one |`null`.
Where keywords imply a type -- `properties`, `items`, `minLength`, `minimum` and the like -- the value is of that type.
|`$ref` |Followed.
In the full body, an optional member that refers back to its own component is followed `recursionDepth` times, as `fields(...)` follows it, and then left out; a required one that recurses deeper has no valid value.
|`allOf` |Every branch applies: the larger `minLength`, the smaller `maxLength`, every `pattern`, the values the `enum` lists have in common, the stricter bounds.
The class's constants and descriptors go on taking the first definition of each keyword, as they always have.
|`oneOf`, `anyOf` of references |The first branch, in declared order, whose value is valid; for `oneOf`, one valid against _exactly_ that branch, so a branch whose value another branch accepts too is passed over.
With a `discriminator`, the discriminating property takes the value its mapping gives the branch.
|`oneOf`, `anyOf` with an inline branch, a type list, a `true` or `false` schema |No value, as there is no `body(...)`: see <<unrepresentable,Constructs no rule represents yet §>>.
|`not`, `if`, `prefixItems` and every other keyword that asserts something the model does not type |No value: the schema's validity depends on it, and a value is never guessed at.
|===

A parameter's value is its value as it travels, a string: an integer parameter's is `"0"`.
Only a parameter with a primitive schema and the default `style` for where it is sent -- `simple` in the path and a header, `form` in the query -- has one.
One in a cookie, with an array or object schema, described by `content`, or with another `style` or `explode` is reported as not supported yet: an optional one is left out of `fullRequest()`, and a required one leaves the request without a value.
Header parameters named `Accept`, `Content-Type` or `Authorization` are ignored, as OpenAPI says they are.
A body is sent as the first JSON content type the operation declares -- `application/json`, or any `+json` type; an operation that accepts none has no valid request.

[#valid-value-determinism]
==== The same contract, the same values

Every choice is made by a fixed rule, and nothing depends on the clock, the machine, its locale or its time zone.
The same contract generates byte-identical sources, and byte-identical reports, on every run and every machine, so the generation task stays up to date.

[#no-valid-value]
==== When there is no valid value

When the contract leaves no valid value -- `minLength` above `maxLength`, bounds that cross, `enum` lists with no value in common, a pattern no value of the allowed length matches, `uniqueItems` with fewer distinct values than `minItems`, a required member that recurses forever -- or this generator cannot find one, it never falls back to something that merely looks right.
The method is generated as one that throws `UnsupportedOperationException`, naming the location in the contract and the reason, and the report lists it under _No valid value could be generated_.
The build does not fail.
A full body can have no valid value where the required one has -- `maxProperties` below the number of members declared, for instance -- and then only `fullBody()` throws.

[#valid-values-report]
==== The machine-readable report

Beside the report, generation writes every valid value as JSON, for tools and tests to read: `build/reports/transcriberj/<contract>.valid-values.json`, or, with `reportFile` set, the same name with `.valid-values.json` in place of `.txt`.
It is compact, its members sorted by name, and its entries by class, so the same contract gives the same bytes:

[source,json]
----
{
  "schemaVersion": 1,
  "contract": "orders",
  "version": "1.4.0",
  "bodies": [
    {
      "class": "OrderV1",
      "location": "/components/schemas/OrderV1",
      "requiredBody": {"value": {"id": "a", "quantity": 1}},
      "fullBody": {"unsatisfiable": {"location": "/components/schemas/OrderV1", "reason": "..."}}
    }
  ],
  "requests": [
    {
      "class": "PlaceOrderOperation",
      "location": "/paths/~1orders/post",
      "method": "POST",
      "pathTemplate": "/orders",
      "requiredRequest": {"value": {"method": "POST", "pathTemplate": "/orders", "pathParameters": [],
                                    "query": [], "headers": [{"name": "X-Tenant", "value": "a"}],
                                    "contentType": "application/json", "body": {"id": "a", "quantity": 1}}},
      "fullRequest": {"value": {"...": "..."}},
      "noBodyRequest": {"value": {"...": "..."}}
    }
  ],
  "unsupportedParameters": [
    {"class": "PlaceOrderOperation", "location": "/paths/~1orders/post/parameters/1", "name": "tags",
     "reason": "a parameter whose schema is an array is not supported yet"}
  ]
}
----

Each variant holds either `value`, the value the method returns, or `unsatisfiable`, with the `location` and the `reason` the method throws.
`noBodyRequest` is present only where the method is.
`schemaVersion` changes when the shape does.

[#invalid-requests]
=== Invalid requests

A contract that declares a response for an invalid request makes a promise about every constraint it puts on request input: break one, and that response comes back.
For each such constraint the tree derives a *case*: the operation's smallest valid request -- `requiredRequest()` -- with exactly that one constraint violated, paired with the response the contract declares.
Nothing is taken from convention: a case expects a response only because the operation declares it.
Every constraint either has a case or is listed in the report with the one reason it has none.
None is left out.

The cases are data.
They render nothing and depend on nothing: an emitter turns them into tests or stubs, and a hand-written test can use them as they are.
They are generated whether or not an emitter renders them.

[cols="2,3", options="header"]
|===
|Class |Holds

|`InvalidRequestCase`, in the base package beside `ContractRequest`
|One case: a record of `id`, `description`, `in`, `name`, `pointer`, `keyword`, `request`, `expectedStatus`, `expectedContentTypes`, `responseBodyClass` and `representative`.

|`<Operation>InvalidRequests`, for every operation -- `InitiateUserRegistrationInvalidRequests` beside `InitiateUserRegistrationOperation`
|`CASES`, the operation's cases in canonical order, and `CASE_COUNT`.
Empty where the operation declares no invalid-request status, or no constraint on its input.
|===

[cols="1,3", options="header"]
|===
|Field |What it is

|`id` |Readable, unique within the operation, and the same on every run: `query-page-minimum`, `body-emailAddress-maxLength`, `body-unknown-member`.
It becomes a test method name and a snippet directory, so it is a valid Java identifier once converted, as `JavaText.variableName` converts it.
Two cases whose ids would read the same -- `/a-b` and `/a/b` both give `body-a-b-type` -- are told apart by a suffix, `-2`, given in canonical order.
Where a body declares more than one JSON media type, the media type is part of the id: `body-application-merge-patch-json-name-maxLength`.
|`description` |One sentence for a display name: "`page` below its minimum of 0".
|`in`, `name`, `pointer` |Where the fault is: `path`, `query`, `header` or `body`; the parameter's name, or the JSON pointer into the body -- the empty string for the body as a whole.
For a missing required member and for an unknown member, the pointer names the member.
|`keyword` |The violated keyword as the contract spells it -- `minimum`, `required`, `type`, `additionalProperties` -- and as a JSON Schema validator reports it: a `null` case records `type`, and a 3.0 `minimum` with `exclusiveMinimum: true` records `exclusiveMinimum`.
|`request` |The complete violating request, as a `ContractRequest`. Its values are raw: encoding them for the path, the query or a header is the renderer's job.
|`expectedStatus`, `expectedContentTypes` |The declared status, and every content type the declared response is declared with; empty when it has no content, and only the status is expected.
|`responseBodyClass` |The simple name of the generated class for the declared response's body, resolved through a `$ref` to `components/responses` where there is one; `null` without content.
|`representative` |Whether this is the case whose documentation is published: the first in canonical order, so exactly one per operation.
|===

*Canonical order* is path parameters, then query parameters, then headers, then the body; within each, `required`, then `type`, then `null`, then the other keywords in the order of the table below; then by name or pointer.

[#invalid-request-derivation]
==== How each case is derived

Start from `requiredRequest()`, and change exactly one thing.
A constraint of an optional parameter or member is reached by adding it first, with a valid value, then breaking it.
Nested objects and array items are derived the same way, at their pointer -- `/items/0/quantity`, `/address/postalCode` -- as deep as `recursionDepth` allows.

[cols="2,5", options="header"]
|===
|Keyword |The one change

|`required`, a body member |The member removed.
|`required`, a query or header parameter |The parameter left out.
|`required`, the request body |No body.
|`type` |A value of a type no binder coerces: see below.
|`null` |`null`, for a member or item whose type does not allow it.
|`enum` |A value of the right type that is not listed.
|`const` |A value of the right type that differs from it.
|`minLength`, `maxLength` |One code point too few or too many, still matching the pattern and the format where there is one.
|`pattern` |A value of a valid length that does not match.
|`format`, where `validateFormats` names it |A value of a valid length that is not of the format.
|`minimum`, `maximum` |One unit below or above -- one `multipleOf` where there is one.
|`exclusiveMinimum`, `exclusiveMaximum` |Exactly the bound.
|`multipleOf` |A value within the bounds that is not a multiple.
|`minItems`, `maxItems` |One item too few or too many, each item valid.
|`uniqueItems` |Two equal valid items.
|`minProperties`, `maxProperties` |One member too few or too many.
|An unknown member |A member named `unexpectedMember`, or, where `patternProperties` names members, a name no pattern matches; its value `"unexpected"`. See <<strict-requests,Strict requests §>>.
|===

*One fault per case is not optional.*
A case is kept only when the request breaks the one keyword at the one place and nothing else -- checked, keyword by keyword, against everything that applies there, including the `allOf` it is part of.
Where no value breaks a constraint alone -- a `minLength` whose length the pattern forces, an `enum` that lists nothing shorter than `maxLength` -- there is no case, and the report names the keyword that breaks with it.
A `minLength: 6` email is one: the shortest address a strict validator accepts, `a@b.co`, is six characters long.

*Types a binder does not coerce.*
Many JSON binders coerce by default: Jackson turns `5` into `"5"` for a string, truncates `1.5` into an integer, and reads `"5"` as a number.
A type case sending a coercible value would pass or fail by the binder's settings rather than by the contract, so:

* a string gets an object, `{}`;
* a number or an integer gets the string `"not-a-number"`;
* a boolean gets the string `"not-a-boolean"`;
* an object gets an array, `[]`, and an array gets an object, `{}`.

Coercible violations -- `5` for a string -- are not derived.
They are real violations, and a lenient binder lets them through; a setting to derive them as well can be added when a project needs it.

[#invalid-request-never]
==== What is never derived, and why

* *A `required` case for a path parameter.* A path without the segment is a different route: a test on it tests routing, not validation.
* *A path value that is empty, or contains `/`, `?` or `#`,* even percent-encoded: it changes which endpoint the request reaches.
* *A `type` case for a string parameter, and a `null` case for any parameter.* Every parameter travels as a string, and an empty one is not `null`.
* *Positive boundary cases* -- a value exactly at a bound. They are valid requests, not invalid ones.
* *Conditional keywords* -- `if`, `then`, `else`, `dependentSchemas` and every other keyword the model does not type. Reported, never guessed at.
* *A case from a request that cannot be vouched for:* one holding a value of a format no check exists for, such as `duration`. The value might be invalid already, and a case must have one fault.
* *Malformed JSON, an unsupported media type (`415`),* and anything that needs a fixture on the real implementation.

[#invalid-request-status]
==== The expected response

`invalidRequestStatus`, `400` by default, is the status that means "the request is invalid".
An operation must declare exactly that status for cases to be derived; neither a `4XX` range nor `default` counts, since both are too broad to be a promise about invalid input.
An operation that constrains its request input and does not declare it is a *gap*: it gets no cases, and the report recommends declaring the status.

[#strict-requests]
==== Strict requests

`strictRequests` is on by default: a request object that does not declare `additionalProperties` forbids the members it does not declare, and an unknown-member case is derived for it.
An explicit `additionalProperties: true`, an `additionalProperties` schema, or `patternProperties` is respected, and no such case is derived; an explicit `additionalProperties: false` is the contract's own and always has its case.
Strictness is judged against the members the whole `allOf` declares: a member one branch defines is known to the object.

Turning it off prints, on every generation that runs, a warning that is meant to be hard to ignore, and records it in the report:

----
WARNING: strictRequests is off for contract 'orders'. No request is tested for unknown members, so the
service may accept them unnoticed: mass assignment (OWASP API3:2023 Broken Object Property Level
Authorization) and unvalidated input passed on (OWASP API10:2023 Unsafe Consumption of APIs). Turn
strictRequests back on; where a contract deliberately allows unknown members, declare
additionalProperties: true instead.
----

A generation that is up to date does not run, and prints nothing.

[#validate-formats]
==== Formats

A format is only as exact as the validator that checks it, so format cases are opt-in, per format: `validateFormats = ['email']`.

* A pattern wins over a format. Where both apply and the format's validation is on, the format is ignored, no format case is derived, and a warning says so.
* A well-known format with no pattern beside it is recommended one, whether or not its validation is on: a pattern says exactly what is valid.
* A format `validateFormats` names that no check exists for is reported, and never guessed at.

[#constraint-coverage]
==== Constraint coverage and gaps

The report lists every constraint on request input -- every keyword of every parameter schema, of every request-body schema, and of every schema they reach within `recursionDepth`, and every object the strict rule applies to -- each with the ids of the cases that cover it, or exactly one reason it has none:

[cols="1,3", options="header"]
|===
|Reason |Meaning

|not isolatable |Every violating value breaks another keyword too; the report names it. Inside a `oneOf` or `anyOf` of references, that keyword is the choice itself.
|changes the route |A path parameter's `required`, or a path value only an empty or `/`, `?` or `#` value would violate.
|keyword not modelled |`not`, `if`, `contains` and the other keywords the model does not type -- and the other constraints of a schema whose validity depends on one.
|parameter style not supported |A parameter no valid value is generated for: in a cookie, an array or an object, a `style` or `explode` other than the default, or described by `content`.
|inside a degraded construct |Inside a `oneOf` or `anyOf` with an inline branch.
|format validation not switched on |`validateFormats` does not name the format.
|pattern overrides format |The format's validation is on, but a pattern applies there too.
|operation declares no invalid-request status |The gap: every constraint of such an operation that has no reason of its own.
|strictness turned off |The implied unknown-member rule, with `strictRequests = false`.
|beyond `recursionDepth` |Reached only by following a reference more often than `recursionDepth` allows.
|not expressible in a parameter |`type` of a string parameter: every parameter travels as a string.
|format not supported |`validateFormats` names a format no check exists for.
|no valid baseline |There is no valid request to change: the operation, or the member to add, has no valid value, or holds one that cannot be vouched for.
|asserts nothing |A keyword no value can violate: `minLength: 0`, `uniqueItems: false`, `required: []`, a 3.0 `exclusiveMinimum: false`, a parameter's `required: false`.
|no violation rule |`oneOf` or `anyOf` of references: it composes schemas rather than constraining a value.
|media type not used |A request body media type that is not JSON.
|===

The list is closed: a constraint with a reason not on it is a change to this README first.

The report also lists the *gaps*, each with the recommendation to declare the invalid-request status, and the *format recommendations*, each well-known format with no pattern and where it is.
The build log prints the counts:

----
API-Only TranscriberJ: user-account 1.0.0: Invalid requests: 22 case(s) derived, 19 constraint(s) covered,
9 uncovered (changes the route: 2, operation declares no invalid-request status: 5, not isolatable: 1,
format validation not switched on: 1), 2 gap(s)
----

In the machine-readable report they are `invalidRequests` -- each operation's cases, and for each the valid `baseline` request it differs from in the one place the fault is -- `constraintCoverage`, `gaps` and `formatRecommendations`.

[#unrepresentable]
== Constructs no rule represents yet

Nothing stops the build, and no class is skipped.
The class and its constants are generated; only a method that cannot represent a construct is generated as one that throws `UnsupportedOperationException`, with the reason and, where there is one, the remedy.

These are the constructs no generation rule covers *yet*: a future version addresses them where a rule is possible and worth having, and the changelog says when one does.
Until then, the remedy -- usually a change to the contract -- is the way out, and link:../docs/guides/hand-written-contract-tests/overview.adoc[the guide to hand-written contract tests →] covers what to do when the contract cannot change.
A `body(...)` that cannot be generated takes `Object...`, since its parameters cannot be known.

[cols="2,1,3", options="header"]
|===
|Construct |Treatment |Note

|`oneOf`/`anyOf` whose branches are all references |Represented |Each branch has its own class, with its own `body(...)`.
A schema that is nothing but such a choice has no `body(...)` or `fields(...)` of its own, and its Javadoc names the branches.
|`oneOf`/`anyOf` with an inline branch |Degraded |Whether or not the schema says `type: object`.
Remedy: name the branches, so each becomes a component.
A choice between values rather than objects, such as a string or an integer, is written as a value and has no body to degrade.
|`discriminator` |Represented |
|`additionalProperties`, `patternProperties` |Represented |Recorded as `open`; a map is a subsection.
|A recursive `$ref` |Represented |To `recursionDepth`.
|`type` naming several types, such as `[string, 'null']` |Undecided, and degrades what reaches it |No rule decided yet.
Always listed as undecided; a `body(...)` or `fields(...)` that reaches it also degrades.
One that nothing reaches, such as a member of a map's values, degrades nothing.
|A schema written as `true` or `false` |Undecided, and degrades what reaches it |As for several types.
|Any other keyword the model does not type |Undecided |Kept, and listed as undecided.
The model types `$ref`, `type`, `format`, `description`, `const`, `enum`, `required`, `properties`, `patternProperties`, `items`, `additionalProperties`, `allOf`, `oneOf`, `anyOf`, `discriminator` and the constraint keywords, and keeps `title`, `default`, `examples`, `example`, `readOnly`, `writeOnly`, `deprecated`, `externalDocs`, `xml`, `$comment`, `contentMediaType`, `contentEncoding` and every `x-` key as annotations; anything else -- `not`, `if`, `prefixItems`, `nullable` -- is listed.
|Security schemes, headers and other component types |Undecided |Kept, and listed as undecided.
|One fragment bundled as different bytes in two places, such as the contract's two documents |Undecided |One class is generated, from the copy read first -- the OpenAPI document's when the fragment is in both -- so it may not match the other; listed as undecided, as <<shared-fragments,A fragment both documents use is one class §>> describes.
|===

The report lists every degraded method, every recommendation and every undecided construct in `build/reports/transcriberj/<contract>.txt` (or the subscription's `reportFile`), and the build log gives the counts.
A valid-value method that reaches such a construct throws too, and is listed under _No valid value could be generated_ rather than among the degraded methods, with every other valid-value method that has no value; the build log counts those, and the parameters not supported yet, as well.
A construct can appear in both lists: *undecided* says the contract uses it, *degraded* names each method it made throw.
A report with undecided constructs and no degraded method means nothing generated was affected.
A schema written inline in an operation is generated, and also listed with the recommendation to make it a component.

[#depth-warnings]
=== Depth is warned about

A contract that goes three levels deep is more often an accident than a design, so generation warns, in the build log and the report, whatever `recursionDepth` allows:

* when `recursionDepth` is set above 3;
* when a recursive `$ref` runs through 3 or more components, such as `A -> B -> C -> A`;
* when a request or response body nests objects 3 or more levels deep, following references and list items, such as `order.customer.address`.

A warning never fails the build.

[#emitters]
== Emitters

An emitter adds a dialect: companion classes in `<basePackage>.<emitter id>`, such as REST Docs descriptors or WireMock stubs, built on the core classes.
None is included; a project adds the ones it wants to `transcriberjEmitters`.

Two are published from https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-Library[the Library repository ↗]:

[cols="1,3",options="header"]
|===
|Emitter |What it generates

|`com.arc-e-tect:api-only-transcriberj-restdocs`
|Spring REST Docs field descriptors and snippets for every class with a body (`<basePackage>.restdocs`).

|`com.arc-e-tect:api-only-transcriberj-microcks`
|From the AsyncAPI document, one JUnit 5 conformance test per `send` operation, checking what an application publishes against a Microcks-imported copy of the contract, as `<basePackage>.microcks.AsyncConformanceHarness`. What a generator cannot know -- the broker, where the contract file is, how the application publishes each event -- is left to abstract methods the project implements. It also writes a properties resource, which is what `EmitterContext.writeResource` is for. It needs every message to carry an `examples` array, which the Publisher can enforce with `lint.examples.asyncapi`.
|===

Each one's README lists what it needs of the project.
They run after the core emitter, each in a class loader built from that configuration, so their dependencies never mix with the build script's.

An emitter is a library that implements `com.arc_e_tect.gradle.apionly.transcriberj.spi.Emitter`, and names its implementation in `META-INF/services/com.arc_e_tect.gradle.apionly.transcriberj.spi.Emitter`.
The interface is part of the plugin: an emitter compiles against `com.arc-e-tect:api-only-transcriberj`, from the Gradle Plugin Portal's repository, as a `compileOnly` dependency, since the plugin provides it when it loads the emitter.
Only the `model` and `spi` packages are meant for emitters.

[source,groovy,subs="attributes+"]
----
repositories {
    gradlePluginPortal()
}

dependencies {
    compileOnly 'com.arc-e-tect:api-only-transcriberj:{api-only-transcriberj-version}'
}
----

[source,java]
----
public interface Emitter {
    String id();                              // "restdocs": its package, and its name in reports
    List<ManagedDependency> dependencies();   // what its generated code needs
    Set<Construct> represents();              // which classified constructs it handles in full
    void emit(EmitterContext context);        // model, settings, class names, writeJava, writeResource, degraded
}
----

`EmitterContext.names()` gives every core class's name, so a companion always matches the class it belongs to.
`EmitterContext.writeResource(path, content)` writes a non-Java file -- a properties file a generated or hand-written class reads through `getResourceAsStream`, for instance -- to the resource root the project's source sets read from, the way `writeJava` writes a class to the sources root.
`path` is `/`-separated and relative, such as `"META-INF/restdocs/service.properties"`; it may not be absolute, and may not use `.` or `..` segments.
`EmitterContext.degraded(...)` returns the statement a method that cannot represent a construct consists of, and records it in the report.
`ClassNames.invalidRequests(location)` names an operation's `<Operation>InvalidRequests` class, which `ClassNames.all()` does not list: its origin is `Origin.INVALID_REQUESTS`.
An emitter with an exhaustive `switch` over `Origin` has one more constant to handle.

[#emitter-options]
=== Emitter options

A project configures an emitter with `emitterOptions`, per subscription, keyed by the emitter's id; each value is a map of names to strings:

[source,groovy]
----
apiOnlyTranscriberJ {
    subscription('orders') {
        basePackage = 'com.example.orders.contract'
        emitterOptions = [restdocs: [tests: 'true']]
    }
}
----

The TranscriberJ does not interpret them.
It passes them to the emitter unchanged, through `EmitterContext.settings().emitterOptions(id())`, empty when the project gave none; what each option means is the emitter's README's to say.
The options are an input of the generation task, so changing one regenerates.
Options for an id no emitter on `transcriberjEmitters` has fail the build, naming the ids there are: a mistyped id is not silently ignored.

[#emitter-dependencies]
=== What the generated code depends on

An emitter declares the libraries its generated code needs, the version it was tested with, and the first version it was not.
The plugin adds each to the source sets it generates into, at a version it only _prefers_: Gradle uses it when nothing else in the build asks for a version, declared or transitive, so a project's own choice always wins.

The core generated code declares one of its own, on the same terms: `com.arc-e-tect.sedr.utils:sedr-library`, for the marker annotation in <<coverage,Generated code is not measured for coverage §>>.

After resolution, a version at or above the untested one is warned about: "not tested with this plugin version", naming the emitter, the library and the version.
`strictDependencies = true` makes that a build failure instead.

[#hand-written-code]
== Hand-written code beside the generated classes

The generated tree does not cover every test: a degraded method throws, and the only invalid requests generated are the cases for the one status the contract declares for invalid input -- one fault each, see <<invalid-requests,Invalid requests §>>.
A `409`, a `422` for a semantically invalid request, and whatever a constraint not isolatable leaves untested are written by hand.
The code a project writes to fill those gaps goes beside the generated classes, and how it does so is a design decision, not an accident.

[IMPORTANT]
.Hand-written test code goes in the generated package
====
Put hand-written code that builds on the generated classes in the subscription's `basePackage`, in a source set that compiles the generated tree: for the default, `src/test/java/<basePackage as a path>/`.

The generated tree keeps its public surface to what callers outside the package need (<<coverage,which classes are public §>>).
Everything else is package-private, and so is only in reach from that package:

* `ContractJson`, the JSON writer every generated `body(...)` uses: `string(value)`, `member(json, name, value)` on a `StringBuilder` begun with `{`, `close(json)`, `embed(body)` and `array(values)`;
* scalar components, such as a constrained string or number, with their constraint constants;
* any other class nothing outside the package needs.

Generation replaces its own output directory on every build and never touches `src/`, so the two sit in one package without either overwriting the other.

These package-private members are *not* a published API.
They are generated with the tree on every build, so they always match the generated bodies, but an upgrade of the TranscriberJ may change them.
Hand-written code that uses them then fails to compile, and has to be adjusted.
====

[#your-responsibilities]
=== What the generated classes do not hold, and what that makes your responsibility

Some of what a contract says is not generated anywhere.
Hand-written code that needs it types it, and from then on the project -- not the generator -- is responsible for it matching the contract:

* **The members of a schema whose `body(...)` degraded**: their names, which are required, and how they nest.
* **`const` values.** A named component writes its `const` members itself, from a private constant; a branch written inline holds its `const` values nowhere.
A body that must carry one -- the `destination` that says which branch a `oneOf` body is -- types it.
* **Constraints written inline inside an inline branch.**
Only components a branch refers to carry their constraints as constants; a `pattern` or `maxLength` written in the branch itself is generated nowhere.
* **That the hand-written code matches the contract at all.**
`verifyContractSources<Contract>` checks the generated tree against the lockfile; nothing checks hand-written code.

So a project that writes its own tests on top of the generated classes takes on four duties:

. **Draw on the generated classes wherever they hold the value**: `AmountV1.MAXIMUM + 1`, not `1000001`.
A generated constant that disappears then breaks the build at the line that used it; a literal goes on compiling while it drifts from the contract.
. **Pin each hand-written part to what it was written against**: a test that compares the class's `FRAGMENT_SHA256` (or, for an inline schema, `SCHEMA_SHA256`) with the value it had when the code was written.
It is the only signal that a typed value may have changed, since nothing else fails when a member is renamed.
When it fails, check the hand-written code against the contract, then update the pinned value.
. **Assert that a degraded method still throws**, and delete the hand-written replacement when it no longer does: a contract that improves, or a TranscriberJ that learns the construct, makes it redundant.
. **Write only what is missing.** Where the report gives a remedy, taking it -- naming the branches of a `oneOf`, making an inline schema a component -- makes the contract generable for every consumer, and leaves nothing to type.

[#limits]
== What this cannot do

The generated field descriptions are a *lossy projection* of the contract.
A field description says a path, a type and whether it is optional; a JSON Schema says considerably more.
A test built on them proves that a payload has the fields the contract describes, of the types it describes.
It does not prove that the payload is valid against the schema, and nothing here claims it does.

Constraints are constants, not checks.
Generated bodies are built from the arguments given, and a body built from arguments that violate a constraint violates it too.
For the invalid-request status, one invalid request per constraint on request input is derived, in <<invalid-requests,Invalid requests §>>; every other invalid or partial body, for the other 4xx responses, is written by hand, starting from a valid one: `requiredBody()`, `requiredRequest()` and the rest, in <<valid-values,Valid values §>>.
link:../docs/guides/hand-written-contract-tests/overview.adoc[The guide to hand-written contract tests →] says how to write them, and anything else the generator could not, on top of the generated classes -- and how many to write.

[#development]
== Development

[source,console]
----
cd api-only-transcriberj
./gradlew check
----

One build, one artifact: the plugin, the built-in core emitter, and the contract model and emitter interface emitters compile against (the `model` and `spi` packages) are released together, at one version.
It is published to the Gradle Plugin Portal as `com.arc-e-tect.api-only-transcriberj`, with the artifact `com.arc-e-tect:api-only-transcriberj`, by `.github/workflows/api-only-transcriberj-release.yml`, under the `api-only-transcriberj-v*` tags.
`./gradlew publishToMavenLocal` puts it in `mavenLocal` for use before a release.

The tests generate from the contracts of this repository's link:../reference-api/README.adoc[reference API →], `system-admin` and `user-account` -- of which only `user-account` has an AsyncAPI document -- read from `../reference-api/dist`, where its build commits them.
They also read fixtures of their own from `src/test/resources/fixtures/`: the Publisher's `init` scaffold, which generates an OpenAPI document only, no AsyncAPI one, and whose `SOURCE.properties` says how to rebuild it; and the corpora and golden files below.

`src/test/resources/fixtures/valid-values` holds what valid-value generation is held to: a corpus of contracts written for it, one golden file of valid values per reference contract, and the hash of every source generated before valid values were.
Its `README.adoc` says what each is for; `./gradlew recordValidValuesGolden` and `./gradlew recordBaselineSources` re-record them, for a deliberate change only.

`src/test/resources/fixtures/invalid-requests` holds what invalid-request derivation is held to: a corpus of contracts written for it, and the golden cases and coverage of the reference API's `user-account` contract, which are the tests an implementation of it is run against.
Its `README.adoc` says which test covers which requirement; `./gradlew recordInvalidRequestsGolden` re-records the golden file, for a deliberate change only.

The build gates on 90% instruction coverage, with no exclusions, and on Javadoc without warnings.
The plugin's tasks are tested in-process as well as through TestKit, so the coverage agent sees them.
