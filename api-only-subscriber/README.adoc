A Gradle plugin that fetches published API description documents into a build, verifies them against a committed lockfile, and fails when a contract has drifted.

It is the consumer half of a pair. The link:../api-only-publisher/README.adoc[API-Only Publisher] builds and publishes the documents; this fetches and verifies them. The two are coupled only by the published artifact and its `manifest.json`, and neither knows anything else about the other.

Its users are implementation projects: both the provider implementing a contract, and genuine API clients generating stubs from one.

[TIP]
====
The question this plugin changes is which one your build is answering.
Before: _does this implementation match this file that happens to sit in `src/`?_
After: _does this implementation match the organisation's published contract, at version X?_
====

== Applying the Plugin

=== Using the `plugins` block (recommended)

.Groovy DSL
[source,groovy]
----
plugins {
    id 'java'
    id 'com.arc-e-tect.api-only-subscriber' version '0.0.1'
}
----

.Kotlin DSL
[source,kotlin]
----
plugins {
    java
    id("com.arc-e-tect.api-only-subscriber") version "0.0.1"
}
----

The `java` plugin is optional. Applied alongside it, the fetched documents are added to the main resources so they reach the classpath; without it, they are still fetched and verified, just not packaged.

== How it works

. **Resolve.** Each subscription names a target and a version. The `maven` channel turns that into a dependency and lets Gradle resolve it; the `file` channel reads a directory.
. **Unpack.** The archive is extracted into `build/api-spec/<target>/`.
. **Check against the archive's own manifest.** Every document the manifest declares must be present and must hash to what the manifest says. An archive that disagrees with itself never reaches the build.
. **Lock.** The resolved version, the channel, and each document's SHA-256 are written to `apionly.lock`, which is meant to be committed.
. **Verify.** `verifyApiSpec` re-hashes what is on disk and fails when it no longer matches the lockfile.

A version that is already locked, coming back with *different* bytes, is refused rather than silently re-locked. That is a released version rebuilt, or a tag moved, and a lockfile that quietly accepts it locks nothing.

== Configuration

The plugin registers an `apiOnlySubscriber` extension.

.Groovy DSL
[source,groovy]
----
apiOnlySubscriber {

    // Where the resolved versions and file hashes are recorded. Commit this file:
    // it is what verifyApiSpec checks against, and what makes "which contract is
    // this project building against?" answerable by reading the repository.
    // Default: apionly.lock, beside the build file
    // lockfile = layout.projectDirectory.file('apionly.lock')

    channel {
        // Which kind of channel to resolve through: 'maven' or 'file'.
        // Default: maven
        type = 'maven'

        // The Maven group the contracts are published under. Required by the
        // maven channel.
        // Default: unset
        groupId = 'com.example.contracts'

        // The artifact extension the contracts are published with, used to form
        // the dependency notation group:name:version@extension.
        // Default: tgz
        // extension = 'tgz'

        // The directory the file channel reads from. Archives are expected at
        // <directory>/<target>/<version>/<target>-<version>.tgz.
        // Default: unset
        // directory = "$rootDir/build/publish"
    }

    subscribe('user-account') {
        // The version of this target's contract to build against. Required.
        version = '2.1.0'

        // Whether this subscription may resolve a pre-release contract.
        // Default: false
        // allowPrerelease = false

        // Overrides channel.groupId for this one target, when it is published
        // somewhere else than the rest.
        // Default: unset, meaning channel.groupId applies
        // groupId = 'com.example.other-contracts'

        // Overrides the artifact name this target is published under.
        // Default: the target name
        // artifactId = 'user-account'

        // Where this subscription's documents land.
        // Default: build/api-spec/<target>
        // into = layout.buildDirectory.dir('api-spec/user-account')
    }
}
----

.Kotlin DSL
[source,kotlin]
----
apiOnlySubscriber {
    channel {
        type.set("maven")
        groupId.set("com.example.contracts")
    }
    subscribe("user-account") {
        version.set("2.1.0")
    }
}
----

=== Channels

[cols="1,3",options="header"]
|===
| Channel | Notes

| `maven`
| The default. The artifact is declared in a detached configuration and Gradle's own dependency resolution performs the fetching, caching and up-to-date checking — so this plugin carries no HTTP client, no cache and no retry policy of its own.

| `file`
| A local directory. The escape hatch for iterating on a contract before it is published anywhere, and the only channel that reads the filesystem directly.
|===

Resolving only through channel APIs is also what keeps an accidental path dependency on the specification repository from creeping in: in a single repository the fragments are always reachable, so such a dependency would never fail.

=== Pre-releases

A contract that is not finished must never quietly satisfy a build, so a pre-release version is refused:

[source]
----
subscription 'user-account' resolves the pre-release version 1.1.0-rc.1.
A contract that is not finished must not quietly satisfy a build. Set
allowPrerelease = true on this subscription to work against it deliberately,
and remember to take it off again before release.
----

Working against one is a deliberate, reviewable line:

.Groovy DSL
[source,groovy]
----
subscribe('user-account') {
    version = '1.1.0-rc.1'
    allowPrerelease = true
}
----

Both the SemVer spelling (`-rc.1`, `-alpha.3`) and Maven's `-SNAPSHOT` count as pre-releases — the latter because it is what Maven consumers expect, even though it is not SemVer-legal.

== Tasks

[cols="2,1,3",options="header"]
|===
| Task name                    | Group         | Description

| `fetchApiSpec`               | api-only      | Fetches every subscribed contract. Aggregate over the per-target tasks.
| `fetchApiSpec<Target>`       | api-only      | Fetches one subscribed contract, verifies it against the manifest inside its own archive, and records it in `apionly.lock`.
| `verifyApiSpec`              | verification  | Checks every fetched contract against the lockfile. Aggregate over the per-target tasks.
| `verifyApiSpec<Target>`      | verification  | Checks one fetched contract against the lockfile.
| `updateApiOnlySubscriberDSL` | api only subscriber | Adds missing `apiOnlySubscriber` properties with their defaults to `build.gradle`.
|===

`<Target>` is the target name in camel case: `user-account` gives `fetchApiSpecUserAccount`.

`verifyApiSpec` **is** wired into `check`, so contract drift fails an ordinary build rather than waiting for someone to look. `processResources` depends on the fetch, so a build that packages resources fetches them first.

After upgrading the plugin, run `./gradlew updateApiOnlySubscriberDSL` to add any
new defaulted properties to the existing `apiOnlySubscriber {}` block. The task
backs up the original file as `build.gradle.bak`. If the block is absent, it
leaves the file unchanged unless run with
`--generateApiOnlySubscriberDSL`. Subscription targets and versions are never
invented by the task.

Running them explicitly:

[source,shell]
----
./gradlew fetchApiSpec
./gradlew verifyApiSpec
----

=== Why `verifyApiSpec` does not depend on `fetchApiSpec`

It is ordered *after* the fetch, but does not depend on it. Depending on it would re-fetch before checking, overwriting a hand-edited document and reporting success — quietly repairing the exact drift the task exists to find.

== Using the fetched documents

Each subscription exposes its documents as providers derived from the fetch task, so anything wired to them carries the task dependency automatically:

.Groovy DSL
[source,groovy]
----
apiOnlySuite {
    rootDocument = apiOnlySubscriber.subscription('user-account').openapi
}
----

.Kotlin DSL
[source,kotlin]
----
apiOnlySuite {
    rootDocument.set(apiOnlySubscriber.subscription("user-account").openapi)
}
----

Handing out a bare path instead would let a consumer read the directory before anything had populated it. Gradle rejects that outright, which is the class of bug these providers exist to remove.

== Where documents land

`build/api-spec/<target>/`, registered as an additional resources directory.

Not `src/main/resources`. Generated files inside a source tree show up in IDE search, tempt hand-editing, and survive a `clean`. From `build/` they reach the classpath identically, `clean` removes them, and nothing gitignored lives under `src/`.

Writing into `src/` stays possible for teams whose tooling insists on it — set `into` on the subscription — but it is not the default.

== The lockfile

`apionly.lock` is committed, and records per target the resolved version, the channel it came from, and the SHA-256 of every fetched file:

[source]
----
# apionly.lock -- the published contracts this project builds against.
# Generated by the Arc-E-Tect API-Only Subscriber. Commit it; do not edit it.
# Run `verifyApiSpec` to check that what is on disk still matches.
format 1

target user-account
version 2.1.0
channel maven
sha256 18baaca0249e15659105a2467338f32bab6d35a48fb1f088dfa30777f2e12059 asyncapi.yaml
sha256 f2a09aed8880faf8e1debf77b9f1f71ca94a5ff13bc217cce3e2df7ef307b739 openapi.yaml
----

It is a small, sorted, line-oriented text file rather than JSON because it is read by people in review far more often than by machines, and a one-line diff should mean one thing changed.

=== What it catches

[cols="2,3",options="header"]
|===
| Situation | What happens

| A fetched document is edited by hand
| `verifyApiSpec` fails, reporting the locked hash and the hash on disk.

| A released version is rebuilt and republished with different bytes
| `fetchApiSpec` refuses to re-lock it, naming each document that differs.

| An archive disagrees with its own `manifest.json`
| `fetchApiSpec` refuses it before anything is unpacked into the build.

| A version is upgraded deliberately
| The lock is updated, and the build logs `Updated user-account from 2.1.0 to 2.2.0`.
|===

=== Why this is not what Gradle already does

Gradle verifies that the *artifact* it downloaded matches its coordinates. The lockfile and manifest verify that the *files extracted into the build* still match what the producer published. Both are needed, and only the second catches a hand-edited document sitting in `build/`.

== Full example

.build.gradle
[source,groovy]
----
plugins {
    id 'java'
    id 'com.arc-e-tect.api-only-suite' version '3.10.0'
    id 'com.arc-e-tect.api-only-subscriber' version '0.0.1'
}

repositories {
    mavenCentral()
    maven {
        name = 'apiContracts'
        url = uri('https://maven.pkg.github.com/example/contracts')
        // Gradle reads apiContractsUsername and apiContractsPassword from
        // gradle.properties, or from ORG_GRADLE_PROJECT_apiContracts* in the
        // environment. Nothing about the credential is named in the build file,
        // which is the point: a build file gets committed.
        credentials(PasswordCredentials)
    }
}

apiOnlySubscriber {
    channel {
        type = 'maven'
        groupId = 'com.example.contracts'
    }
    subscribe('user-account') {
        version = '2.1.0'
    }
}

apiOnlySuite {
    rootDocument = apiOnlySubscriber.subscription('user-account').openapi
}
----

[source,shell]
----
./gradlew fetchApiSpec     # resolve, unpack, lock
./gradlew check            # build, test, and fail on contract drift
----

== A caution about `mavenLocal()`

The local Maven repository is a convenient test harness, not a faithful model of a remote one: its metadata and snapshot-staleness behaviour differ. Confirm pre-release semantics against a real remote before relying on them.

== Relationship to the API-Only Suite

The link:https://plugins.gradle.org/plugin/com.arc-e-tect.api-only-suite[API-Only Suite] bundles the Shadow, Mirage and Doppelganger detectors, which answer _does this implementation match its contract?_

This plugin answers a different question: _where does the contract come from, and is it still what we agreed?_ A project can reasonably want either without the other, so they are separate plugins, applied side by side.
